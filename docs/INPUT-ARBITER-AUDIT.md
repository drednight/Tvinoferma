# Нативный арбитр: аудит и первый этап внедрения

## Граница текущего этапа

Реализован процесс-локальный арбитр `src-tauri/src/input_arbiter.rs`.
Это первый защитный слой, НЕ полное завершение архитектуры из обсуждения.
Не меняет совместимость фоновых сообщений с игрой.

Политика normal lane пока **отказ при занятости**, а не накопление очереди.
Устаревший ввод не должен неожиданно воспроизводиться позднее. Арбитр держит
lease на время нативной операции, а повтор — на время worker-сессии вместе
с очисткой. Весь составной JS-план пока не имеет единой нативной lease.

| Канал | Вмешательство | Защита первого этапа |
|---|---|---|
| game_macro_action | Focus, foreground/background keys, click, layout | Эксклюзивная нативная операция; generation захватывается до spawn_blocking |
| game_macro_pointer | Курсор, клики, оконная мышь | Та же lease; конфликтующий вызов получает отказ |
| game_macro_background_probe | WM_NULL/активность, тест клавиш | Эксклюзивная diagnostic lease |
| Калибровка game_macro_guide | Фокус перед показом координат | Lease вокруг подготовки/фокусировки, не на всё время открытого guide |
| receiver_send | Оконные тестовые клавиши | Receiver lease; receiver не подтверждает эффект в игре |
| mirror worker | Повтор клавиш/мыши | Lease на worker до защитных отпусканий; очередь уже ограничена 256, возраст событий 250 мс |
| game_macro_input_stop | Отмена текущей generation | Не ждёт освобождения operation lease; короткий dispatch barrier |
| Ctrl+Alt+Pause | Аварийный хоткей | Нативная отмена до уведомления JS; UI также вызывает stop IPC |
| Launcher press_enter | Enter в свежем диалоге запуска GC | Вне арбитра макросов на этом этапе; отдельная ownership-проверка, требуется дальнейшее согласование |
| input_receiver закрытие | WM_CLOSE собственного окна | Не игровой ввод; не включено в normal lane |
| Перечисление клиентов/геометрия | Чтение | Может выполняться параллельно, но geometry внутри action пока консервативно получает lease |

## Отмена и точка упорядочивания

Stop и отдельная отправка используют общий короткий dispatch mutex. Поэтому
после точки отмены старый down не проходит; down, вошедший раньше stop, мог
быть отправлен. Stop не ждёт всей команды/задержки/очереди. Синхронные отправки
с таймаутом и комбинированный пакет повторителя могут задержать этот барьер:
нулевая задержка и полное отсутствие влияния зависшего Win32 не обещаются.

Cleanup допускается после отмены. Фактическое отпускание выполняет владелец
операции/повторителя по существующему пути очистки. Отдельного параллельного
исполнителя priority releases пока нет: запуск второго отправителя без единого
учёта удержаний создал бы гонку up-before-down. Lease освобождается после cleanup,
поэтому новый владелец не накладывается на старые отпускания. Физически удержанные
пользователем клавиши и неудачная доставка up остаются ограничением.

Отмена не блокирует все будущие явные вызовы навсегда: новая операция получает
новую generation, но лишь после освобождения предыдущей lease. Уже запланированный
worker со старой generation отказывается при acquire. Вызовы, поступившие после
stop, считаются новыми; это не полноценный протокол run_id для всего JS-плана.

SendInput получает проверку поколения; cleanup определяется по UP-флагам.
Фоновые клавиши/уведомления и оконная мышь проходят dispatch barrier.
Повторитель проверяет отмену, останавливает обработку очереди и отпускает свои
учтённые клавиши. Фокус/курсор макроса проверяются на отмену перед изменением.
Существующие проверки личности, foreground и DPI сохранены.

## Что ещё НЕ выполнено

- Нативный run_id/token на весь составной план; сейчас lease на отдельный IPC.
- Объединение с Enter лаунчера и другими системными каналами управления окнами.
- Единый учёт всех удержаний и отдельный исполнитель приоритетной очистки.
- Новый foreground-протокол и условное восстановление курсора/фокуса.
- Полная новая схема фаз DeliveryReport и UI timeline арбитра.
- Transport-рефакторинг/state machine.

Поэтому сборка предназначена для проверки первого защитного этапа, а не для
заявления «все конфликтующие операции приложения уже согласованы».

## Автоматические проверки

Нативные unit-тесты: конкуренция каналов; удержание lease после stop до cleanup;
отказ старой generation; новый явный запуск; отменённый down и разрешённый up;
конкурентное упорядочивание stop/dispatch. Windows compile/clippy/tests должны
пройти для точного HEAD. JS-тесты не подтверждают нативную отправку.

## Протокол проверки на Windows

1. Начать с receiver и одной безопасной клавиши. Не включать расходные действия.
2. Во время повтора запустить диагностическую пробу: ожидается отказ busy,
   не параллельная отправка. Для пробы сначала явно выключить повтор.
3. Запустить последовательность с задержкой, нажать Ctrl+Alt+Pause:
   следующие действия не должны отправляться; проверить отсутствие залипания.
4. После завершения очистки явно запустить новую короткую команду.
5. Проверить обычные клики/клавиши без повтора, затем повтор отдельно.
6. Проверить смену foreground во время удержания. Не считать условное
   восстановление полностью реализованным на этом этапе.
7. Сохранить метод, версию, foreground до/после, коды Windows и наблюдаемый эффект.
   Не присылать пароли, cookies и ссылки авторизации. После timeout не повторять
   автоматически: предыдущее действие могло быть обработано.
