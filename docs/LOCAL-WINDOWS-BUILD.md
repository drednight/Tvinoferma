# Локальная тестовая сборка Windows

Скрипт `scripts/build-windows-local.ps1` собирает текущий checkout на вашем ПК,
без GitHub Actions и расхода его минут. Он **не устанавливает системные инструменты**,
не скачивает секреты GitHub, не переключает ветку, не публикует релиз, не создаёт
установщик/подпись автообновления и не запускает полученную программу.

## 1. Подготовка один раз

Нужна **Windows x64**, доступ в интернет и несколько гигабайт свободного места
(для Rust/SDK/кэшей лучше иметь запас в десятки гигабайт).

Установите из официальных источников:

1. **Git for Windows** — <https://git-scm.com/download/win>.
2. **Node.js 22 LTS**, не ниже 22.12 — <https://nodejs.org/> (включая npm).
3. **Visual Studio Build Tools 2022** — <https://visualstudio.microsoft.com/downloads/>,
   раздел Tools for Visual Studio → Build Tools. В установщике выберите
   **Desktop development with C++ / Разработка классических приложений на C++**,
   MSVC x64/x86 и Windows 10/11 SDK.
4. **Rust stable, MSVC x64** — <https://rustup.rs/>.
   Если уже установлен другой toolchain, выберите нужный самостоятельно:
   `rustup default stable-x86_64-pc-windows-msvc`.
5. **Microsoft Edge WebView2 Runtime** — нужен для запуска приложения:
   <https://developer.microsoft.com/microsoft-edge/webview2/>.

После установки откройте **новое** окно PowerShell. Поддерживается Windows
PowerShell 5.1 и PowerShell 7. Обычный запуск не требует прав администратора.
Системные установщики могут отдельно запросить повышение прав.

## 2. Получить исходники

Для первой загрузки откройте PowerShell в папке, где хотите хранить проект:

```powershell
git clone --branch arena/95755e6b-tvinoferma --single-branch https://github.com/drednight/Tvinoferma.git
cd Tvinoferma
git rev-parse --short HEAD
```

Скрипт и все его файлы должны быть из одного checkout, не копируйте только `.ps1`
поверх старой версии проекта. Если используете существующий checkout нужной ветки,
обновите его сами после проверки местных правок:

```powershell
git status --short
git branch --show-current
git pull --ff-only
```

Не сбрасывайте свои изменения через `reset --hard`. Скрипт по умолчанию откажется
собирать изменённую рабочую копию. Параметр `-AllowDirty` разрешает её явно, но
результат получает отметку `dirty: true`: SHA коммита уже не описывает весь код.

## 3. Запустить сборку

Из корня репозитория:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\build-windows-local.ps1
```

`Bypass` действует только на этот процесс PowerShell; глобальная политика не меняется.
Не обходите корпоративную политику, запрещающую выполнение скриптов.

По умолчанию выполняются `npm ci`, lint, проверка форматирования, типов и
Tauri release build без упаковки. Используются `tauri.acceptance.conf.json` и
Cargo feature `acceptance` вместе; несовпадающая пара блокирует запуск. Отдельный
каталог `src-tauri/target/acceptance` не перезаписывает обычную сборку. Frontend
собирается автоматически через `beforeBuildCommand`. Cargo использует `--locked`, LTO выключен и codegen-units=16,
как у acceptance-сборки. Target явно `x86_64-pc-windows-msvc`.

**Первая сборка может быть долгой**: загружаются npm/Rust-зависимости и компилируется
приложение. Прогресс виден в консоли; не закрывайте её. Скрипт останавливается
при ненулевом коде любой команды, а изменённые lock-файлы не откатывает молча.

### Дополнительные режимы

Полные frontend-тесты и Rust library tests (дольше, не равнозначно всем заданиям CI):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\build-windows-local.ps1 -Checks Full
```

Повторная сборка с уже установленными зависимостями:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\build-windows-local.ps1 -SkipInstall
```

`-SkipInstall` не подтверждает соответствие `node_modules` текущему lock-файлу.
После изменения зависимостей запускайте без него. `-Checks None` пропускает lint,
format/typecheck и тесты, но не саму сборку; это **не успешное прохождение CI**.
Не выдавайте такую сборку за проверенный релиз.

## 4. Где результат и как его использовать

При успехе консоль напечатает `SUCCESS: ...`. В новой папке
`local-acceptance/isolated-<дата>-<коммит>-<суффикс>/` появятся:

- `Tvinoferma.exe`;
- `SHA256SUMS.txt` — SHA-256 исполняемого файла;
- `BUILD-INFO.json` — коммит, ветка, признак местных правок, версия и режим проверок;
- `READ-ME.txt` — ограничения и предупреждения.

Предыдущие сборки не перезаписываются. Папка исключена из Git.
Можно проверить хеш вручную:

```powershell
Get-FileHash .\local-acceptance\<папка-сборки>\Tvinoferma.exe -Algorithm SHA256
```

**Это неподписанная тестовая программа, а не установщик. Встроенный номер версии
может совпадать со стабильным. Настроены отдельные identifier, папки приложения,
WebView-профили и пространства имён Windows vault; updater отключён. Эти разделения
пока НЕ проверены на Windows и не являются доказанной изоляцией. Запускайте только в
отдельной тестовой учётной записи Windows без рабочих данных Твинофермы. Не запускайте
одновременно с другой версией, пока ручная проверка ниже не завершена.**

Скрипт сам приложение не запускает. SmartScreen может предупредить об отсутствии
подписи; не отключайте защиту Windows целиком. Проверьте происхождение исходников
и собранного файла. Копирование exe не переносит профиль, контакты или vault.

Для тестов фонового ввода см. `docs/GAME-MACROS.md`. Сборка сама по себе не доказывает
совместимость с игрой. Скрипт не получает OAuth-настройки CI: облачные интеграции,
требующие build-переменных, могут быть недоступны. Для игровых проверок не нужно
копировать секреты из GitHub или пересылать их в чат.

## Если сборка не удалась

- `Missing prerequisite` / MSVC: установите нужные компоненты и откройте новое окно PowerShell.
- Ошибка линкера/Windows SDK: проверьте C++ workload и SDK в Visual Studio Installer.
- `npm ci` не скачивает пакет (в том числе SheetJS): проверьте интернет/прокси,
  затем повторите без `-SkipInstall`. Не отключайте TLS и не меняйте lock-файл наугад.
- Cargo сообщает, что lock-файл требует обновления: не удаляйте его; пришлите ошибку.
- Сообщение о грязной копии: сначала посмотрите `git status --short`; скрипт ничего не сбрасывает.
- Ошибка компиляции Rust: это полезный результат — Windows-компиляция новых правок
  могла не пройти на GitHub из-за лимита. Нужен текст ошибки, не повторные попытки вслепую.

Пришлите SHA исходников (`git rev-parse HEAD`), выбранный режим и последние строки
ошибки. При успешной сборке достаточно `BUILD-INFO.json`; `.exe` для диагностики
не нужен. Перед отправкой вывода уберите пароли, токены и личные пути. Не присылайте
переменные окружения, cookies, vault или резервные копии данных.

Скрипт подготовлен в Linux-среде: настоящая Windows-сборка должна быть выполнена
на вашем ПК; статические проверки скрипта не заменяют этот прогон.


## 5. Приёмка разделения профилей (пока не выполнена)

Только в отдельной учётной записи Windows и с **искусственными** данными, не с
рабочими паролями. Перед тестами сделайте независимую копию нужных данных. Тестовый
EXE и стабильная версия могут обращаться к одним и тем же внешним ресурсам:
**GameCenter.ini, AstrumPlay.ini, каталоги игры, работающие игровые окна, облачные
аккаунты и файлы пользователя не изолированы.** Используйте отдельные тестовые
каталоги, игровые клиенты и облачные аккаунты. Не подключайте рабочее облако и не
передавайте в отчёте контакты, ключи, токены или содержимое vault.

1. Запустите стабильную версию в тестовой Windows-учётной записи. Создайте уникальную
   тестовую карточку и контакт, убедитесь в сохранении после закрытия и перезапуска.
   Зафиксируйте только факт и путь профиля, не секреты; полностью закройте приложение.
2. Запустите тестовый EXE. Проверьте, что в заголовке и внутри программы видна надпись
   «ТЕСТОВАЯ СБОРКА», а проверка и установка обновлений недоступны. Убедитесь, что
   карточка стабильного профиля отсутствует и папки данных различаются.
3. Создайте в тестовой версии другие синтетические контакты и браузерные сессии,
   перезапустите её. Проверьте восстановление только тестовых данных и отдельные имена
   записей в Credential Manager, в том числе ключа cookie-bank и облачных токенов при
   использовании только тестового облака. Не экспортируйте их значения.
4. Проверьте раздельный автозапуск и уведомления. Сбросьте **только тестовый профиль**;
   вновь откройте стабильную версию и убедитесь, что её тестовые карточки, контакты,
   сессии и автозапуск не изменились. Затем проверьте обратное направление на новых
   синтетических данных. Не делайте сброс, если не уверены в открытом профиле.
5. Убедитесь, что заданные в среде `WEBVIEW2_USER_DATA_FOLDER` или
   `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` запрещают запуск тестовой сборки, а после
   удаления этих переменных она снова открывается. Проверьте также действующие политики
   WebView2 в Windows: сторонние политики или конфигурации могут переопределять профили.
6. Проверьте раздельные localStorage, cookie, импорт/экспорт, резервные копии и
   отключённый updater. Работа одноимённых записей в Credential Manager проверяется
   реальным чтением, записью и сбросом в обоих направлениях. Только после проверки с
   реальными Windows/WebView2 можно оценить готовность к использованию на одном ПК.

Скрипт фиксирует `profile: acceptance`, но `isolationVerified: false` намеренно: сборка
и статические тесты не доказывают разделение. Проект ещё не проверялся как одновременная
работа двух версий и не защищает от пользователя, который вручную выбрал рабочие пути
или аккаунты. Не создавать установщик через обход `--no-bundle`.

## 6. Явная тестовая сборка с общим рабочим профилем

По умолчанию скрипт, как и прежде, собирает изолированный вариант. Вариант ниже
**не изолирован**: он намеренно использует identifier, данные, настройки,
Credential Manager и браузерные профили основной версии. Любое сохранение, сброс,
миграция или облачная синхронизация могут изменить рабочие данные и другие устройства.
Сборка неподписана, не создаёт установщик и не включает updater. Одинаковая версия в
файле не является признаком стабильного релиза.

Перед первым запуском сначала проверьте этот сценарий в отдельной Windows-учётной записи
с искусственными данными. Для рабочих данных обязательно закройте основное приложение
полностью, включая трей, и подготовьте независимые резервные копии. Обычная копия
`state.json` не включает содержимое vault; отдельно создайте зашифрованный файл контактов
и сохраните ключ отдельно. Такая копия не сохраняет все сессии и OAuth-токены. Не
включайте автосинхронизацию и не проводите сброс во время первоначальной проверки.

Только когда вы осознанно хотите работать с общими данными, соберите из корня проекта:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\build-windows-local.ps1 -Profile Shared -SharedProfileConfirmed
```

Если исходники содержат проверенные вами локальные изменения, скрипту дополнительно
нужен `-AllowDirty`; в `BUILD-INFO.json` это будет помечено. Сборка не выполняет push,
не запускает GitHub Actions и не стартует приложение. Ищите `Tvinoferma-SHARED-TEST.exe`
в новой папке `local-acceptance/shared-…`; имя и баннер специально отличают её от
изолированной. Не заменяйте установленный EXE. При старте виден баннер «ОБЩИЙ ПРОФИЛЬ».

Tauri single-instance для одинакового identifier обычно поднимает уже запущенную версию
в той же пользовательской сессии, а не запускает вторую. Это не межпользовательская или
межпроцессная транзакция: не полагайтесь только на неё. Явно закройте другую версию и
не запускайте их одновременно. Изменение автозапуска из тестовой версии запрещено; её отдельные имена автозапуска
не затрагивают стабильные записи. Тестовая версия не переименовывает стабильный ярлык;
уведомления в ней отключены, чтобы не менять регистрацию стабильной версии.

Поведение этого нового варианта, включая доступ к прежним сессиям и реальному vault,
ещё нужно проверить на Windows. Пути WebView зависят от версии Tauri, среды и политик;
наличие всех старых сессий не гарантируется. Ни данные, ни сессии, ни доступ к облаку
не отправляйте в чат. См. также раздел о рисках отката версии и резервных копиях выше.

### Проверка на искусственных данных до работы с настоящими

1. В отдельной тестовой учётной записи Windows создайте в стабильной версии тестовую
   карточку и контакт, закройте её полностью. Запустите shared EXE и убедитесь, что
   он показывает тестовый баннер и те же карточки и контакты. Измените тестовую
   карточку, полностью закройте тест и проверьте изменение в стабильной версии.
2. С искусственными контактами и сессиями проверьте чтение и сохранение vault и
   WebView после перезапуска, без отправки значений в отчёт. Проверьте отключённые
   updater, уведомления и изменение автозапуска, неизменность ярлыка и стабильной
   настройки автозапуска.
3. Попробуйте запуск второго варианта, пока первый запущен, в обе стороны. Проверьте,
   что не появляется второй процесс с доступом к профилю; затем полностью закройте
   оба. Это проверка конкретной среды, не гарантия межпользовательской защиты.
4. Проверьте запрет переменных WebView2 из раздела 5 и используйте только тестовое
   облако и тестовые каталоги GameCenter. Если обнаружено несовпадение, сбой или
   недостающие данные, не переходите к рабочему профилю до выяснения причины.
