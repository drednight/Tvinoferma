# Синхронизация через личный облачный диск

## Текущий основной сценарий: самостоятельные полные файлы (31.10.2026)

Основной UI теперь использует `standaloneFileCodec.js`, `standaloneFileExchange.js` и
`standaloneFileRuntime.js`, а не `connectedPublication`, общий корень, очередь старой
истории или технический код сопряжения. Дальнейшие разделы о старой истории и мастере
ключей описывают **совместимость и восстановление**, не обязательные шаги нового режима.

- Вход Google / Яндекс → выбор одного или обоих дисков → одна кнопка сохранения,
  одинаковая для первого и последующих снимков. По умолчанию берутся текущие данные;
  можно выбрать совместимый полный `state.json`, без замены текущего приложения.
- Основной экран: подключение, выбор дисков и две кнопки «Сохранить на диск» / «Проверить».
  Источник `state.json`, приватные поля, запоминание ключа и старые копии находятся в
  закрытых параметрах. Старые окна отсутствуют в рабочем DOM и открываются только
  в Настройки → Данные → «Восстановить старый облачный набор».
  Верхний выбор Google/Яндекс управляет **только входом**. Направления сохранения
  выбираются отдельно и не меняются ни при входе, ни при фоновой проверке.
  Старое восстановление имеет свой независимый выбор провайдера.
- Обычное сохранение текущих публичных данных не открывает дополнительное подтверждение.
  Оно остаётся для непринятых облачных версий, сохранённого файла и приватной части;
  подтверждение полной замены местных данных также сохранено. Пустая ошибка пароля
  скрыта; неверная длина или несовпадение повторного ввода показываются текстом.
  Ошибки доступа выводятся фиксированными кодами отдельно для каждого диска,
  без сырых OAuth/transport-ошибок, токенов или подписанных ссылок.
- Файл содержит полные публичные данные и, только по отдельному выбору на конкретное
  действие, контакты/пароли. Для паролей нужны отдельное подтверждение риска и проверка
  источника контактов. Сессии сайтов, cookies, профили, пути, OAuth-привязки и настройки
  этого ПК не экспортируются. Частные поля никогда не становятся автоматической политикой.
- Фиксированный UUID коллекции отличает эти файлы от старых наборов. Он не является
  корневой версией, идентичностью, pin доверия или ссылкой на обязательного предка.
- В каждом конверте есть самостоятельно открываемая v2-капсула случайного ключа данных.
  При первом сохранении — **один диалог пароля с повтором**, минимум **8 символов**;
  при меньшей длине, включая пустой ввод, диалог явно сообщает об этом и остаётся открыт.
  После перезапуска без запоминания в ОС вводится прежний пароль одним полем для
  разблокировки существующего bundle; новый bundle/пароль молча не создаётся.
  Сохранена проверка хотя бы 6 различных символов и очевидных последовательностей;
  интерфейс сообщает и об этих условиях. Старые секреты открываются по прежним правилам.
  Существующие основные и запасные ключи не меняются и остаются в старом режиме.
- Внутренняя вторая случайная обёртка сохранена для совместимости формата v2, но её
  случайный секрет не сохраняется и **не выдаётся за пользовательскую резервную копию**.
  Пользователь должен сохранить свой пароль. Без него или явно запомненного ключа
  восстановление нового файла не обещается.
- По желанию запоминается только внутренний ключ в **отдельном пространстве хранилища
  ОС** `com.tvinoferma.desktop.cloud.simple-key/current`. В `state.json` — только
  публичные bundle/pin и зашифрованное намерение отправки; пароля/dataKey там нет.
  Запись, чтение после записи, удаление и фабричный сброс проверяются отдельными командами.
- На другом ПК: войти → проверить → скачать и сравнить → принять **полную** облачную
  копию с backup либо оставить местную. Сравнение ничего не применяет, не отправляет
  и не меняет принятую базу. При принятии повторно проверяются местное состояние,
  аккаунт и точные байты облачного файла. Backup и запись используют прежний guarded
  механизм с повторной сверкой диска, а не прямое присваивание/обычное сохранение.
- Если при полной замене удаляются персонажи с местными контактами, требуется отдельное
  подтверждение их резервирования: `state.json` не копирует Windows vault. Применение
  выбранных приватных полей также требует этого предупреждения и отдельного согласия.
- Отклонение запоминает точную версию/хеш на обоих дисках, не провоцирует автоматическую
  отправку местных данных. Следующая версия снова предлагается; ручная проверка видит
  и отклонённую. После принятия нет автоматической записи на второй диск.
- Байтово одинаковые конверты на двух дисках показываются одной копией с двумя местами.
  Различающиеся копии остаются отдельными, дата не выбирает победителя. При изменении
  обеих сторон относительно принятой базы показывается предупреждение.
- Прежние копии остаются на диске. Аутентифицированный список `supersedes` лишь помечает
  наблюдавшиеся копии как резервные: ни одну из них не нужно скачивать для открытия
  выбранного нового файла. Резервные копии можно показать отдельной галочкой ручной
  проверки. Циклические подсказки не скрывают все конкурирующие версии.
- У Google автоматически находится/создаётся видимая папка приложения; заранее выделенный
  ID сохраняется до POST, при неизвестном результате новый ID не генерируется. При
  нескольких папках пользователь выбирает явно. Старые dataset-привязки не меняются.
  Яндекс использует `app:/`. Ограничения Desktop/loopback/drive.file и безопасных native
  transport/host allowlist не ослабляются.
- Google Desktop JSON выбирается непосредственно в блоке входа Google, а не как
  файл данных для отправки. Web/service-account/Firebase JSON не принимаются;
  отображается конкретная фиксированная причина. UTF-8 BOM принимается, импортированные
  URL не используются. Идентичный повторный импорт ранее сохранённого клиента — без
  записи и без смены аккаунта даже при pending refresh. Другой client ID по-прежнему
  не заменяет существующую привязку.
- Сверка/продолжение показывают безопасный этап и HTTP-категорию отказа также в журнале:
  аккаунт, список, upload-link, download-link, содержимое. Ни исходные ошибки, ни ссылки,
  ни токены в журнал не попадают. Отсутствие файла отличается от невозможности его
  проверить; повторная отправка прежних байтов разрешена только после известного 404.
  В продолжении больше нет двойного одинакового запроса перед отправкой.
- Для каждого диска сохраняется отдельное зашифрованное намерение с фиксированным ID
  **до отправки**. HTTP-ответ сам по себе не означает успех: нужна точная сверка чтением.
  Проверка может завершить прежнюю квитанцию, но никогда сама не отправляет файл.
  Явное продолжение сначала сверяет результат, затем при подтверждённом отсутствии
  повторяет только те же байты с тем же ID/путём. Сбой Google не откатывает Яндекс.
- Проверки при запуске, после входа и каждые 5 минут не вызывают публикацию/применение.
  Фоновый просмотр может кэшировать лёгкие пины и проверенные архивные подсказки;
  ручная проверка, подготовка сохранения и принятие перечитывают байты.
  Это оптимизация, не доказательство свежести облака.
- Список нового пространства допускает до 4096 копий вместо старой границы истории
  128/129. Старые лимиты и проверки исторического протокола не расширены. Данные
  читаются по одному файлу, все полные базы не удерживаются в памяти как архив.

**Граница доверия и приёмка.** Pin из капсулы в новом сценарии — самосогласованность,
а не независимо полученное доказательство автора/корня. Доверие при первом открытии:
выбранный OAuth-аккаунт, пароль и явное принятие после сравнения. Это не доказательство
свежести, защиты от согласованного отката у провайдера или отсутствия скрытых файлов.
Синтетические тесты не удостоверяют реальные API, WebView2/Windows vault, обновление
OAuth и две физические машины. Неизвестный исход ротации Google refresh по-прежнему
ограничивается native credential CAS; старый токен не повторяется автоматически.
Нужна отдельная реальная приёмка авторизации/восстановления без очистки данных.


## Основной сценарий: полный файл, без автоматического объединения

Реализуется упрощённый режим по уточнённому требованию: **проверить/скачать → показать
различия → явно заменить местные данные** либо **отправить полный местный снимок**.
Это не завершённая приёмка настоящих сервисов: Google/Яндекс и два Windows-ПК ещё не испытаны.

- Основная панель — «Обмен полным файлом». При запуске выполняется только проверка.
  Проверка не назначает ID, не применяет файл, не обновляет принятую основу и не отправляет данные.
- Дата файла справочная; содержимое сравнивается по семантическому SHA-256. Порядок объявлений
  records не создаёт ложной правки, но порядок пользовательских списков учитывается.
- «Отправить на диск» сначала сохраняет местные данные и подготавливает недостающие sync-ID
  с backup. Затем показывает подтверждение полного снимка, включая удаления и порядок.
- Для версии, которую этот ПК ещё не принимал, отдельно предупреждается о замене облачных
  правок местным файлом. Если файл/местные данные/провайдер изменились после просмотра,
  прежнее подтверждение не применяется.
- «Заменить данные файлом с диска» — полная замена переносимых публичных записей и выбранных
  настроек. Отсутствие в этом **явно выбранном полном файле** удаляет местные записи, включая
  весь банк; это не вывод об удалении из неполного списка облака. Перед записью создаётся
  точная резервная копия местного состояния. Контакты/входы/пути другого ПК не импортируются.
- Последние принятые pin/hash сохраняются отдельно от местных правок и не обновляются обычным
  сохранением. После нового местного сохранения сравнение сбрасывается; автоматической отправки нет.
- Используется прежний AES-GCM-конверт v2 и новый вариант содержимого **history v5** — полный
  снимок. Для явного выбора среди конкурирующих файлов используется **history v6**:
  выбранный файл — источник полного содержимого, остальные проверенные heads перечислены
  по pin как заменённые, но остаются резервными файлами. Это не слияние записей.
  Проверяются все ссылки/отпечатки, отсутствие циклов, дубликатов и ссылок на предков
  вместо независимых heads. Пропуск любого файла, на который ссылается выбор, блокирует чтение.
  Старые клиенты, не понимающие этот формат, должны остановиться;
  **обновите все ПК**. Старый консервативный merge не продолжает файловую линию.
- Технически новый актуальный файл загружается отдельной неизменяемой версией, а предыдущие
  файлы остаются резервными. Выбор актуального файла определяется проверенными ссылками,
  не временем. Fixed-name перезапись не используется; отдельная подтверждаемая очистка после history v8 описана ниже.
- До загрузки шифртекст и заранее выделенный Google ID сохраняются в локальной отметке
  `settings.cloudSnapshotFiles`. Ключ и открытый публичный снимок в эту отметку не входят.
  Перед сетевым вызовом фиксируется attempting. После неизвестного результата — только
  точная сверка старых байтов, без автоматического повтора загрузки; новые местные правки
  при сверке сохраняются. Подготовленный до вызова файл может продолжить отправку после проверки.
- Если подготовка устарела, «Отменить подготовку / снять ожидание» позволяет отменить только
  местный prepared-файл без сети. Перед очисткой — точная резервная копия. Текущие данные,
  принятая база и облако не меняются; новая отправка выполняется отдельно, после нового сравнения.
- Для attempting это **не отмена облачного запроса**. Нужны отдельные согласия с тем, что
  результат неизвестен и прежний файл ещё может появиться. В local state v2 остаётся
  `unsettled`: pin/parent/fileId/hash без ключа и открытых данных (не более 32 записей).
  Старые зашифрованные байты остаются в backup. Новая отправка не повторяет старую попытку.
  Если файл появился, его pin проверяется. Метка снимается только при принятии файла, чья
  проверенная история покрывает эту попытку. Отсутствие в списке не объявляется доказательством
  неуспеха. Автоматической очистки неизвестных меток по сроку нет.
- При нескольких heads сначала показывается список дат/ID **без выбранного победителя**.
  Выбор для просмотра только скачивает/сравнивает. Можно отдельно заменить местные данные,
  не изменяя облако, либо назначить выбранный облачный файл актуальным на диске, не меняя
  местные данные. Также можно отправить полный текущий местный файл вместо всех показанных
  вариантов. Последние два действия требуют отдельного подтверждения выбора итогового файла.
  Не выбранные публичные/приватные поля не подмешиваются. Приватная часть выбранного файла
  сохраняется лишь с прежним отдельным согласием.
- Список heads повторно проверяется перед публикацией; новый файл или изменившийся pin
  отменяет прежний выбор. Глобального CAS двух ПК нет: если конкурент появился уже во время
  загрузки, оба файла сохраняются. Подтверждённая отправка завершает pending, но UI отдельно
  сообщает о конкуренции либо о следующей версии, не объявляя отправленный файл победителем.
- Старые queued/prepared/private намерения не выбрасываются при переходе. Сначала их нужно
  завершить в свёрнутом прежнем режиме. Его автоотправка в новом интерфейсе отключена.
  После начала перехода старые действия блокируются для этого провайдера.
- Новые местные пароли и контакты **автоматически не выгружаются**. В отдельном свёрнутом
  блоке «Пароли и контакты · отдельный ручной перенос» категории email/запасная почта/телефон/
  пароль выключены по умолчанию. Нужны подтверждение полноты источника и отдельное согласие
  на риск пароля. После сохранения и подготовки ID выбираются конкретные пары персонаж/поле;
  есть «Выбрать все»/«Снять все». Список показывает только наличие/различие и явные очистки,
  не значения. Перед отправкой подтверждается **полный публичный местный файл плюс выбранные
  поля**. Остальная прежняя облачная приватная часть сохраняется с отдельным согласием;
  не выбранные новые местные значения в неё не добавляются. Все обладатели ключа набора
  смогут расшифровать выбранные контакты. Cookies, статусы входов и местные пути не переносятся.
- Входящий ручной перенос тоже требует выбора конкретных полей, подтверждения источника,
  риска пароля и независимой копии прежних контактов. Автокопия state.json **не копирует
  Windows vault**. Применяются только контакты существующих местных sync-ID; сначала можно
  явно применить публичный файл. Приватное применение не принимает публичные изменения и
  **не меняет принятые pin/hash**. Если файловой отметки ещё нет, создаётся пустая отметка
  с непринятой базой. Категории/разрешения не сохраняются; просмотр сбрасывается при смене
  категорий, диска, сохранении или применении. При конкурирующих heads сначала нужно выбрать
  итоговый полный файл в основной панели, а не молча выбирать источник паролей.
- Перед подготовкой/отправкой и чтением/применением проверяется источник: заблокированный/
  непрочитанный vault не считается набором пустых полей. Активный vault перечитывается без
  записи; несовпадение с известными raw-данными блокирует операцию. Несохранённая местная
  правка не объявляется внешним конфликтом vault. Межпроцессной атомарности этот контроль
  не создаёт. Подготовленные приватные значения остаются в памяти внутренних capabilities;
  новая панель, cloud-журнал и pending не получают их. При выключенном vault обычный местный state
  и резервные копии всё ещё могут содержать открытые контакты — это не защищённый экспорт.
- Уже одобренная приватная партия входит в шифртекст pending. Продолжение отправки не читает
  новые местные контакты и не пересобирает партию; снятие галочек не удаляет уже подготовленные
  байты. Для отмены используйте основной блок ожидания; attempting нельзя отозвать этой кнопкой.
- Если в полном местном файле удалён персонаж с облачными контактами, требуется отдельное
  подтверждение пропуска его приватной записи. **History v7** содержит точные `privatePrunedIds`
  и `replacedHeads` (возможно пустой): удалить можно только приватные записи персонажей,
  отсутствующих в новом публичном файле. Остальные ранее переданные поля обязаны оставаться.
  Старые облачные версии и местные backup всё ещё содержат прежние секреты; это **не удаление
  с диска навсегда**. Обновите все ПК до понимающей v7 версии. Для существующего персонажа
  очистка поля передаётся только как явно выбранная пустая строка, не отсутствующее поле.

**Оставшиеся ограничения:** настоящие API/два Windows-ПК не испытаны. Снятие неизвестного
ожидания не отзывает запрос
провайдера и не гарантирует, что он не создаст поздний файл. При новых неизвестных heads
нужен новый явный выбор, автоматического last-write-wins нет.
Лимит активной истории — 128 версий/64 MiB; сокращение выполняется только через проверенный архив и history v8, не удалением родителей вручную. Отметка в state
не является межпроцессным CAS, транзакцией с vault или гарантией fsync. Копия state при vault
может содержать только ссылки на контакты. Настоящие API и аварийное питание не проверены.

### Контрольный файл history v8, явная корзина и местное восстановление

1. Примите нужную единственную облачную версию. Остановите остальные ПК и обновите их
   перед следующим запуском. Сохраните ключ/пароль отдельно. Подготовьте архив выше,
   сохраните и **выберите сохранённый файл для криптографической сверки**.
2. «Создать контрольный полный файл» копирует именно принятую облачную публичную и
   приватную часть, не текущие местные правки. Для старых контактов нужно отдельное
   согласие. AES-GCM-аутентифицированное содержимое v8 родительствует доверенному корню
   и содержит source pin, накопленные retiredPins (не более 4096), типизированный реестр
   исторических UUID и SHA-256 предшествующего архива. Это явное доверенное заявление
   об отсечении истории, не доказательство наличия удалённых ciphertext. Старый клиент
   обязан отказать на неизвестном формате; root и контрольный файл остаются на диске.
3. Используется прежний durable pending: checkpointSource отдельно от физического
   parent=root; перед отправкой повторно проверяется прежняя голова и местный hash.
   Prepared/attempting, Google ID, перечитывание и восстановление ожидания после restart
   работают без повторной неизвестной отправки. До подтверждения новой версии ничего
   не удаляется. Незавершённые/unsettled и legacy-очередь блокируют сокращение.
4. Снова выберите сохранённый **предшествующий** архив в поле очистки/восстановления.
   Проверяются ключ, native root/key pin, digest, точные pin реально присутствующих
   кандидатов и единственная принятая контрольная голова. Другая версия, новое местное
   состояние или появление новых файлов останавливают действие. Корень/контрольный файл
   не входят в кандидаты. Неизвестная поздняя голова никогда не удаляется и не скрывается.
5. Отдельно подтвердите «Переместить старые файлы в корзину». Для КАЖДОГО запроса журнал
   attempting сохраняется **до сети**; список/даты сверяются заново, содержимое кандидата
   перечитывается. Native проверяет канонический SHA-256 и scope: Google — ID, папка,
   appProperties, имя, checksum и обязательный ETag/If-Match; Яндекс — только построенный
   app:/ путь набора, имя/type/checksum и `permanently=false`. Произвольного URL и
   постоянного удаления нет. При отсутствии SHA/ETag native отказывает, не ослабляя проверку.
   После исчезновения кандидата перечитываются и сверяются оба оставляемых anchor pin.
6. HTTP 200/202/204 не объявляется успехом. Неизвестный запрос — verify-only, без
   автоматического повтора. После перезапуска снова выберите архив и проверьте очистку:
   исчезнувший файл подтверждается; присутствующий остаётся неизвестным. Отдельное
   снятие ожидания **не отменяет запрос**; архивные байты остаются в backup. Снятие
   ожидания очистки не создаёт upload receipt и не отправляет старый файл заново.
7. Публичное/приватное восстановление архива не требует сетевого чтения облака, но
   требует существующей доверенной native-привязки и ключа. Архив проверяется независимо
   от собственного checksum. Выберите конкретную фактически содержащуюся версию,
   покажите изменения и явно подтвердите полную местную замену, включая удаления.
   До записи — точная местная резервная копия; принятые pin/hash и облако **не меняются**:
   восстановленное содержимое считается местной правкой до отдельной ручной отправки.
   Контакты по умолчанию не выбраны, значения не показываются. Для них — категории,
   конкретные пары, согласие с риском паролей, отдельный backup контактов/vault и
   проверка свежего местного vault. Несохранённый state/подмена файла блокируют применение.

Активный бюджет остаётся **128/64 MiB**. Для промежуточного root+старые файлы+checkpoint
читатели допускают максимум **129 файлов / 96 MiB + 256 KiB**; archive добавляет ещё
256 KiB метаданных. Обычная 129-версионная история без проверенного retirement отвергается;
это не увеличение активного лимита. Копии типизированных UUID и точные старые pin остаются
проверяемыми после удаления старых ciphertext, но недоступный снимок не выдумывается.
Следующая обычная полная версия может продолжить линию нового checkpoint.

**Границы гарантии:** атомарного общего CAS нет, особенно у Яндекса. Остановка остальных
ПК и отсутствие ручных изменений папки — обязательные условия, а не программная блокировка.
Если старый клиент поздно отправил ребёнка удалённого родителя, проверка останавливается;
архив сохраняйте для восстановления. Автоматическое возвращение недостающих родителей
из архива на диск/объединение поздней ветки не реализовано: местное восстановление архивной
версии не выдаётся за ремонт облачной DAG. Очистка корзины, fsync/аварийное питание,
настоящие API, два Windows-ПК и desktop-релиз требуют отдельной приёмки.

### Архив истории: формат и исходная read-only подготовка

В разделе полного файла показываются число версий и запас до 128, объём проверяемого
шифртекста до 64 MiB. При 96 версиях или 48 MiB выводится предупреждение. Это запас по
числу файлов, не обещание такого же числа успешных отправок: ограничение объёма независимо.
Лимиты активной истории не повышены; отдельный ограниченный физический overlap для v8 описан ниже.

Отдельный свёрнутый блок сохраняет `.tf-history.json`: точные зашифрованные конверты всей
проверенной истории, код сверки, провайдер, дата и SHA-256 канонического содержимого. Нет
открытых персонажей/контактов, dataKey, OAuth-токенов, аккаунта, местных путей или Windows
vault. В ciphertext старых версий могут остаться уже переданные секреты. Для расшифровки
нужен отдельно сохранённый основной пароль/запасной ключ. Код из самого файла не является
независимым доказательством доверия. Архив не заменяет местные резервные копии.

Сначала подготовка сверяет облачный список повторным чтением и проверяет AES-GCM/HMAC,
доверенный корень, прежние известные pin и всю историю. Несколько голов архивируются
вместе, без выбора победителя. Незавершённые, неизвестные и прежние queued/private намерения
блокируют подготовку: они не должны молча исчезать из «полной» копии. Скачивание требует
отдельного согласия; оно **не доказывает запись файла**. Затем пользователь выбирает
сохранённый файл: ограничение размера проверяется до чтения, checksum не заменяет полную
криптографическую проверку относительно текущей доверенной привязки и всех подготовленных
pin. Состав облака проверяется снова. Изменившийся набор, файл, привязка, провайдер или
местное состояние не получают успешного подтверждения. Форматирование JSON может отличаться,
но зашифрованные конверты и смысловые метаданные должны совпадать с подготовкой.

Эти действия не меняют публичные данные, принятую основу, outbox или облачные файлы.
Открытие сессии может штатно обновить OAuth. Подготовка хранится только в памяти;
смена диска/сохранение сбрасывает просмотр. Выбор другого файла снимает прежний статус
успешной сверки. Журнал содержит только фиксированный код результата, не файл/код сверки.

Сам архив не разрешает удаление. В history v5/v6/v7 без контрольного заявления все
старые версии нужны для проверки связей. После v8 активные и выведенные из истории файлы
считаются отдельно; для корзины требуется самостоятельная проверка и подтверждение по
процедуре выше. Сверка файла не доказывает fsync или сохранность носителя.

Контроль блока архива: 203 модельные/UI/смежные проверки и 76 fake Google/Yandex
сценариев (62 прежних файловых/приватных + 14 архивных), включая конкурирующие головы,
изменившийся инвентарь, подмену файла, внешнюю запись state, pending/unsettled и отсутствие
изменений данных/очереди/облака. Линтер, типы, формат и сборка прошли; полный JS-набор
выполняется в PR CI. Предпросмотр web не включает native-операции. Это не приёмка API.

## Справка о предыдущем экспериментальном режиме

Ниже сохранены описания прежних протоколов, ограниченного merge и истории работ.
Их незавершённые универсальные объединения не являются планом основного файлового сценария.

**Состояние:** полная синхронизация ещё не работает. В настоящих настройках доступны разовая
диагностика OAuth и отдельное **экспериментальное сохранение доступа** после согласия и сверки
аккаунта. Экспериментально подключены локальная подготовка нового набора, однократная ручная
отправка первого снимка, восстановление по независимому коду, предварительное сравнение и
выборочное применение. На ПК, создавшем и подтвердившем первый снимок, экспериментально
добавлены ручная и отдельно включаемая автоматическая отправка последующих сохранений через
зашифрованную очередь. Восстановленный ПК может продолжить отправку после согласования
основы: полного совпадения или поддерживаемого трёхстороннего объединения относительно
подтверждённой основы. Это **не полноценная
двусторонняя синхронизация**: при несогласованном выборочном применении, расхождении ветвей,
неподтверждённых удалениях и неразрешённых конфликтах публикация блокируется. Конфликты поддерживаемых полей
можно явно выбрать по записи. Для ручных записей календаря добавлен отдельный протокол
подтверждения удаления; остальные удаления ещё не реализованы. Добавлена отдельная ручная передача контактов по категориям, не автоматическая выгрузка секретов. Реальные OAuth-серверы, облачные API и
собранный Tauri/Windows ещё не испытаны; сохранение доступа или fake IPC-тесты не означают
готовую синхронизацию. В `demo/cloud-sync/` находится только изолированный макет с вымышленным
облаком: он не подключается к сервисам и не переносит данные между настоящими компьютерами.

В полном демо раздел «Синхронизация между ПК» свёрнут при загрузке. Выбор диска, кнопки,
сравнение, частичное обновление и подтверждение удаления работают только на вымышленных
примерах. После проверки макет отдельно показывает вымышленную дату изменения файла на
выбранном диске, примерное время с момента изменения, время проверки и локального сохранения
на момент сравнения. Смена диска и условная отправка сбрасывают старое сравнение. Пример
отправки создаёт условную отдельную исходящую версию, не меняя дату входящего файла; время
локальной копии в уже показанном сравнении не меняется задним числом при частичном обновлении.
Условные отправка и обновление отражаются в отдельном источнике общего журнала копии приложения;
он хранится в памяти вкладки и не пишет в реальные журналы. Автоматические действия,
подключение учётных записей, шифрование и резервное копирование в макете не работают.
Внутри выбора диска доступен пример окна сверки аккаунта: он показывает только постоянные
вымышленные email или логин и никого не подключает.

## Экспериментальная проверка и применение

В `Настройки → Синхронизация` свёрнутый блок предлагает подготовить отсутствующие sync-ID
после явного согласия и резервной копии локального состояния. Проверка не создаёт набор и не
заключает, что старого облака нет. При уже существующей локальной привязке `checkConnectedCloud.js`
сверяет запись аккаунта, ключ, журнал и pin, затем читает и проверяет зашифрованную историю.
При запуске настольного приложения проверяются оба диска; вручную сравнивается выбранный диск и
конкретная версия, не «самая новая» по времени. Дата файла, время проверки и время подтверждённого
локального сохранения показываются отдельно с местным часовым поясом; неизвестное время не
выдумывается.

В `cloudReviewPanel.js` можно выбрать целые публичные записи или доступные группы настроек,
посмотреть поля и подтвердить применение с backup; локальные пароли, контакты, входы и пути не
переносятся. Отсутствие записи не является удалением. Если в проверенной линии уже есть явная
метка удаления записи календаря, она показывается отдельно. Для нового протокола v3 доступен
явный выбор удаления ручной записи с предупреждением о потере местных правок и backup.
Метки старого экспериментального v2 доступны только для просмотра. Большие детали и записи сверх первых 1000
пока недоступны для выбора. `applyPublicSnapshot.js` проверяет зависимости, локальные ID и
повторную нормализацию; неоднозначности и вложенные удаления блокируются. Резервная копия state
не обязательно включает отдельное хранилище контактов Windows или входы GameCenter.

`pendingSelectiveApply.js` записывает вместе с изменениями локальную отметку источника без значений.
Это не полноценный учёт происхождения и не защита от отката. `requireResolvedSelectiveApply()`
блокирует отправку. Отметку можно снять только после явного подтверждения полного совпадения
с единственной наблюдаемой головой и проверки, что все частично принятые источники и ранее
подтверждённые локальные версии входят в её линию. Неподтверждённые исходящие версии не
удаляются и блокируют согласование; для расходящихся ветвей общего решения нет.
Применение облачных изменений и публикация дополнительно координируются в одном JS-контексте,
но не в других процессах. Существующие guarded-проверки памяти, файла
и backup действуют только для участвующих операций одного JS-контекста: они не являются
межпроцессным CAS, транзакцией с vault, гарантией fsync или защитой от согласованного отката.
Повреждённый либо повторный sync-ID молча не заменяется. Потерянный ответ записи блокирует
дальнейшее сохранение до проверки и перезапуска.

### Сохранение местной правки при подтверждённом удалении задачи

В **«Объединить все поддерживаемые изменения»** конфликт облачного удаления ручной
задачи теперь допускает два явных решения: принять удаление либо отдельно отметить
**«Сохранить местную версию как новую задачу»**. Во втором случае старый sync-ID остаётся
удалённым, а точные публичные поля местной задачи, включая повтор и отметки по датам,
переходят в новую задачу с новым sync-ID. Это создание новой сущности, не отмена облачной
метки и не воскрешение старого ID. Без обоих вариантов согласование останавливается.
Обычное выборочное «Применить выбранное» само копии не создаёт.

Копия никогда не выбирается автоматически или кнопкой «Выбрать все». Выбор удаления
и новой копии взаимоисключающий; перед записью показано дополнительное подтверждение.
Новый ID проверяется на совпадение со всеми известными ID публичных снимков и метками
удалений. Отсутствие записи без подтверждённой метки, клановые события, неподдерживаемые
изменения связей, расходящиеся ветви и неотправленные секретные партии не обходятся.

До изменения очереди сохраняется backup и **v5 отметки незавершённого объединения**:
точные исходный/целевой pin, выбор и новый ID, хеши исходного и подготовленного снимков,
а также при необходимости отдельное подтверждение ciphertext-carry и хеш прежнего
выборочного применения. В отметке нет полей задачи или секретов. После прерывания
используется тот же ID, новый не выделяется; изменение решения или устаревший просмотр
не применяются. Старые v1–v4 отметки не получают новую семантику: копии допустимы только
в v5. **Обновите все ПК:** старая сборка должна остановиться на незнакомой отметке.
Форматы облачной истории v3/v4 и шифрованного конверта не меняются.

Старая неотправленная/подготовленная версия остаётся в зашифрованных retained intents до
проверенной отправки нового потомка. Потомок содержит прежнюю метку удаления и новый ID.
Независимые правки и местные контакты сохраняются; копирование задачи не разрешает
передачу нового местного пароля. Даты не определяют победителя.

Автотесты: модель и v5-кодек (`cloudPlannerCopyMerge.test.js`, `cloudPlannerCopyMarker.test.js`),
отдельный UI-выбор и защита подтверждения (`cloudReviewPanel.ui.test.js`), 20 сквозных
сценариев fake IPC/Google/Yandex, включая queued/prepared, потерю ответа CAS и перезапуск,
входящую секретную партию и ранее применённое удаление другой задачи. Это **имитация**
дисков, не проверка настоящих API или двух реальных Windows-ПК.
Локальная общая регрессия: **4986 passed, 1 skipped**, 253 файла; `lint`, `typecheck`,
`format:check`, `build`, `git diff --check` прошли. Браузерный smoke с подставным ответом
проверил явный выбор новой копии и отсутствие автоматического удаления; page errors — 0,
axe WCAG-проверка блока конфликтов — 0 нарушений. Это не браузерная проверка всего приложения
или работающего аккаунта.

### Архив пати: согласование связанных данных

Поддержан проверяемый перенос существующей пати между активным списком и архивом.
Он сохраняет sync-ID пати и персонажей; **это не удаление сущности**. Перед объединением
проверяются точные последствия штатного `archiveParty`/`restoreParty`: состав активных
и архивных персонажей, сохранённые `memberLinks`, `isMain`, порядок участника и выбор
основной пати после переноса. Потеря ссылки, роли, порядка или постороннего ключа не
принимается за обычную правку. Пати сохраняются по `order` уже до записи, как после
перезапуска: это не меняет подтверждённый локальный снимок при восстановлении checkpoint.

Независимые заметки, характеристики и имя пати объединяются отдельно. Если другая сторона
одновременно изменила поддерживаемые связи затронутого состава, показывается отдельный
конфликт **связанной группы пати**. Галочка пати берёт с диска всю группу: статус архива,
сохранённый состав, основную пати и порядок у затронутых персонажей. Без галочки остаётся
местная группа. Это может отменить архивирование/восстановление с другой стороны; перед
записью об этом есть предупреждение. Выбирать роли участников независимо от статуса
пати нельзя — иначе возникла бы комбинация, которой не было ни на одном ПК.

Операция проходит прежние проверки pin, сохранённого состояния, backup, checkpoint и
зашифрованной очереди. Незагруженное queued/prepared намерение сохраняется до проверенной
отправки объединённого потомка. Форматы истории, конверта и локальных отметок не меняются;
старая сборка остановится на неподдерживаемом переносе, поэтому **обновите все ПК**.
Отдельное согласие на удаление задачи или ciphertext-carry не выводится из выбора пати.
Местные контакты и путь запуска не заменяются.

Ограничения: одновременно переносимые пати с пересекающимся составом, новый персонаж,
связанный с переносимой пати, произвольное исчезновение связи вне проверенного переноса
и настоящее удаление пати остаются блокирующими. Непересекающиеся переносы допустимы.
Это не журнал всех операций над членством и не общая поддержка конфликтов любых связей.

Автопроверки блока: модель связанного переноса, штатная сортировка/rollback архива,
предупреждение выбора в UI и 40 сквозных fake IPC/Google/Yandex сценариев. В них проверены
оба направления и стороны, активные/архивные участники, queued/prepared, потеря ответа
CAS, перезапуск, private carry и выбор связанной группы. Это не реальные облачные API
или испытания двух Windows-ПК.
Полная локальная регрессия: **5055 passed, 1 skipped**, 254 файла; `lint`, `typecheck`,
`format:check`, `build` и `git diff --check` прошли. Предпросмотр проверен с разрешённым
конкретным host среды, без расширения доступа к dev-серверу для произвольных доменов.

### Подтверждённые удаления ручных записей календаря

Кнопка **«Проверить удаления календаря»** сравнивает уже сохранённый state с проверенной
родительской версией в локальной очереди. Она показывает полный список исчезнувших ручных
записей. Только после отдельного подтверждения сохраняется зашифрованный потомок с явными
метками удаления. Проверка и подтверждение не отправляют данные; обычная ручная или
разрешённая автоотправка затем заново проверяет облачную голову. Если другой ПК успел
опубликовать правку, отправка останавливается. Удаления других сущностей и клановых событий,
незавершённые retained intents и начатая неопределённая отправка не разрешают это подтверждение.

Содержимое истории **v3** хранит и новые удаления, и полный накопленный набор меток во всех
последующих версиях. Отсутствие записи без метки, исчезновение старой метки, повторное появление
удалённого sync-ID или переход обратно на старый формат блокируются. Старый экспериментальный
формат содержимого v2 остаётся только для просмотра. Это не версия шифрованного envelope или очереди.
**Перед использованием обновите все ПК**: старые сборки не понимают v3 и остановятся.

На принимающем ПК v3-метка показывается отдельно с текущими местными полями. По умолчанию она
не выбрана. Пользователь может сохранить местную запись, не выбирая удаление, либо явно выбрать
удаление **вместе с местными правками**. Применение требует отдельного подтверждения, создаёт
backup и использует guarded запись. Неоднозначные ветви, чужие типы и клановые записи блокируются.
При объединении подтверждённое облачное удаление каждой ещё существующей местной ручной записи
показывается как отдельный конфликт, даже если её поля не менялись. Галочка означает явное
принятие удаления вместе с местными правками. Без галочки запись сохраняется на ПК, но
согласование останавливается: старый sync-ID не воскрешается в потомке облачной версии.
Независимые поля других записей сохраняются. Одна неотправленная запись очереди в фазе
`queued` или `prepared` удерживается зашифрованной до проверки нового объединённого потомка.

После уже выполненного выборочного удаления доступно узкое согласование с прежней очередью:
все отметки применения должны относиться к той же выбранной v3-версии и только к подтверждённым
удалениям ручного календаря. Сохранённый публичный снимок обязан точно совпасть с прежним
зашифрованным намерением за вычетом выбранных удалений. Дополнительные правки после применения,
другие источники, изменения настроек и смешанные операции пока блокируют этот путь.
Перед переносом основы сохраняется отметка операции **v3** с хешем прежнего намерения;
после потери ответа CAS можно продолжить с тем же retained снимком. Обе локальные отметки
снимаются только после проверенного сохранения результата. При полном совпадении данных кнопка
объединения остаётся доступной для такого согласования; обычное принятие точной основы не
выбрасывает ожидающую очередь. Это не универсальное снятие отметок частичного применения.
Метки не очищаются по возрасту. Реальные Windows/облака и crash-durability не подтверждены.

### Ограниченное объединение и добавление записей

Кнопка «Объединить все поддерживаемые изменения» — отдельное явно подтверждаемое действие,
**не учитывающее галочки выборочного применения**. Она доступна после просмотра различий
единственной наблюдаемой головы. Для последнего подтверждённого локального pin и каждого
перехода до выбранной версии проверяются линия и отпечатки, затем выполняется трёхстороннее
сравнение общей базы, сохранённого состояния и облака. Независимые поля существующих персонажей,
пати, марафонов, календаря и финансов и выбранные группы настроек могут объединяться; контакты,
пути и `lastSync` остаются локальными. Поддерживаются также некоторые добавления записей в
конец сохранённого порядка, в том числе разные добавления на обоих ПК: сначала сохраняется
локальный, затем облачный порядок новых записей. При противоречивом порядке общих добавлений
или вставке в середину операция блокируется. Изменения полей существующих элементов массива,
например прогресса сайта, возможны без исчезновения элементов. Для объектов без уникального
якоря требуется полное совпадение, иначе операция блокируется. Новые записи истории монет и
характеристик могут добавляться сверху, если все прежние записи сохранились; обрезание истории
характеристик при встроенном лимите 10 пока блокирует объединение. Задания, награды и бонусы
марафона объединяются по собственным sync-ID; прочие массивы считаются одним полем,
а несовместимые одновременные изменения остаются конфликтом. Новый шаблон и связанный с ним
марафон можно добавить с локальными идентификаторами. В существующем шаблоне можно изменять,
добавлять, убирать и переставлять задания, награды и бонусы: это **копируемые значения**, а не
sync-сущности исходного марафона. Списки `tasks` и `bonuses` объединяются как два отдельных целых
поля, не по названию, индексу или похожести наград. Разные изменения одного списка на двух ПК
требуют выбора стороны, даже если затронуты разные задания. Независимое название, другой список
и правки других записей сохраняются. Локальные ID остаются только у точного неизменённого
префикса; после первого отличия весь суффикс получает новые местные ID. Уже созданные марафоны,
их задания, ссылки, отметки и прогресс от изменения шаблона **не меняются**.

Также согласуются очистка/замена тегов персонажа, снятие отдельной отметки повтора календаря
и порядок/показ разделов в отдельно выбранной группе навигации. Удаление отметки против её
местной правки — конфликт, а не автоматическая победа удаления. Теги и списки навигации
сравниваются целиком; запрещённое скрытие настроек, сдвиг закреплённых разделов и некорректные
значения останавливают материализацию до записи.

Для истории характеристик допускается ограниченный сдвиг при штатном лимите приложения 10:
новые записи стоят сверху, в конце остаётся однозначный точный префикс старой истории, выпадает
только её хвост. Даты не используются ни для сопоставления, ни для выбора победителя. Полная
очистка, произвольное обрезание, правка старой записи, повторяющиеся неоднозначные якоря или
полная замена без общей части блокируются. Разные новые истории на двух ПК — конфликт целого
списка; старые значения остаются в независимой резервной копии и прежних зашифрованных версиях.
Это ограничение не снимается для истории монет.

Перенос **персонажа** между активным списком и архивом больше не считается удалением
или произвольной перестановкой. Сохраняются тот же sync-ID, порядок оставшихся в каждой
группе и все известные ссылки; перемещённые и новые персонажи добавляются в конец.
Архивирование/восстановление согласуется с независимыми правками с другого ПК, включая
обычное разрешение конфликта поля. При одновременно созданном sync-ID с разным архивным
состоянием нужен отдельный выбор, как для остальных различающихся новых записей.
Противоречащие друг другу порядки добавленных/перенесённых записей не угадываются:
объединение останавливается до записи. Это не разрешение настоящего удаления персонажа
или произвольной сортировки списков.
Для пати действуют отдельные проверки связанного переноса, описанные выше.
Форматы шифрования/истории не расширяются: сущность не исчезает, метка удаления не нужна.

Автопроверка этого блока: `tests/cloudArchiveMerge.test.js` проверяет 256 сочетаний
архивного состояния четырёх персонажей на двух сторонах, независимые правки, выбор
конфликтов, добавление персонажа, отдельное подтверждение удаления правившейся задачи
и материализацию без потери местных секретов. В `tests/cloudInitialSetup.integration.test.js`
добавлены 16 сквозных сценариев через fake IPC и **имитацию** Google/Яндекс: обе стороны
и оба направления переноса, backup, ссылки пати/марафона, зашифрованная очередь и
последующая отправка, в том числе с ранее согласованным приватным разделом. Новый
местный пароль не заменяет ранее согласованный секрет в облаке без нового согласия.
Это не испытания настоящего API или двух реальных Windows-ПК.
Локальная общая регрессия после изменения: **4934 passed, 1 skipped**, 251 файл;
`lint`, `typecheck`, `format:check`, `build` и `git diff --check` прошли.

Поддержки перестановок прежних sync-ID, исчезновения прочих полей/элементов массивов,
удалений сущностей вне подтверждённого ручного календаря и расходящихся ветвей пока нет.
Все ПК следует обновить: старая сборка может остановиться на новом поддерживаемом изменении.
Даты не выбирают победителя.

При конфликте поля сначала показывается список конфликтов и сравнение значений. Пользователь
может выбрать облачную сторону для отмеченных записей, настройки или финансов; для неотмеченных
конфликтующих полей сохраняется локальная сторона. Все конфликты внутри одной записи получают
один выбор; остальные поддерживаемые изменения объединяются независимо от галочек. При конфликте
массива без отдельных ID выбирается весь массив, поэтому изменения другой стороны внутри него
могут быть потеряны. Выбор не применяется без отдельного подтверждения. Он привязан хешем к конкретной базе, голове,
сохранённому снимку, ревизии очереди и списку конфликтов: если что-то изменилось, требуется
новая проверка. В отметке незавершённой операции v2 сохраняются только выбор и отпечатки,
без значений записей; после прерывания продолжается первоначальный выбор. Противоречивый
порядок общих добавлений таким способом не разрешается. Повторный экспорт, ссылки и нормализация проверяются до записи.
Это намеренно консервативное ограничение, а не гарантия пригодности всех данных.

Перед изменением очереди `reconcileConservativeMerge.js` сохраняет с резервной копией отметку
операции в state: provider, пины, выбранные группы настроек и хеши исходного и объединённого
снимка, без значений записей. Отметка блокирует публикацию и выборочное применение. Если ответ
CAS потерялся, после проверки и перезапуска доступно продолжение с теми же данными и пинами;
до изменения очереди можно безопасно отменить операцию. После переноса основы отмена запрещена.
Если локальные данные или облачная ветвь существенно изменились, автоматическое продолжение
может остановиться: не удаляйте отметку вручную, сохраните копии и проверьте историю. Если при
повторном чтении появилась единственная более поздняя **дочерняя** версия, завершается только
уже подтверждённое объединение прежней версии; перед отправкой требуется новая проверка.

Одна совпадающая с текущим сохранением запись очереди в фазе `queued` или `prepared` может
переноситься вместе с основой: локальная зашифрованная очередь v5 хранит исходный шифротекст
и адрес до точного подтверждения нового объединённого потомка. При последовательных объединениях
сохраняются до 16 таких намерений; если достигнут предел, операция блокируется. Даже при полном
совпадении результата ставится отдельный зашифрованный потомок, чтобы подтвердить завершение.
Потерянный ответ создания не повторяется; `attempting`, несколько активных попыток и устаревший
относительно state снимок не переносятся, кроме описанной выше строго проверенной проекции выборочного удаления. После проверки нового файла и записи подтверждения
старые намерения удаляются из очереди тем же CAS; облачные файлы не удаляются. Старая сборка
не понимает отметку и v5 — **обновите все ПК до эксперимента**. Само объединение не отправляет
файл, но отдельно включённая автоотправка может начаться после сохранения.

Компоненты проверялись на синтетических данных, fake IPC и browser localStorage. Это **не**
доказательство работоспособности настоящего облака, сборки Tauri, Windows vault, гонок других
процессов или восстановления после падения. Не следует подключать к эксперименту единственную
копию ценных данных. Email, телефон, recovery и пароли доступны только через отдельную ручную передачу ниже; автоматическая выгрузка местных секретов не включается.

## Ручная передача контактов и паролей · экспериментально

В свёрнутом блоке синхронизации есть отдельная панель `privateTransferPanel.js`. Email, запасная
почта, телефон и пароль выбираются **независимо**, по умолчанию всё выключено. Разрешения
действуют только на одну ручную операцию, не записываются в настройки и сбрасываются после
действия или смены диска. Для пароля обязательно дополнительное подтверждение риска: любой,
у кого есть внутренний ключ набора или доступ к нему через основной/запасной секрет, сможет
расшифровать переданные данные. Полнота местных контактов подтверждается отдельно; недоступный
или заблокированный vault не выдаётся за пустые поля.

`stagePrivatePublication()` готовит офлайн партию выбранных категорий **всех существующих
активных и архивных персонажей** с уже сохранёнными sync-ID. Отдельное подтверждение показывает
число персонажей и категории, но не значения. Ничего не пишется до `commit({confirmed:true})`.
Проверяются сохранённый state, привязка аккаунта/набора/ключа, принятая основа и ревизия очереди.
Партия шифруется до устойчивой очереди; для отправки используется обычная отдельная кнопка
отправки, а уже включённая автоотправка также может отправить эту явно подготовленную партию.
Подготовка очереди сама по себе не называется успешной отправкой.

Это **не автоматическая синхронизация местных секретов**: изменение контакта после подготовки
не добавляет его новое значение в партию. Обычные сохранения не читают контакты для экспорта;
они переносят уже согласованную зашифрованную приватную часть без обновления её местными
значениями. Coalescing публичной очереди, в том числе возврат публичных данных к основе,
не должен выбросить отдельное секретное намерение. Подготовленная партия сохраняется при
перезапуске. Снятие галочек не отзывает уже подготовленную отправку и не удаляет прежние файлы.
Автоматической отмены/очистки такой очереди, отзыва раскрытых секретов и ротации ключа здесь нет.

Содержимое истории **v4** включает публичный снимок, отдельный `privateSnapshot` с явными
парами `characterId → поля`, родительский pin и cumulative метки ручного календаря. Это версия
**содержимого**, не изменение внешнего AES-GCM-конверта v2, капсулы ключа или очереди v5.
Приватная схема принимает только четыре категории строк и существующие публичные character
sync-ID, отклоняет повторы, посторонние поля, getters и превышения ограничений. Пропавшая
категория не означает удаления: все потомки сохраняют прежние записи и поля. Очистка передаётся
только явно присутствующей пустой строкой. Понижение v4 до v1/v3 и исчезновение уже перенесённого
поля блокируются. **Обновите все ПК до первой партии:** старые сборки v4 не понимают.

При отдельной проверке контактов пользователь сам выбирает проверенную версию. Показываются
раздельно источник, дата файла, время проверки, известное локальное сохранение и часовой пояс.
Значения не выводятся в DOM, атрибуты, журнал или исходные ошибки: видны только имя персонажа,
категория, факты заполненности и предупреждение **«выбор ОЧИСТИТ местное поле»**. По умолчанию
ничего не отмечено; применяются только выбранные пары персонаж/поле. Для отсутствующего местного
sync-ID сначала нужна публичная запись персонажа, сопоставления по нику нет. Показ ограничен
первыми 1000 различающимися полями. Перед применением голова перечитывается, источник должен
оставаться единственным и с тем же pin; память, диск и vault проверяются guarded записью.
Публикация новых местных секретов после применения автоматически не включается.

**Перед заменой нужна отдельная защищённая копия прежних контактов.** UI требует явное
подтверждение её наличия; само приложение не доказывает, что внешняя копия действительно есть.
Автоматическая копия `state.json` сохраняется, но при OS-vault содержит только ссылки и **не
восстанавливает прежние значения vault** после замены. Если пользователь отключил vault,
локальный state и его копия могут содержать открытые контакты — облачный файл всё равно
шифруется, но локальную копию надо защитить отдельно. Общего автоматического отката vault+state
после частичного сбоя нет; неподтверждённая запись останавливает сохранения до проверки.

**Сохранение входящей приватной части без применения:** если приватная часть на подтверждённой
облачной линии изменилась, публичное объединение по умолчанию останавливается до записи
отметки. В сравнении есть отдельная изначально выключенная галочка: разрешить сохранить
**уже имеющуюся на диске** зашифрованную партию в будущих версиях. Подтверждение не применяет
её к местным контактам и не разрешает выгрузку новых местных значений. Оно действует для
конкретного выбранного pin; дата не выбирает версию. Смена диска, версии, галочки во время
диалога и завершение/отмена попытки сбрасывают разрешение. Публичные конфликты по-прежнему
требуют своего отдельного выбора.

Для такой операции используется **v4 отметки незавершённого объединения**, не v4 содержимого
истории и не версия очереди. Отметка хранит только pins, хеши, явное `privateCarryConfirmed:true`
и прежнее решение публичных конфликтов. `appliedIntentHash` равен `null` либо проверенному
хешу прежнего намерения при согласовании уже выбранного удаления календаря. До изменения
очереди создаются backup и отметка; после неизвестного CAS и перезапуска подтверждение
восстанавливается только для того же target pin. Переданное противоположное разрешение не
заменяет сохранённое. Capability авторизации сверяет разрешение с проверенным планом и
устойчивой отметкой. Уже изменённую основу нельзя просто отменить снятием галочки — требуется
проверенное завершение. **Обновите все ПК:** старые сборки эту отметку не понимают.

**Ограничение:** отдельная неотправленная местная секретная партия продолжает блокировать
перенос публичной основы, даже с новым разрешением. Проверяется вся ожидающая линия, включая
более раннюю prepared-партию перед публичным queued-хвостом. Старые queued/prepared публичные
намерения сохраняются зашифрованными до проверки объединённого потомка. Разные секретные
намерения и разошедшиеся ветви автоматически не объединяются; полноценный private three-way
merge, отмена ожидающей секретной партии, долговременный opt-in автоматической передачи и
аудит криптографии остаются отдельной работой. Испытания настоящих дисков, приложения на двух
Windows-ПК, отключения питания и нескольких процессов не заменяются синтетическими тестами.
В веб-версии и демо нативные действия этой панели отключены.

## Эксперимент первого снимка и восстановления

После сохранения доступа пользователь отдельно подтверждает создание **нового** набора: поиск
старого облака не выполняется. Создаются локальный backup state и случайный ключ данных с двумя
независимыми обёртками; запасной ключ нужно сохранить отдельно и повторно ввести. Конверт и
намерение первой отправки устанавливаются вместе в защищаемой локальной очереди, затем
закрепляется pin. Повторный показ кода сверки не требует сети. После неизвестного ответа запись
не повторяется автоматически; есть ограниченный сценарий продолжения с уже сохранённым ключом.

Кнопка первого снимка сверяет подготовленный файл с сохранёнными данными, затем читает и
сверяет отправленный шифротекст. Если данные изменились после подготовки, отдельное явное
подтверждение позволяет отправить более ранний снимок **только как исторический корень**:
текущие изменения при этом не считаются отправленными. Замены подготовленного корня нет.
При неизвестном исходе повторное создание не запускается. Не удаляйте старое облако и не
считайте его отсутствие доказанным. Ограничения доставки сохраняются даже при проверке чтением.

На другом ПК код получен отдельно от облачного файла; сначала проверяются отпечатки, ключ,
корень и наблюдаемая история, создаётся backup и показывается предварительное сравнение без
возможности применения. Только после выбора версии и явного подтверждения повторно проверяются
облако и локальные данные, затем локально устанавливаются ключ, пустая очередь и привязка.
Применение выбранных записей — отдельная операция с отдельной копией: публичные поля выбранной
облачной записи заменяют местные целиком, включая неотправленные правки; это действие не
объединяет их и не разрешает конфликты. Пустой или неполный список
у провайдера не доказывает полноту истории. Эксперимент поддерживает лишь Google «Мой диск»
`root` и Яндекс `app:/`; перемещённые/другие папки и старые наборы автоматически не обнаруживаются.
Сценарии проверены на синтетических данных и fake IPC, не на реальных аккаунтах или Tauri/Windows.

## Ограниченная отправка последующих сохранений

После подтверждения первого снимка его создавший ПК может вручную подготовить и отправить
изменения или отдельно включить автоотправку для одного выбранного провайдера. Восстановленный
ПК может это делать после отдельного согласования полного совпадения с облачной основой. Разрешение
хранится локально в WebView и не входит в переносимый state; по умолчанию оно выключено.
При сохранении и запуске планировщик повторно проверяет сохранённый state, при необходимости
назначает новые sync-ID с резервной копией и ставит **зашифрованный** снимок в очередь без
сети. Частые ещё не начатые отправки объединяются. После неизвестного ответа уже начатый
запрос создания не повторяется; допускается только проверка точного файла. При отключении
автоотправки уже начатый native IPC может завершиться.

Перед новой отправкой проверяются локальная последовательность и все наблюдаемые облачные
версии; требуется единственная видимая голова, совпадающая с последней подтверждённой локальной.
Другая голова, развилка, недоступная история, исчезновение опубликованной сущности или отметка
частичного применения останавливают отправку. Отсутствие записи не считается удалением.
Пустая очередь восстановленного ПК не считается принятой базой. После полного совпадения
публичных данных и выбранных групп настроек пользователь может подтвердить основу: история и
локальный файл проверяются повторно, сначала закрепляется шифротекст с локальным anchorId, затем
с backup сохраняется связанная отметка state. Это также работает на первом ПК, если все ранее
подтверждённые локальные версии входят в наблюдаемую линию новой головы, а ожидающих отправки
версий нет. Ранее известные отпечатки и квитанции сохраняются; при потере ответа между записью
очереди и state старая отметка не позволяет отправку, а подтверждение можно повторить с тем же
anchor при неизменной истории и state. Новая принятая основа — в том числе при восстановлении
на другом ПК — сохраняется в локальной очереди формата v4 вместе со всей проверенной линией.
Более старая сборка не умеет читать v4 и должна остановиться, поэтому все ПК нужно обновить
перед экспериментом. При неполном выборе, разных источниках, неподтверждённых удалениях,
неподтверждённых исходящих версиях или изменениях во время проверки согласование останавливается.
Предельная история — 128 версий; её автоматической очистки на диске нет. При переносе
очереди v4 в этот предел входят все известные предки, а не только собственные квитанции;
новый снимок сверх предела не ставится в очередь. Для старой принятой очереди v3 полный
размер линии офлайн неизвестен и окончательно проверяется перед отправкой. Настройки для
последующих снимков берутся из ранее подготовленного корня, а не из временных
галочек сравнения. Отдельная ручная передача контактов использует тот же ключ, диск и очередь; перенос журналов и автоматическая выгрузка новых местных секретов отсутствуют.

Старый IPC для создания очереди без проверки привязок удалён из текущей desktop-сборки.
Начальная установка проходит через отдельную команду, которая под общим lock проверяет обе
очереди, обе привязки и локальные привязки аккаунта и ключа. Это не защищает от старых версий
приложения, других команд, некорректного прямого доступа к файлам и хранилищу или иных процессов.

Запись state и очереди не образует единой транзакции: после падения между ними следующий запуск
должен повторно подготовить текущий сохранённый снимок. Пины и локальный CAS не защищают от
согласованного отката, других процессов или вызовов других IPC в обход протокола. Даже единая
наблюдаемая голова не доказывает полноту списка провайдера; конкурентная отправка с другого ПК
после проверки может создать развилку. Подтверждение чтением не гарантирует fsync или будущую
сохранность. Пользователь должен сохранять независимые резервные копии.

Местный журнал содержит только время, диск, тип операции и результат из ограниченного списка.
Он не включает ключи, код, ошибки, содержимое данных или метки аккаунтов; хранится отдельно в
localStorage, ограничен 200 записями и **не синхронизируется**. При невозможности записи
показываются только события текущего запуска. Он не заменяет очередь или доказательство доставки.

определяются этим разделом и вводным предупреждением.

## Что уже написано

Ниже описаны отдельные компоненты; ограниченная автоматическая публикация описана выше,
остальные модели пока не образуют полный двусторонний обмен:

- `envelope.js` шифрует проверенный JSON с AES-256-GCM, случайной nonce и ключом
  восстановления; идентификаторы набора и версии связаны с зашифрованными данными через
  AAD. Расшифровка проверяет целостность. Это не проверка полноты и порядка облачной истории;
  экспериментальная панель подготовки и восстановления описана выше; полный жизненный цикл ключа и безопасная ротация ещё не готовы.
- `keyBundle.js` экспериментально создаёт случайный ключ данных и защищает его двумя
  независимыми секретами пользователя. Для обеих обёрток используются scrypt с отдельными
  солями и AES-256-GCM, общая целостность метаданных и обеих обёрток дополнительно проверяется
  HMAC. Можно подготовить замену способов доступа по одному известному секрету или по
  сохранившемуся внутреннему ключу, а при потере обоих — новые ключи для другого набора.
  Результат существует только в памяти: модуль не
  сохраняет ключи, не подтверждает резервную копию и ничего не удаляет или не отправляет.
  Точный формат, ограничения, доверие к отпечатку и необходимость аудита описаны ниже.
- Экспериментальный конверт версии 2 может содержать **две зашифрованные** обёртки
  ключа непосредственно в файле версии. Они привязаны к AES-GCM и проверяются вместе
  с внутренним ключом до помещения в устойчивую очередь. `pairingCode.js`,
  `portableKeyDiscovery.js` и `keyRecovery.js` моделируют поиск и восстановление на
  другом ПК по секрету и независимо сверенным отпечаткам; `cloudReview.js` читает и проверяет
  историю, сравнивает выбранную версию и подготавливает выборочное применение. Настройка,
  восстановление и первая отправка экспериментально подключены в интерфейсе. Всё проверено на
  fake IPC, а не с настоящими дисками или между физическими ПК.
- `encryptedOutbox.js` ставит только зашифрованные конверты в переданное совместимое с
  Web Storage хранилище и снимает их с очереди по точному подтверждению. После `setItem`
  сравнивается прочитанная строка; ошибка записи или несовпадение блокируют чтение и дальнейшие
  изменения очереди в том же JS-модуле и с тем же объектом Storage. Уже запланированные записи
  тоже останавливаются; адрес очереди и хранилище нельзя подменить во время ожидания шифрования.
  Сама очередь не сохраняет карантин после перезапуска и не защищает другие вкладки.
  Отдельная модель `persistentQuarantine.js` испытывает отметку для участвующих вкладок,
  но к очереди или приложению не подключена и не является готовым восстановлением.
  Межпроцессной защиты приложения, подтверждённого атомарного Tauri-хранилища и связи с
  успешным сохранением пока нет. Неоднозначный JSON очереди не перезаписывается.
- `identityMigration.js` строит **только локальный план** назначения постоянных случайных
  sync-ID персонажам, пати, марафонам, заданиям, наградам, бонусам, шаблонам, календарю и
  финансовым записям. План не меняет исходное состояние и не сохраняет результат. Его копия
  содержит всё исходное локальное состояние, включая секреты: отправлять эту копию в облако
  нельзя. `commitSyncIdentities.js` и кнопка в настройках предлагают подтверждённое локальное
  сохранение с проверкой состояния и backup. В ограниченном режиме публикации новые ID
  подготавливаются автоматически с backup; атомарности между процессами или с vault и
  надёжной защиты от конкурирующих изменений пока нет.
- Нормализаторы сохраняют уже назначенные sync-ID. Формы и архив покрыты дополнительными
  тестами: существующие записи сохраняют идентичность, а копии из шаблона и персонаж при
  импорте «Оставить обе» её не наследуют. Обычный импорт обновлённого марафона сохраняет
  локальные ID совпадающих сущностей; при несовпадении уже назначенных ID он останавливается
  до изменений. Полный набор путей удаления и импорта ещё требует проверки.
- `characterExport.js`, `partyExport.js`, `plannerExport.js`, `marathonExport.js`,
  `templateExport.js` и `financeExport.js` по отдельности строят строго проверенные
  разрешённые снимки сущностей. Они требуют уже назначенные sync-ID, заменяют ссылки на
  них и отказывают при неизвестных полях, некорректных или осиротевших ссылках. Для
  марафонов сохраняются задания, награды, участники, назначения, прогресс, история, балансы и
  ссылки на серии и шаблоны; локальный `lastSync` с ошибками входа не экспортируется.
  Адрес источника пока допускается только на HTTPS-домене PW Online с ограниченным
  набором параметров: другие адреса блокируют экспорт, а не обрезаются. Проверка адреса при
  экспорте **не разрешает автоматический запуск**; исполнитель обязан проверить его снова.
- `settingsExport.js` подготавливает только явно выбранные переносимые предпочтения: тему,
  порядок/видимость разделов, вид календаря и отдельно настройки напоминаний встроенных
  игровых событий. Отсутствие невыбранной группы не означает её
  удаление. Другие группы настроек и отдельные хранилища журналов не экспортируются. Выбор и
  применение этих групп есть в экспериментальной панели проверки, но экспорта журналов пока нет.
- `publicSnapshot.js` объединяет подготовленные публичные записи персонажей, пати, марафонов,
  шаблонов, календаря и финансов в отдельный набор; настройки добавляются только по явному
  выбору. Он не включает журналы или структурированные секреты; в ограниченном режиме
  публикации запускается для подтверждённых локальных сохранений.
- `compareSnapshots.js` сравнивает два таких набора по стабильным ID и возвращает поля и
  значения, отличающиеся между ПК и диском. Неполные разделы и повторные идентификаторы
  отклоняются. При отсутствии общего подтверждённого предка записи помечаются как «только
  здесь/там», но не как добавленные или удалённые; невыбранные группы настроек не стираются.
  Это предварительный просмотр, а не разрешение конфликтов, полная проверка бизнес-схемы,
  восстановление и применение на другом ПК.
- `encryptPreparedSnapshot.js` отдельно выбирает email, почту восстановления, телефон и пароль;
  по умолчанию все четыре отключены. Для пароля нужно дополнительное подтверждение риска;
  для любых контактов вызывающий код должен подтвердить полноту их источника, чтобы сбой vault
  не выдал пустые значения за намеренное удаление. Сам этот модуль не может доказать полноту
  vault и не должен получать подтверждение автоматически после повреждённой записи.
  Функция возвращает только зашифрованный конверт, не файл с открытым текстом. Она не создаёт
  интерфейс выбора, не хранит ключ, не отправляет данные и не восстанавливает контакты.
- `mergeRecord.js` сравнивает одну сущность по общей базе: объединяет независимые поля,
  различает отсутствие и `null`, возвращает конфликты при одновременной правке одного поля,
  удалении против правки или неоднозначном восстановлении. При конфликте частичная запись
  не возвращается. Это не проверка общей базы, не слияние полного набора и не применение
  данных; массивы считаются целым полем, чтобы не потерять изменения из-за сдвига индексов.
- `selectiveRecordReview.js` предварительно рассматривает **одну** запись относительно
  предоставленной базы: строит копию-кандидат только с выбранными неконфликтными полями,
  оставляя невыбранное в списке ожидающих. Массивы рассматриваются целиком; неизвестные или
  повторные пути выбора отклоняются. Выбранный конфликт блокирует весь план; отсутствие поля
  не считается удалением. Метка удаления записи требует отдельного подтверждения, но её
  происхождение сам модуль не удостоверяет. Новая облачная запись без базы блокируется до
  проверки истории и идентичности. Объём сравнения и выбора ограничен.
  Это предварительный расчёт в памяти, **не готовый импорт или сохранение**: модуль не проверяет
  общий предок, подлинность меток, полноту истории, бизнес-схему, зависимости между записями
  или актуальность локальной и облачной версий. Тексты и даже ключи путей могут содержать
  личные сведения; ни кандидат, ни пути нельзя автоматически записывать в журнал.
- `history.js` экспериментально шифрует подготовленные **публичные** снимки вместе с одной
  ссылкой на родительскую версию. Ссылка содержит ID и SHA-256-отпечаток полного зашифрованного
  конверта. Для переданного набора модуль проверяет AES-GCM, формат, связи, единый доверенный
  корень и ранее известные отпечатки; отказывает при пропущенных родителях, повторных ID,
  подмене, циклах или использовании одного sync-ID для разных типов сущностей в разных
  снимках. Для двух версий находит ближайшего общего предка в проверенном дереве. Читатель
  понимает прежнюю версию содержимого и новую экспериментальную версию с явными метками
  удаления календарных записей; старый читатель новую версию не понимает. Новая версия
  проверяет удалённые ID строго относительно непосредственного родителя и запрещает повторное
  появление помеченного ID в её потомках. Метка не выводится из простого отсутствия записи.
  Проверка выполняется только в памяти и не сохраняет файлы, очередь или контрольные отметки.
  Версия содержимого v4 добавляет отдельную приватную часть ручной передачи и сохраняет cumulative метки календаря, в том числе пустой набор меток. Структурная проверка
  не обнаруживает секрет, вручную записанный в примечание, и не заменяет allowlist-экспорт.
  Ограничения безопасности и применения приведены ниже; этот формат ещё не финальный.
- `reviewDependencies.js` проверяет известные связи в одном уже подготовленном публичном
  кандидате: персонажи и пати, архивный состав, серии и марафоны, задания, шаблоны,
  участников, назначения, прогресс, балансы и награды, операции, товары, долги и платежи.
  Отдельно сообщает об отсутствующей записи, несовпадении типа и некоторых несогласованных
  обратных связях; пустые необязательные ссылки не превращаются в удаления. При превышении
  10 000 проблем отказывает целиком, а не возвращает усечённый результат. Нет полного
  соответствия бизнес-схемам, восстановления или записи: даже отсутствие обнаруженных проблем
  не разрешает импорт. ID и пути результатов тоже не следует писать в журнал.
- `fieldProvenanceReview.js` экспериментально совмещает историю, выбор полей одной существующей
  записи и проверку известных зависимостей кандидата. Источник записывается отдельно для каждого
  выбранного поля только после совпадения всего предложенного снимка со следующей локальной
  версией в проверенном дереве; невыбранные поля остаются ожидающими. Это проверка **в памяти**,
  а не доказательство записи в desktop-хранилище. Для неё добавлен изолированный кодек
  зашифрованного checkpoint: при повторной передаче файла и независимых доверенных отметок он
  может восстановить модель в тесте. В самом приложении постоянное хранение, ключи и безопасное
  восстановление после перезапуска пока не подключены. Нет поддержки создания/удаления/архивации,
  разрешения конфликтов или безопасной публикации. Более строгие ограничения, включая остановку
  при появлении новой облачной версии до решения ожидающих изменений, описаны ниже.
- `plannerCandidate.js` предварительно преобразует выбранные поля **одной существующей**
  задачи, события или заметки в отдельную копию локального состояния. Поддерживаются также
  записи, связанные с клановым событием, без обращения к сайту. Сначала весь публичный снимок
  локальных данных сравнивается с просмотренной версией; проверяется известная история,
  конфликты и зависимости. Неизменённые поля, локальные ID, `syncId`, источник события,
  дата создания, остальные записи и локальные секреты остаются в копии. У выбранных дат,
  времени, длительности, напоминания, статусов и повторов дополнительно проверяются допустимые
  значения и точное обратное преобразование через экспорт и нормализатор: неверные значения
  не исправляются молча. Неподтверждённое отсутствие отметки не считается её удалением.
  Общие ссылки объектов развязываются как в JSON, чтобы правка календаря не задела другое
  локальное поле. Неотмеченные поля остаются ожидающими **в модели памяти**. Её `bindModel`
  и `refreshModel` не подтверждают запись файла, резервную копию или полноту истории. Повторное
  создание модели от исходного предка после частичного выбора теряет сведения о принятом.
  В тестах модель можно восстановить из checkpoint с независимо переданными доверенными
  отметками, но в приложении безопасного сохранения и продолжения после перезапуска пока нет.
  Этот мост не создаёт и не удаляет записи и не разрешает конфликты; другие разделы пока не
  имеют такого моста. Копия локального состояния может включать контакты и секреты — её нельзя
  отправлять или писать в журнал. Модуль не подключён к реальному UI, облаку или записи на диск.
- `plannerLifecycleCandidate.js` отдельно моделирует создание или удаление **одной выбранной
  ручной** задачи, события или заметки. Он сверяет локальную публичную проекцию, независимые
  известные отпечатки, общего предка и все переданные ветки. Для создания удостоверяет новое
  появление sync-ID в видимой истории, выдаёт отдельный случайный локальный ID и не переносит
  чужой порядок или другие невыбранные записи. Для удаления требует явную метку в истории и
  второе подтверждение, а локальная правка или перестановка блокирует план. Перед выдачей
  кандидата также проверяются известные зависимости всех публичных разделов; это не полная
  бизнес-валидация. Ошибочные даты,
  статусы и другие поля не исправляются молча. Клановые записи здесь заблокированы до сверки
  с сайтом; голоса и ответы эта модель не посылает. Результат — лишь копия в памяти, без
  подтверждения записи, резервной копии, полноты облака или защищённых якорей. Подробности и
  ограничения, включая сбой между записью данных и служебных отметок, приведены ниже.
- `providers/` содержит конструкторы запросов, ограниченный GET-транспорт и отдельный
  **не подключённый** транспорт создания файлов `uploadTransport.js`, а также читатели и
  `versionVerifier.js` для сверки загруженного конверта. Реальное приложение, OAuth, очередь,
  автосохранение и демо их не вызывают. Токен находится в памяти, а доверенный `fetch` обязан
  соблюдать TLS, запрет redirect и сигнал отмены; это не безопасное хранилище и не гарантия
  стирания. Нельзя логировать токены, пути, подписанные ссылки, исходные ошибки и содержимое.
  Google заранее выдаёт ID через `generateIds`, а multipart-создание передаёт этот ID;
  Google документирует `409` при успешном прежнем создании с **тем же** ID. Один и тот же
  `versionId` с разными Google ID всё ещё может дать дубликаты, а ID и зашифрованный конверт
  должны быть надёжно сохранены вместе до POST. `uploadTransport.js` принимает ID папки от
  вызывающей стороны; отдельная экспериментальная модель поиска и создания описана ниже.
  Для Яндекса запрашивается ссылка с
  `overwrite=false`, а PUT выполняется без OAuth-заголовка и без перенаправления. Ответ `202`
  — только принятие, не завершённая загрузка. После отправки результаты `accepted`, `pending`,
  `conflict` и `unknown` не означают проверенного содержимого; автоматических повторов нет.
  Сверка перечитывает файл и сравнивает исходный ASCII JSON конверта; Google дополнительно
  проверяет ID в двух полных обходах, Яндекс — заданный путь. Отсутствие, разница, ошибка или
  несовпадающий ID не разрешают удалять элемент очереди или автоматически повторять запрос.
  Даже совпадение — наблюдение в данный момент, не доказательство полноты облака, устойчивости
  локального журнала или будущей сохранности. Структурная проверка конверта не доказывает, что
  вызывающий действительно зашифровал исходные данные. `authenticatedSession.js` связывает
  проверку заданного ID аккаунта с чтением, записью и сверкой одним токеном: несовпадение или
  ошибка останавливают действие. Это не первое подтверждение пользователя, не проверка
  стабильности ID и не устойчивая привязка. Модели проверены на вымышленных API и двух
  тестовых клиентах; отдельно в Chromium запросы выполнялись только к перехваченным поддельным
  CORS-ответам. Это не испытания настоящих аккаунтов, совместимости CORS/Tauri или Windows.
  Устойчивых журнала попыток, межпроцессной блокировки, привязки аккаунта и восстановления нет:
  **не использовать этот код для настоящих данных до устранения этих блокеров**. Обычная Google
  multipart-загрузка ограничена 5 MB; больших и возобновляемых загрузок пока нет.
- `providers/nativeDiskFetch.js` и зарегистрированная команда `cloud_disk_network` добавляют
  экспериментальный мост этих моделей к нативному HTTPS. Интерфейс, очередь и реальные токены к
  нему не подключены. Разрешены только известные операции Google и Яндекса; Rust независимо
  строит адреса и метаданные, отклоняет лишние поля и неподходящие подписанные ссылки. PUT на
  uploader Яндекса не содержит OAuth, запросы не перенаправляются и не повторяются. Структура
  канонического AES-GCM-конверта проверяется до отправки, но не доказывает, что отправитель
  действительно зашифровал исходные данные. Таймаут не означает отмены уже начатой записи;
  слот в JS остаётся занят до завершения IPC. Ограничение одного запроса внутри процесса не
  является межпроцессной блокировкой или устойчивым журналом. Сценарии обоих провайдеров
  проверены только с поддельным IPC/API; нативный исполнитель и URL-политика — с поддельными
  Tauri и HTTP-типами. Реальные reqwest, Windows, Tauri, провайдеры и устойчивость не испытаны.
  До этих проверок и реализации очереди/восстановления мост нельзя использовать для настоящих
  данных. Любой код главного окна может вызвать зарегистрированную команду.
- `googleFolderManager.js` экспериментально выделяет ID, дважды полностью ищет папки по
  `appProperties` и отдельно создаёт видимую папку «Твиноферма». Переименование не мешает
  поиску, несколько папок остаются неоднозначными, а уже найденная папка блокирует создание.
  До POST вызывающий должен устойчиво сохранить ID и намерение; при таймауте или потере ответа
  исход остаётся неизвестным, и этот экземпляр не повторяет создание. Два одновременных ПК
  всё ещё могут создать разные папки: полного облачного lock, сохранения намерения, выбора и
  доверенной привязки нет. Результат поиска — кандидаты, а не доказательство полного списка или
  разрешение автоматически применять данные. Испытания проведены только с поддельным API/IPC.
- `providers/oauthPkce.js`, `oauthTokenTransport.js`, предпросмотр идентичности и
  `src-tauri/src/cloud_oauth_callback.rs` используются разовой проверкой регистрации и
  отдельным экспериментальным первым входом в настройках. Нативный OAuth-канал обмена кода
  и просмотра аккаунта не читает и не пишет файлы диска. В диагностике токены отбрасываются;
  при отдельном согласии первый вход сохраняет доступ в локальном Credential Manager.
  Разрешение у провайдера автоматически не отзывается. Реальные Tauri, сервисы и само
  приложение Windows ещё не проверены; демо не вызывает ни один из этих сценариев. Команды
  ограничены главным окном, но любой код в нём может их вызвать. Испытания Credential Manager
  в Windows CI используют только синтетические имена и данные. Безопасность и устойчивость
  реального сохранения и ротации токенов не подтверждены; границы описаны ниже.
- `ui/confirmCloudAccount.js` используется экспериментальным входом для отдельной сверки
  метки. Демо показывает тот же компонент только с постоянными вымышленными данными, без
  входа, записи или журнала.

### Усиление локальных копий и восстановления

В desktop-командах сохранение и резервное копирование теперь используют отдельные временные
файлы без перезаписи: подготовленное содержимое сбрасывается и проверяется до замены состояния.
После `rename` состояние перечитывается; на Unix дополнительно запрашивается сброс каталога.
При ошибке после попытки `rename` результат считается **неизвестным**. В этом JS-контексте
очередь `persist()` останавливает последующие и уже поставленные в очередь записи до перезапуска,
а интерфейс предупреждает пользователя. Потерянный ответ desktop-команды тоже считается
неизвестным исходом; повтор допускается лишь при явном ответе об ошибке до замены. Автоматический
откат или повтор не выполняется: перед
перезапуском нужно учесть возможные несохранённые изменения и проверить данные и копии. Native-команды
состояния, резервных копий, контактов и `factory_reset` используют общий mutex для отдельных вызовов
в одном процессе. Это не общая транзакция между вызовами и не блокирует другие процессы, внешние
изменения, прямые вызовы адаптера или не участвующие команды других хранилищ.

Обычная стартовая миграция старой схемы теперь сначала требует **проверенную копию именно
загруженного исходного JSON**, без ротации старых копий — и в desktop-версии, и в браузере.
Адаптер временно связывает исходную строку с прочитанным объектом в памяти: если объект или
источник изменились, операция останавливается. Перед заменой исходник проверяется снова; в
native временный файл подготавливается и сверка исходника повторяется непосредственно перед
`rename`. В этой вкладке/JS-контексте на время миграции запрещены новые записи, загрузка,
восстановление и обычная копия с ротацией; уже поставленная запись сначала завершается. При
ошибке копирования профили и vault не переносятся, onboarding не открывается автоматически,
запись блокируется и остаётся видимое предупреждение. При подтверждённой ошибке до замены можно
восстановить существующую копию; при неизвестном исходе записи повтор и восстановление
заблокированы до перезапуска и проверки. Временное свидетельство забывается после операции,
но JavaScript не гарантирует физическое стирание строки из памяти. Оно не пишется в журнал.

При загрузке контактов из хранилища ОС теперь сначала проверяются все полученные записи и
однозначность исходных и новых ID, включая архив и цепочки переименований. Повреждённые записи,
неизвестные поля, конфликтующие старый/новый ключ или неподтверждённый ответ останавливают
сохранение. Если исходный файл помечен `secretsInVault`, отсутствие доступа к vault не превращается
в пустые контакты даже при выключенной настройке. Если после повторного включения vault открытые
контакты в файле отличаются от старой записи ОС, включая намеренно очищенные поля, запись
останавливается вместо молчаливого выбора одной из версий; автоматического разрешения конфликта
пока нет. Когда открытые контакты впервые переносятся в vault, до его изменения также нужна
проверенная копия исходного файла, даже без смены схемы.
Проверочная запись доступности использует отдельное от контактов имя, чтобы не затронуть персонажа
с необычным ID. Смена только регистра ника сохраняет прежний ID и не переносит профиль.

При изменении vault затронутые ключи сверяются с ранее прочитанными значениями и перечитываются
после записи. Ошибка, несовпадение или отказ сохранения `state.json` после изменения vault блокирует
повтор и восстановление в текущем JS-контексте; в интерфейсе показывается предупреждение. Это
**не транзакция**: часть записей vault могла уже измениться, проверка до записи не является CAS,
а блокировка не сохраняется после перезапуска. Отсутствующая запись сама по себе не доказывает,
что контакты были пустыми, а не потерялись ранее. Нужно вручную проверить данные и копии до
перезапуска; обещать автоматический откат нельзя.

Это **не межпроцессный или межвкладочный CAS**: другая программа, вкладка или не участвующий
писатель могут изменить файл между сверкой и заменой. Native mutex действует только в одном
процессе и сериализует отдельные команды контактов и состояния, но не всю последовательность
переноса vault, профилей и сохранения. Прямые IPC-вызовы и другие процессы могут вмешаться между
этапами. После успешной копии, но до неудачного сохранения эти действия уже могли изменить профили
или хранилище ОС; автоматического общего отката нет. Копия состояния может содержать пароли в
открытом виде, если они находились в старом JSON, и может не содержать контакты, уже перенесённые
в хранилище ОС, или отдельные журналы. Эта защита не является согласованной копией всех хранилищ
и сама по себе не разрешает применение данных из облака.

### Полный сброс: ограничения и защита от гонок

Подтверждение теперь строится по активным **и архивным** персонажам и пати. Одноразовый план
связан с состоянием, показанным пользователю; изменившееся состояние требует нового подтверждения.
Имена контактов и входов GameCenter собираются раздельно и удаляются из соответствующих пространств
`contacts:` и `gc-magic:`; число в диалоге означает возможные имена, а не найденные записи ОС.

В этом JS-контексте сброс останавливает новые записи, загрузку, восстановление и операции с
копиями, дожидается уже начатых сохранений и повторно проверяет согласованный снимок. Затем
читает точную строку `state.json`, ещё раз проверяет состояние в памяти и передаёт строку только
локальной native-команде. Под тем же процессным mutex она до первого удаления проверяет имена,
типы файлов, список копий и неизменность этой строки. Если чтение не удалось, сохранение и сброс
блокируются, но можно восстановить существующую копию. После отправки самой команды частичный,
неполный или потерянный ответ считается неизвестным исходом: повтор, запись и восстановление
в текущем контексте остановлены до проверки данных и перезапуска. При подтверждённом успехе
запись также остаётся остановленной до перезапуска, чтобы не вернуть прежнее состояние из памяти.

Это не безопасная очистка носителя и **не транзакция**: сравнение не доказывает совпадение памяти
с файлом, не устраняет гонки с другим процессом после сверки и не охватывает команды GameCenter,
банка кук, прямые IPC-вызовы или другие JS-контексты. После перезапуска блокировка не сохраняется.
Отдельные локальные журналы и неизвестные или забытые записи хранилища ОС могут остаться;
перечислить все такие записи команда не может. Пользователю предлагается завершить другие операции,
закрыть другие окна и заранее сохранить данные: штатные резервные копии при сбросе удаляются.
Снимок подтверждения и считанная строка могут содержать открытые контакты, хранятся только в памяти
и не журналируются, но JavaScript не гарантирует их стирания. Реальный Tauri/Windows, обрывы IPC,
хранилище ОС и сбои питания ещё не проверены; изолированные native-тесты используют подставные
Tauri и keyring. При неподтверждённом удалении отдельной резервной копии интерфейс обновляет список
и предлагает проверить её наличие; сообщение не доказывает, что файл сохранился.

При массовом удалении пати, марафонов или персонажей приложение больше не продолжает действие,
если сохранение или создание копии не подтверждено. Диалог и снимок проверяются до и после ожидания
сохранения и копии; два опасных действия из этого интерфейса одновременно не запускаются. Ответ
native-команды создания копии проверяется на допустимое имя. Это не межпроцессная блокировка,
не доказательство совпадения памяти с файлом и не транзакция хранилища ОС. Копия состояния не
включает контакты из vault и входы GameCenter; их удаление нельзя откатить этой копией. Если ответ
об удалении входов не подтверждён, показывается предупреждение. Ошибка после начала удаления может
означать частичный результат: в текущем JS-контексте дальнейшие запись и восстановление тогда
останавливаются до проверки и перезапуска; неизвестные записи ОС могут остаться. Эта блокировка не
сохраняется после перезапуска. Снимок подтверждения может содержать открытые контакты, не
журналируется и удерживается в памяти до завершения действия.

При обычном импорте JSON предварительное сохранение обязательно. Если пользователь не отключил
настройку копии перед импортом, неподтверждённое создание копии останавливает и замену, и
объединение до изменения данных; если отключил, диалог прямо предупреждает об этом. В обоих режимах
сообщается, что копия не включает отдельное хранилище контактов ОС, входы GameCenter и сессии.
Состояние в памяти сравнивается со снимком до и после диалогов и ожидания сохранения/копии. Если
оно изменилось, файл предлагают открыть заново. Закрытие окна замены при ожидании отменяет её.
Снимок исключает UI, может содержать контакты, не журналируется и остаётся только в памяти, но
JavaScript не гарантирует его стирания. Это сравнение значений не обнаруживает изменение с возвратом
прежнего значения, прямые изменения диска/vault или другого процесса и не доказывает совпадения
памяти с файлом. При режиме замены обычный JSON-импорт теперь включает календарь, если он есть в
файле: повторы, состояния отдельных дней, напоминания и локальные ID клановых событий сохраняются.
Дубли ID, повреждённые даты, неизвестные или теряемые нормализатором поля останавливают замену;
файл более новой схемы отклоняется. Если календарь отсутствует в файле, текущие записи остаются.
**Объединение календаря обычным импортом пока не поддерживается**, об этом сообщает сводка; оно не
является облачной синхронизацией и не отправляет ответы на сайт. Ошибка после начала изменения может
означать частичный импорт; дальнейшие запись и восстановление в этом контексте останавливаются до
проверки и перезапуска. Переименование профилей и записи vault не входят в общую транзакцию;
полноценной резервной копии vault по-прежнему нет.

### Резервные копии и восстановление

Новая desktop-копия побайтно сверяется с исходным файлом, а затем публикуется под новым именем
без перезаписи. Ротация старых копий начинается только после подтверждения новой и не удаляет
её при совпадении времени файлов. Если файловая система не поддерживает hard link, создание
копии останавливается, прежние копии не удаляются. В одном JS-контексте создание копии дожидается
ранее поставленных записей, а запрошенные после начала копии записи выполняются после неё; ошибка
ранее поставленной записи останавливает копирование. У записи при начале подготовки создаётся
независимый JSON-снимок, чтобы изменения вложенных полей во время ожидания vault не примешивались
к уже начатой записи. Изменения до начала ожидающей записи всё ещё могут в неё попасть; изменения
без последующего запроса сохранения эта очередь не сохраняет. Копирование не пересекается с
обычным восстановлением, удалением копии, загрузкой или сбросом в этом контексте. Это не блокирует
внешних писателей и не создаёт согласованную копию vault.

Перед ручным восстановлением интерфейс показывает версию, число персонажей, архивных персонажей
и задач/событий, состояние текущего файла и отметку связи с хранилищем ОС, не показывая контакты.
Отсутствие отметки не доказывает отсутствия записей ОС; отсутствующие или нераспознанные разделы
могут стать пустыми. Неизвестная или более новая версия и некорректная отметка vault останавливают
восстановление в интерфейсе. Доступный интерфейсу review проверяет тип и JSON выбранной копии,
но **не является полной проверкой бизнес-схемы или гарантией пригодности данных**. Контакты ОС после
восстановления остаются прежними и могут не соответствовать копии. Пользователь подтверждает замену.

В desktop выбранный файл и текущий файл связываются с временными SHA-256-отпечатками; в браузере
для этого удерживаются считанные строки. Свидетельство одноразовое, не показывается и не пишется в
журнал. Снимок состояния в памяти сравнивается после ожидания очереди. Изменившаяся копия, текущий
файл или снимок останавливают замену; текущий файл, если он существует, предварительно сохраняется
отдельной проверенной копией без ротации. Сбой копирования останавливает восстановление. Повреждённый
текущий файл сохраняется побайтно для ручного разбора; при его отсутствии native публикует новый
файл через hard link без перезаписи вновь появившегося файла. Если hard link недоступен, операция
останавливается. Файлы больше 128 МиБ при проверке desktop-восстановления отклоняются. Старый прямой
native-вызов для совместимости по-прежнему допускает восстановление без review-свидетельства.

Отпечаток не доказывает подлинность, свежесть или согласованность копии с vault. Сверки не выявляют
изменение с возвратом прежнего значения (ABA) и не являются CAS: внешняя запись между последней
проверкой и `rename` остаётся возможной; проверка символических ссылок и открытие также не атомарны.
Локальные строки свидетелей могут содержать секреты: они не журналируются, однако JavaScript не
гарантирует их физического стирания из памяти.

При ошибке чтения на старте сохранение в этом контексте блокируется, чтобы значения по умолчанию
не перезаписали исходные данные. Восстановление из существующей резервной копии остаётся доступным.
Если desktop-файл читается, но его JSON повреждён или не является объектом, программа пытается
создать проверенную копию без ротации и сообщает, получилось ли это. Непрочитанный файл не
объявляется сохранённым в копии. Если данные созданы более новой схемой, эта версия также
останавливает запись и предлагает обновить приложение; перенос секретов в хранилище ОС и
автоматические проверки клана и входов при таком запуске не выполняются. После восстановления приложение
нужно перезапустить; ограничения по другим процессам и хранилищам сохраняются.

Браузерный адаптер также сверяет записанную строку и перед восстановлением сохраняет текущую;
ошибка до замены останавливает операцию, но после попытки записи исход может быть неизвестен.
При ручном восстановлении интерфейс дожидается уже поставленных в очередь `persist()` и блокирует
новые; дополнительное принудительное сохранение перед копированием не выполняется, поскольку
значения в памяти могут быть пустыми после ошибки загрузки. При успехе запись остаётся остановленной
до перезагрузки, чтобы устаревшие данные в памяти не перезаписали восстановленное состояние.
Это защита одного JS-контекста, не межвкладочная транзакция или гарантия сохранности после сбоя
питания. На Windows переносимого сброса каталога здесь нет. Проверены сценарии и инъекции ошибок
для файлового ядра на Linux и браузерного адаптера; полный Tauri/Windows и реальные сбои питания
ещё нужно испытать. Неочищенный временный файл после аварии не считается резервной копией и может
содержать личные данные.

Полный JSON-экспорт из настроек и командной палитры отдельно предупреждает, что файл **не зашифрован**
и может содержать контакты и пароли открытым текстом, включая данные, загруженные из vault. Перед
созданием файла требуются явное подтверждение, доступный vault при его использовании и успешное
сохранение; снимок в памяти и состояние vault проверяются повторно. При изменении данных экспорт
останавливается. Это не согласованная копия хранилища ОС и не гарантия отсутствия внешних изменений;
браузер только запрашивает скачивание и не подтверждает сохранность файла на диске. Такой JSON нельзя
считать облачным зашифрованным backup. У существующего гибкого экспорта отдельных разделов свой
интерфейс выбора: он тоже создаёт открытый файл и при выборе паролей включает их в JSON; отдельный
аудит этого пути ещё необходим.

**Граница защиты:** копия `state.json` не включает контакты в хранилище ОС, отдельные журналы,
несохранённые изменения в памяти или облачные ключи. Если хранилище ОС выключено/недоступно,
сам файл и его копии могут содержать контакты открытым текстом: отправлять их в облако нельзя.
Перед настоящим облачным применением нужны согласованная копия всех затрагиваемых хранилищ,
блокировка параллельных процессов и очереди сохранений, проверка актуальности, транзакционное
применение и проверенное восстановление. Пустой или неподходящий JSON не заменяет полноценную
проверку бизнес-схемы. Реальное применение синхронизации по-прежнему отключено.

Проверки новых модулей охватывают шифрование, отказ при повреждении, приватность очереди и
экспорта, безопасные параметры запросов, осиротевшие ссылки и поддельные адреса. Тесты форм
также проверяют сохранение ID при изменении долга и его связанной операции. Тест с настоящим
Chromium проверяет восстановление зашифрованной очереди после перезапуска браузера. Это не
испытания с облачными аккаунтами и не проверка сохранности при сбоях desktop-хранилища.

Переименование персонажа меняет только явные ссылки на него, а не произвольные совпадающие
строки в марафонах. При пересечении ключей операция останавливается до изменения данных;
после ожидания профиля ссылки пересчитываются по актуальному состоянию. Если конфликт возник
уже после вызова команды переноса профиля, результат переноса считается неподтверждённым:
повторять перенос вслепую нельзя. Текущая desktop-команда отдельно не подтверждает атомарность
профиля и cookie-хранилища, поэтому этот случай требует проверки пользователем.

## Что должно получиться

Пользователь выбирает **Google Диск или Яндекс Диск** и разрешает доступ к своему аккаунту.
Данные остаются в его облаке; отдельный сервер Твинофермы для их хранения не требуется.
Подключение другого сервера, например WebDAV, — отдельное расширение, не подмена поддержки
обоих выбранных дисков.

На каждом компьютере остаётся локальная копия. Целевое поведение после включения функции:

1. При запуске и периодически во время работы проверять выбранный диск и показывать найденные
   изменения. Проверка может быть автоматической; **входящие данные применяются только после
   выбора пользователя**, а не перезаписывают ПК в фоне.
2. После локального сохранения ставить изменения в постоянную очередь и, при включённой
   автоматической отправке, передавать их с задержкой, объединяя частые сохранения. При
   отсутствии сети очередь должна переживать перезапуск. При конфликте или непроверенном
   состоянии отправка должна ожидать решения, а не затирать чужие изменения.
3. Предоставить две отдельные ручные кнопки: «Сохранить и отправить на диск» и «Проверить
   обновления». После проверки — сравнение по разделам, выбор записей и отдельное подтверждение
   удаления. Отсутствие записи без подтверждённой истории не считать удалением.
4. Показывать состояние, последнюю удачную проверку, ожидающие изменения, ошибку и конфликты;
   фиксировать фактические отправки и обновления в отдельном журнале.

Первое подключение к облаку с существующими данными требует сравнения и подтверждения.
До применения входящих изменений создаётся проверенная локальная резервная копия. Если её
создать нельзя, данные не заменяются. Неотмеченные изменения остаются ожидающими и не должны
исчезать при следующей отправке с этого ПК. При потере доступа к облаку приложение продолжает
работать локально и показывает ошибку; оно не считает пустой ответ удалением.

### Дата и результат проверки

В рабочей версии сравнение должно показывать отдельно для **конкретного проверенного файла**:
диск и дату последнего изменения, сообщённую сервисом; время успешной проверки на этом ПК;
время локального сохранения на момент сравнения. Формат — местный часовой пояс устройства с
обозначением зоны. При отсутствии надёжно разбираемой метки — «Дата недоступна»; не считать
текущую дату датой файла. Сколько времени прошло, допустимо показывать только приблизительно,
по часам ПК. Если дата файла более чем на пять минут позже времени проверки, предупредить о
расхождении часов; это не причина автоматически принимать или отбрасывать данные.

Дата изменения может зависеть от операций сервиса или копирования и, например, в Google её
можно устанавливать. Она не удостоверяет автора, дату отдельных изменений, содержимое или
свежесть и **не выбирает победителя**: конфликт и историю нужно проверять отдельно. Если у
набора несколько веток, в будущем нужно показывать даты у соответствующих версий, не выдавая
одну дату за все ветки. При изменении выбранного диска, файла или локальных данных результат
предпросмотра нужно сбросить или явно пометить устаревшим; перед записью проверять изменения
ещё раз и при необходимости требовать новое сравнение и резервную копию. Настоящая
межпроцессная гарантия такой проверки пока не реализована.

Если проверка не удалась или сети нет, следует отдельно сообщить причину и время последней
**успешной** проверки, не выдавать прежний результат за свежий и не применять его. Если файл не
найден, нужно отличать первое подключение от потери ранее известного файла и не удалять
локальные данные или автоматически перезаписывать диск. Неполный список, повреждённая версия
или отказ доступа не означают «обновлений нет». Эти состояния, реальные часы последнего
сохранения и повторные проверки перед применением — план, в макете они не подключены.

## Данные и приватность

Нельзя просто отправить `state.json` целиком. Экспорт строится по явному списку разрешённых
полей и проверяется на каждом вложенном уровне. Целевой состав — персонажи, пати, марафоны,
календарь, финансы, выбранные настройки и необходимые журналы. Отдельные схемы перечислены
выше; это ещё не полная схема обмена и не восстановление на другом ПК.

Календарный набор включает все ручные задачи, события и заметки: даты, время, повторы,
напоминания, общий статус и отдельные отметки по дням. Встроенное расписание игровых ивентов
формируется кодом приложения и не содержит отдельных пользовательских отметок; его не следует
превращать в созданные пользователем записи. Запись, возникшая из кланового сайта, сохраняет
идентификатор события сайта, чтобы в будущем её можно было отличить от ручной. Если одно событие
уже создано независимо на двух ПК с разными sync-ID, предварительное сравнение запрашивает
проверку идентичности, а не объединяет его молча. Клановый ответ «Пойду/Не пойду» хранится на
сайте и не отправляется при восстановлении календаря. Мост календаря сохраняет существующую
клановую запись, если событие или ответ отсутствуют в сводке, дата не распознана или сайт вернул
неоднозначные строки; явный ответ «Не пойду» по-прежнему удаляет запись. При переносе даты
сохраняются sync-ID и пользовательские отметки. Для безопасной облачной синхронизации удаления
ещё нужен реестр меток и согласование с другими устройствами.

Локальные напоминания записей календаря теперь учитывают повтор и отметку конкретного дня,
а для запаса до суток проверяют также завтрашнее вхождение: например, «за день» срабатывает
накануне, а событие в 00:05 — ещё до полуночи. Журнал привязан к дате вхождения, поэтому
сообщение не повторяется при смене даты. Если запись журнала уведомлений недоступна, защита от
повтора действует только в памяти текущего запуска. Нестандартный сохранённый интервал отображается в
форме и не сбрасывается при другой правке. Запасы **больше суток** пока сохраняются, но,
как и прежде, проверяются только в день события; форма показывает это ограничение. Для полного
переноса таких интервалов нужны отдельные правила и тестирование, а системную доставку в
Windows ещё нужно проверить на настоящем Tauri-приложении.

История промокодов, передач, покупок, «Коллекции» и общие журналы сейчас лежат отдельно в
`localStorage`, а не в `state.json`. У записей часто нет постоянных sync-ID, некоторые записи
ограничиваются по размеру или могут не сохраниться при ошибке хранилища, а ссылки на локальный
id персонажа могут устареть при переименовании. Нельзя считать их перенесёнными или применять
как разрешение повторить покупку/передачу. Для них ещё нужны отдельные миграция, проверка
сохранения и согласование устройств; необработанный журнал ошибок может содержать локальные
статусы и приватные строки. Свободный текст из любого разрешённого поля сам по себе не
проверяется на наличие секретов.

Удалённый персонаж или позиция комиссионки могут оставить осиротевшие ссылки. Реестра
подтверждённых tombstones пока нет, поэтому текущие экспортеры блокируются на таких случаях;
они не удаляют связи и не притворяются, что экспорт полон.

По умолчанию **не экспортируются** контакты и пароли, cookies, токены облака, профили браузера,
локальные статусы входа, пути к игре, GameCenter и настройки конкретного компьютера. Пароли и
контакты доступны как отдельная ручная партия с разрешением для каждого вида поля. Разрешения
не сохраняются и не включают автоматический экспорт новых местных секретов. См. ограничения,
предупреждения о копии vault и протокол v4 в разделе ручной передачи выше.
Пользователь может сам записать секрет в свободный текст; автоматическая фильтрация не
гарантирует обнаружение такого содержимого.

Облачные данные должны шифроваться до отправки. Открытые пользовательские секреты и внутренний
ключ не помещаются в облачный файл. Экспериментальные модули создают зашифрованный конверт и
две защищённые обёртки ключа, но безопасное хранение, передача на новый ПК и полный сценарий
потери ключа ещё требуют интеграции и проверки; макет этого не делает. Токены доступа и
обновления должны храниться только в защищённом хранилище ОС, не в
`state.json`, резервных копиях, логах, репозитории или синхронизируемом содержимом. Если
хранилище недоступно, нельзя молча переходить к хранению токенов открытым текстом.

### Пароль шифрования и запасной ключ: согласованная схема

Пользователь согласовал основной вариант: пароль шифрования плюс отдельный запасной ключ. Он
также попросил возможность задать **свои основной и запасной ключи**. Части этой схемы уже
проверяются изолированно, но это ещё не работающая функция приложения.

1. При настройке приложение создаёт случайный внутренний ключ данных. Основной способ доступа —
   пользовательский пароль/секретная фраза или свой основной секретный ключ. Запасной ключ можно
   создать случайным образом или задать самостоятельно. Оба способа доступа независимы:
   для открытия копии достаточно одного из способов и доступа к файлу.
2. Данные шифруются случайным внутренним ключом **до отправки**. Для доступа на другом ПК
   предлагается хранить вместе с копией две защищённые версии этого внутреннего ключа: одну
   открывает основной секрет, другую — запасной. Пользовательские значения рассматриваются как
   секреты доступа к внутреннему ключу, а не автоматически как готовые байты AES. Ни пароль,
   ни заданные пользователем ключи в открытом виде на диск не отправляются.
3. Экспериментальный формат использует `scrypt` из `@noble/hashes` 2.4.0 с параметрами
   `N=32768, r=8, p=3` и отдельной случайной 16-байтовой солью для каждого секрета; это
   вариант с примерно 32 МиБ памяти из рекомендаций [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
   Параметры файла проверяются до вычисления, произвольные повышенные и пониженные значения не
   принимаются. `scrypt` расходует ресурсы и не заменяет стойкий секрет. Случайный запасной
   ключ содержит 256 бит. Для новых пользовательских значений прототип требует не менее
   8 символов (с 31.10.2026; прежний порог 16 отменён) и отклоняет некоторые очевидные последовательности; секреты сравниваются после
   Unicode NFC и должны отличаться. Эта проверка не измеряет энтропию и не гарантирует защиту
   от угадывания. Не следует повторно использовать пароли облака или персонажей, но пароль
   облака приложению неизвестен и его нельзя запрашивать для сравнения. Параметры, формат,
   зависимость и реализация требуют отдельного аудита и проверки производительности.
4. Основной секрет можно вводить на новом ПК после авторизации в выбранном облаке. Запасной
   секрет стоит сохранить отдельно от облачной копии и независимо от основного, например на
   бумаге в безопасном месте или в защищённом менеджере паролей. Ни один секрет нельзя
   отправлять разработчику, писать в журнал или незашифрованные резервные копии.
5. Забытый пароль нельзя восстановить в открытом виде. Если сохранился запасной секрет,
   `rewrapKeyBundle` может построить новые обёртки того же внутреннего ключа без изменения
   старого файла. Если на доверенном ПК сохранился сам внутренний ключ, похожий расчёт возможен
   через `rewrapKeyBundleFromDataKey` после проверки исходного набора. Модуль не извлекает ключ
   из хранилища и не подтверждает, что оно защищено. Это ещё не сохранение нового файла или
   восстановление в приложении. Простая
   смена пароля или запасного секрета не отзывает доступ к старым обёрткам: при утечке нужна
   ротация внутреннего ключа данных и отдельная политика старых версий и устройств.
6. Если утеряны оба способа и нельзя получить ключ с ранее подключённого устройства,
   расшифровать облачную копию не получится. Локальные данные при этом не исчезают. Чистый
   `prepareKeyLossRestart` создаёт независимый новый набор и ключи, но не читает и не удаляет
   старые файлы и не начинает обмен. Перед реальным перезапуском нужны проверенная локальная
   резервная копия и подтверждение пользователя; другие ПК сначала сохраняют данные и проходят
   сравнение. Старую зашифрованную копию можно оставить на случай, если ключ найдётся.

Прототип проверяет обе обёртки при создании и целостность обеих при открытии через любой слот;
AES-GCM связывает слот и метаданные, HMAC с отдельным HKDF-ключом — весь набор. Открытие
требует заранее доверенный SHA-256-отпечаток набора; вычислить отпечаток из непроверенного
облачного файла **не значит** установить доверие к нему. Постоянного защищённого хранилища
отпечатков и безопасной процедуры доверия на новом ПК пока нет. Возможен откат всего файла,
если доверенный отпечаток потерян. Смена обёрток тоже требует безопасного сохранения нового
отпечатка и согласования устройств. Работа блокируется при нескольких тяжёлых расчётах в
одном JS-контексте, но между процессами такой защиты нет.

Стойкое выведение замедляет подбор, но не исправляет слабый секрет: достаточно взломать один
из двух способов доступа. Защита облачной копии не защищает от вредоносной программы или
постороннего доступа к разблокированному ПК. Строки JavaScript нельзя надёжно стереть из памяти;
возвращаемые внутренний ключ и сгенерированный запасной секрет нельзя логировать или хранить
открытым текстом. Если локальное защищённое хранилище недоступно, нельзя молча записывать ключ
открытым текстом. Ввод, подтверждение сохранения запасного секрета, передача на другой ПК,
устойчивое хранение, полное восстановление, удаление и ротация ещё не подключены.

## Обмен и защита от потери изменений

Один общий файл, который каждый ПК перезаписывает по времени `updatedAt`, недостаточен:
два компьютера могут одновременно сохранить разные правки или работать без сети. Нужны:

- неизменяемые версии с уникальными идентификаторами и ссылками на общую базу, а также
  постоянная очередь; нельзя полагаться на часы компьютеров;
- отдельные стабильные sync-ID сущностей, не зависящие от изменяемого ника персонажа;
  текущий локальный `character.id` используется также для профилей и может меняться;
- слияние независимых полей относительно общей базы, явный выбор при изменении одного поля
  с двух сторон и отдельная обработка удаления против изменения;
- метки удаления, сохранённые до безопасного подтверждения всеми нужными устройствами;
- отказ от автоматической записи при отсутствии общей базы, неполном списке версий,
  повреждённом файле, неподдерживаемой схеме или невозможности расшифровки;
- безопасная обработка частичной отправки, повтора и неизвестного ответа сервиса без потери
  очереди и без слепой перезаписи; детали атомарности каждого API необходимо проверить;
- защита от повторения реальных покупок, передач и других необратимых действий при
  параллельной работе ПК. Синхронизация списка данных сама по себе такой защиты не даёт.

### Подготовленный транспорт записи и восстановление результата

Для одного файла транспорт различает результаты, не записывая журнал и не меняя очередь:

| Результат | Что известно | Что нельзя заключить |
| --- | --- | --- |
| `not_sent` | Запрос с содержимым не был запущен этим экземпляром; например, не получена ссылка | Что на диске нет такого файла или что другие процессы не отправляют его |
| `accepted` | Получен ожидаемый ответ создания | Что файл доступен, совпадает с отправленным или будет сохранён навсегда |
| `pending` | Яндекс вернул `202` | Что файл уже перемещён на Диск |
| `conflict` | Google ответил `409` на создание с данным ID или Яндекс — на получение ссылки загрузки для уже существующего пути | Что существующий файл содержит именно эту версию |
| `unknown` | Запрос записи мог дойти до сервиса | Что файл создан или что запись безопасно повторять |

После любого результата, кроме подтверждённого отсутствия отправки, необходимо оставить
зашифрованный элемент очереди и намерение. До сетевого запроса будущий устойчивый журнал должен
атомарно и надёжно зафиксировать провайдера, ранее подтверждённую привязку аккаунта,
идентификаторы версии/файла, точный конверт и состояние «попытка началась». Если запись журнала
или её подтверждение неизвестны, отправка не начинается. После обрыва или перезапуска сначала
сверяется тот же аккаунт и перечитывается файл; `not_found` и одинаково пустые поиски не
доказывают, что отправка не произойдёт позже. Даже точное совпадение нужно зафиксировать в
устойчивом журнале прежде, чем подтверждать или удалять элемент очереди. Ниже описан
экспериментальный Windows-адаптер с кооперативной блокировкой; он ещё не проверен в реальном
приложении и не обеспечивает защиту от совместного отката или потери данных.

Google [описывает повтор с предварительно выданным ID](https://developers.google.com/workspace/drive/api/guides/manage-uploads#use_a_pre-generated_id_to_upload_files):
успешный предыдущий запрос с тем же ID даёт `409`, а не дублирует файл. Это не делает безопасным
повтор с новым ID, не подтверждает совпадение содержимого и не устраняет необходимость журнала.
Яндекс [документирует двухэтапную загрузку и `202`](https://yandex.com/dev/disk-api/doc/en/reference/upload);
атомарность конкурирующих загрузок на один путь и восстановление после позднего ответа пока не
проверены. Транспорт автоматически не повторяет запросы ни для одного диска. Внутри одного
экземпляра незавершённый fetch удерживает слот даже после таймаута; другая вкладка или процесс
этим не блокируются. Проверки с двумя тестовыми ПК используют вымышленное облако и не доказывают
поведение реального сервиса.

Облачное содержимое считается недоверенным: проверяются размер, схема, ссылки, порядок версий
и целостность; до подтверждения оно не применяется и не исполняется как код.

### Ограниченная проверка истории снимков

Текущий прототип `history.js` строит не произвольный граф слияний, а дерево с одним родителем
у каждой версии. Отпечаток SHA-256 рассчитывается по каноническому зашифрованному конверту;
ссылка на него находится внутри аутентифицированного AES-GCM содержимого дочерней версии.
Смена местами полей внешнего JSON не меняет отпечаток. Для проверки требуется независимо
сохранённый отпечаток корня и список ранее известных версий: повторно зашифрованный файл с
тем же ID, потерянная известная версия или неподходящий родитель приводят к отказу.

Эта проверка доказывает только согласованность **переданного** набора с указанными отметками и
то, что конверты расшифрованы общим ключом. Поставщик может скрыть ещё неизвестную ветку или
вернуть старый неполный список; сам прототип полноту выдачи и свежесть не доказывает. Чтобы
обнаруживать откат уже виденных версий, отметки должны постоянно и надёжно сохраняться отдельно
от облака; такого хранилища пока нет. Нельзя принимать отметку корня из того же непроверенного
облачного списка за доверенную. Любой обладатель ключа данных может создавать новые версии.

Общий предок дерева **не означает**, что все поля одного снимка были приняты другим устройством.
Формат версии 1 не содержит меток удаления, а экспериментальная версия 2 содержит их только
для календаря и не поддерживается прежним читателем. Ни одна версия не представляет частичное
принятие, поэлементное происхождение, разрешение конфликтов или объединение двух родителей;
нельзя публиковать через неё результаты частичного слияния. Формат не проверяет все бизнес-схемы,
ссылки и идентичность сущностей, не
создаёт резервные копии и не применяется к приложению. При первом подключении или неподтверждённой
истории по-прежнему требуется отдельное сравнение. Экспериментальный предел — 128 версий и
64 Ми символов зашифрованных данных в одном наборе; усечение запрещено, стратегия длительной
истории и контрольные точки ещё не разработаны.

### Экспериментальные создание и удаление календарных записей

Модель не считает удалением ни пустой ответ диска, ни отсутствие записи в старой версии 1.
Для новой версии 2 вызывающий код должен отдельно передать точный список удалённых sync-ID и
подтвердить действие. Проверка требует, чтобы каждое удаление действительно происходило в
переходе от непосредственного родителя, а незаявленных удалений на этом переходе не было.
Зашифрованная метка подтверждает целостность сообщения **обладателя общего ключа**, но не то,
какой человек выбрал удаление или подтвердил его в интерфейсе. В версии 1 отсутствие не
превращается в метку задним числом. После метки тот же ID не допускается в потомках; отдельный
протокол восстановления или отмены удаления ещё не разработан. Другая ветка дерева может
содержать запись, поэтому её сохранение и конфликт нельзя игнорировать.

Предварительное создание проверяет, что ID отсутствовал у общего предка и на локальном пути,
появился только на удалённой линии и не исчезал без объяснения. Любая дополнительная известная
вершина блокирует решение. В копию добавляется только целиком выбранная ручная запись с новым
локальным ID, а существующий локальный порядок и другие сведения сохраняются. Проверяются
бизнес-значения, нормализатор, известные зависимости и обратный экспорт; невыбранные облачные
изменения не копируются. Проверка зависимостей не является полной валидацией всех разделов.

Предварительное удаление требует явного выбора и **дополнительного** подтверждения на этом ПК,
подходящей метки и отсутствия локальных правок записи и перестановки прежних записей с общего
предка, в том числе правок с последующим откатом. Простое исчезновение на любом этапе блокирует
кандидат. Если до удаления запись менялась на другом ПК, модель указывает последнюю версию для
просмотра, но не принимает её автоматически. Ручная запись не должна переходить в клановую
или обратно без отдельной проверки идентичности. Для клановых событий ни создание, ни удаление
этой моделью не предлагаются: необходимо сопоставить `guild-<eventId>` с актуальным ответом
сайта, не отправляя голос повторно. Автоматическое восстановление одного и того же ID после
метки, разрешение конфликтов и согласование нескольких известных веток не реализованы.

Проверяются только **переданные** версии: заявленный список всех ранее известных отметок,
включая корень и локальную версию, должен быть независимо сохранён и передан вызывающей
стороной. Пропущенная известная отметка обнаруживается, только если она есть в этом списке;
неизвестную скрытую ветку, общий откат списка и файла или подмену доверенного якоря модель не
обнаружит. Список, ключи и файлы для настоящего приложения пока не сохраняются. Результат
`prepared` — не разрешение применять или отправлять данные. Кандидат в памяти может содержать
контакты и пароли и не должен попадать в облако или журнал.

В тестах моделируются сбои, когда новое состояние и отметка истории оказываются сохранены
по отдельности: повторный просмотр с несовпадающей парой останавливается; согласованная
модельная пара не повторяет то же создание или удаление. Эти тесты не записывают файлы и не
доказывают атомарность, восстановление реального устройства или защиту от скрытых веток. Между
просмотром и записью могут поменяться и **непубличные** данные, которых сравнение не видит:
старый кандидат способен содержать устаревший пароль. Перед интеграцией нужны проверенная копия
всех затронутых хранилищ, независимое устойчивое хранение якорей, точная проверка полного
локального источника и известного исхода записи, защита от конкурирующих изменений и безопасное
восстановление после каждой стадии. Существующие локальные средства backup/witness сами по себе
этой общей транзакции не предоставляют.

### Частичный выбор и последующая отправка

Выбор нескольких строк нельзя реализовать как «заменить весь локальный снимок выбранными
значениями, объявить всю облачную версию принятой и потом загрузить локальный снимок поверх
неё». Это потеряет остальные входящие изменения. Нужна история принятой базы и происхождения
правок на уровне, достаточном для частичного выбора (записи/поля и зависимости); неизвестное,
невыбранное и подтверждённое удаление различаются. Точный формат истории и правила выбора
зависимых записей ещё предстоит разработать и проверить. Новая исходящая версия не должна
утверждать, что пользователь принял или удалил невыбранные изменения; существующие версии и
ожидающие решения сохраняются. Одно лишь создание неизменяемого полного снимка не доказывает
корректность частичного слияния.

Ограниченный планировщик одной записи держит копии входов только в памяти и возвращает
`applied` и `pending`, но сам по себе не сохраняет историю их происхождения. Новый отдельный
экспериментальный слой `fieldProvenanceReview.js` использует общий предок проверенного дерева,
ведёт последовательность выбранных путей и их исходных версий и строит поэлементную базу.
Само предложение ничего не принимает: следующий снимок должен быть потомком просмотренного
локального снимка и **целиком** совпасть с предложением, а переданная наблюдаемая облачная
версия должна остаться прежней. Предложение также блокируется, если проверенная история уже
содержит другую известную ветвь-потомка просмотренной облачной версии. Это осторожный отказ,
а не определение актуальной версии: неизвестную ветвь он обнаружить не может. Проверка
известных зависимостей проводится до предложения.
Это позволяет в тестах сохранить невыбранное поле и позже выявить конфликт с правкой уже
выбранного. Пустой выбор, отсутствующая ссылка, неподтверждённое исчезновение поля или выбранный
конфликт не продвигают учёт. В последовательности хранится не более 10 000 решений.

Для проверки перезапуска добавлен отдельный **модельный** checkpoint одной записи. Внутри
зашифрованного AES-GCM конверта — ID набора и устройства, отметки исходных/текущих версий и
последовательность выбранных путей с источниками, но не сами значения полей и не локальные
секреты. Его можно построить только из созданной моделью проверки, а не из произвольной базы.
При восстановлении база заново строится из общего предка и исходных версий; проверяются порядок
источников, идентичность записи, предки, известные потомки и соответствие полной публичной
проекции актуальным локальным данным. Для календаря восстановленная модель снова проходит
бизнес-проверки кандидата. Прототип ограничивает checkpoint двумя МиБ, 10 000 решениями,
длиной пути 64 и отдельной части пути 256 символами; переполнение блокируется, а не усекается.

Восстановление требует **независимо доверенных** ID набора/устройства, отпечатка checkpoint,
корня, локальной и облачной версий и списка всех ранее известных отпечатков. Они не должны
браться из восстанавливаемого файла или непроверенного облака. Шифрование требует независимого
случайного ключа устройства, отличного от общего ключа данных. Кодек не генерирует и не хранит
такой ключ, отметки или файлы, не защищает от одновременного отката checkpoint **и его якобы
доверенной отметки** и не подтверждает происхождение выбора при подмене доверенного якоря.
Потеря нужной исходной версии или ключа блокирует восстановление; молча считать все поля
принятыми или выбрасывать ожидающие нельзя. Доступ к ключу не доказывает волю пользователя.

Эта модель пока **не подключена к приложению**: нет защищённого постоянного якоря, транзакционной
связи со state/историей и проверенной защиты от сбоев/отката. Даже точное совпадение в модели не
подтверждает, что desktop-файл действительно сохранён или что облако не скрыло новые версии.
Понадобятся независимое устойчивое хранение, резервное копирование, согласование ключей и
восстановление после прерывания транзакции; профили и vault пока не входят в общую транзакцию.
Эксперимент останавливается, если новая облачная версия приходит при неразобранных входящих или
если ожидающее поле изменено локально — даже до совпадения с облаком. Разрешение таких случаев
ещё не реализовано. Полноценное создание, удаление и архивация записей требуют отдельных правил,
как и выбор между зависимыми записями; эксперимент для ручного календаря описан выше и ничего
не применяет. Выгружать этот частный формат как общую историю устройства нельзя.
Служебный маркер проверенного объекта не делает недоверенный корень доверенным. Даже пустой
`pending`, `status: planned` или `status: proposed` не разрешают импорт или публикацию. Снимки,
поля и пути нельзя автоматически передавать в журнал.

### Модель намерения для одной локальной записи

Изолированный `plannerCommitJournal.js` экспериментально связывает частичный выбор полей одной
**существующей** календарной записи с точными строками полного локального JSON и checkpoint до и
после выбора. В отдельном AES-GCM конверте находятся отпечатки этих строк, ID операции и отметки
проверенной истории, но не значения полей или пароли. Отпечаток конверта и отдельные случайные
ключи намерения и checkpoint должны предоставляться из независимого защищённого источника;
такого источника и постоянного хранения ключей ещё нет. Ключи также должны быть независимы от
общего ключа набора — сам модуль это проверить не может. Кандидат, наоборот, содержит полное
локальное состояние с личными сведениями: его нельзя передавать в облако или писать в журнал.

Наблюдение сравнивает прочитанные строки с зашифрованными отпечатками и различает прежнюю пару,
новую пару, два порядка частичной записи и неопознанное состояние. Так обнаруживается и изменение
непубличной части, например пароля, которого публичное сравнение не видит. При появлении другой
известной ветки она отдельно помечается. **Все** результаты требуют ручной проверки: совпадение
не доказывает успешную физическую запись, момент сбоя или отсутствие отката. Неизвестные ветки,
совместный откат файла и его «доверенной» отметки, подмена якоря и устаревший ответ облака этим
не обнаруживаются. Намерение не содержит копий данных для восстановления и не заменяет backup.

Эксперимент принимает также форматированный JSON: после синтаксической проверки выполняется
ограниченный проход по лексемам, который запрещает повторные имена ключей, включая записанные
через `\u`, и числа, меняющие десятичное значение при преобразовании в JavaScript `Number`.
Невыбранные данные остаются в кандидате, а сравнение при наблюдении по-прежнему требует именно
исходную строку, даже если отличались только пробелы. Лимиты — 32 МиБ UTF-8, глубина 64 и 500 000
лексических узлов; слишком длинные или неоднозначные числа блокируются. Такой разбор — частный
эксперимент, не доказательство совместимости всех desktop-файлов.

Отдельное хранилище секретов ОС, профили и журналы в этой строке отсутствуют и не защищены.
Файл с `secretsInVault` сейчас блокируется. Подготовленный JSON также не совместим напрямую с
native-процедурой, меняющей `savedAt` и сериализующей данные самостоятельно. Настоящее чтение,
запись и восстановление в Tauri/Windows не проверены.

Для испытаний один зашифрованный конверт можно отдельно положить в переданный `Storage`, не
заменяя занятый слот. Независимый pin должен быть сохранён **до** такой публикации; функция не
может это проверить. После неоднозначной ошибки записи в том же JS-контексте повтор запрещён,
но другая вкладка, другой объект хранилища и другой процесс не заблокированы. Чтение требует
отдельно переданного pin; очистка или исправление слота не реализованы. Это не межпроцессный CAS,
не fsync и не восстановление. Код не подключён к приложению, облаку, реальному `state.json`, vault
или интерфейсу, а создание и удаление записей не поддерживает.

`tests/cloudSyncPlannerCommitJournal.test.js` проверяет оба порядка частичного сбоя, приватные и
невыбранные поля, подмену, неизвестную ветку, отсутствие слепого повтора, форматированный JSON,
повторные ключи и отдельное чтение вымышленных временных файлов новым процессом Linux. Также модель
проверена в Chromium с WebCrypto и настоящим `localStorage` после перезагрузки. Это не испытание
собранного Tauri, Windows, падения питания, fsync, конкурентных процессов или защищённого якоря.

### Экспериментальная координация браузерных вкладок

`browserCoordination.js` отдельно пробует `navigator.locks` с одним фиксированным именем на всё
локальное состояние и неблокирующей эксклюзивной попыткой (`ifAvailable`). Занятый ресурс не
запускает callback; при отсутствии API нет небезопасного fallback. Callback должен **после**
получения блокировки заново прочитать данные и сам дождаться всех своих действий. Его возвращённое
значение не выводится. Даже `completed_for_test` — не подтверждение записи, backup или импорта.
При ошибке после входа исход считается неизвестным, а повтор в том же экземпляре модуля блокируется.

Это работает только для участвующих вкладок/воркеров одного origin и browser storage partition.
Сам координатор после перезагрузки не знает о неизвестном результате; отдельная модель отметки
рассматривается ниже, но независимого надёжного хранилища и восстановления пока нет. Обычное
сохранение приложения и native-команды не используют этот lock, другие процессы и внешние редакторы
не блокируются. Принудительный `steal` способен отнять lock, а начатый callback прежнего владельца
может продолжиться и после отказа promise — wrapper не может безопасно его остановить. По этим
причинам механизм **не подключён** к реальной записи.

На Chromium с настоящими Web Locks и `localStorage` проверены две вкладки, отказ второй при занятом
lock, повторное чтение после освобождения, закрытие вкладки-владельца и остановка повторов после
неизвестного исхода в том же модуле. Отдельно подтверждено, что после `steal` прежний callback
может продолжить выполняться. Многопроцессный Tauri, разные браузерные профили, Windows, надёжное
хранение карантина и падение питания не проверены.

### Экспериментальная отметка незавершённой операции

`persistentQuarantine.js` пробует хранить в переданном `Storage` отдельную отметку `ready` или
`pending` с HMAC-SHA-256. Проверяемые marker ID, ID устройства и набора, а также неизвлекаемый
HMAC-ключ должны предоставляться **независимо** от самой отметки. Модуль их не создаёт, не
сохраняет и не восстанавливает. `prepareFreshQuarantineMarker` только готовит начальную строку в
памяти: это не проверка нового устройства и не разрешение сбросить повреждённую отметку.
Интерфейса сброса или восстановления нет. Отметка не содержит данных callback или ключа, но её ID
и фаза видимы в открытом виде; это аутентификация, а не шифрование.

Под кооперативным Web Lock модель перечитывает и проверяет отметку, затем записывает `pending`
и сравнивает точную строку до входа в callback. Ошибка callback оставляет `pending`; другая вкладка
и новая загрузка с теми же доверенными ключом и pin тогда не запускают callback. Изменённую,
неверно подписанную, неоднозначную или отсутствующую отметку модель не перезаписывает. После
успешного callback возвращается `ready`, но только если слот по-прежнему содержит ожидаемую
`pending`. Неизвестная ошибка записи отметки блокирует дальнейшие попытки в текущем JS-модуле.
Если запись `ready` прошла, а её подтверждение потерялось, после перезагрузки может читаться
`ready`: callback завершился раньше, однако это не доказывает физической сохранности его данных.

Это только модель протокола, **не готовый устойчивый карантин**. Web Storage не подтверждает fsync,
а повторное чтение — не гарантия сохранения после сбоя питания. Подписанную старую `ready` можно
откатить: HMAC подтверждает целостность, но не свежесть. Нет независимого монотонного якоря,
подтверждённого отдельного защищённого хранилища, безопасной инициализации и восстановления.
Проверка не охватывает код, который обращается к очереди напрямую, другие browser partition,
обычную запись приложения или native-процессы. При `steal` модель не снимает `pending`, если уже
узнала о потере lock; гонка до получения уведомления и продолжающийся callback остаются. Доверенный
callback обязан сам удостовериться в своих действиях; его успешное завершение не является backup.
К настоящей очереди, vault, сети и приложению модель не подключена.

Тесты проверяют подмену, потерю ответа, сбои до/после записи, блокировку после перезагрузки и
демонстрируют нераспознаваемый откат старой подписи. В Chromium с вымышленным ключом проверены
WebCrypto, две вкладки, перезагрузка, закрытие владельца и поздний callback после `steal`. Это не
проверка реального защищённого ключа, долговечности диска или Tauri/Windows.

### Отключённая модель нативной межпроцессной блокировки

`src-tauri/tests/support/sync_native_lock.rs` — только тестовый код: приложение и его команды его
не используют. На Linux он пробует неблокирующий advisory `flock` через `File::try_lock` из Rust
1.89+, с одним пустым постоянным файлом на каталог состояния. Каталог канонизируется; отказ блокировки
не заменяется продолжением без неё. Символическая ссылка, несколько жёстких ссылок, непустой файл и
уже изменившийся inode отклоняются. После освобождения lock-файл намеренно не удаляется.

В Linux на временных файлах проверены два независимых процесса, обычный выход и принудительное
завершение владельца, повторное получение блокировки и проверки ссылок. Тест также показывает,
что постороннее удаление lock-файла позволяет другому процессу создать новый inode и получить
вторую блокировку: проверка inode обнаруживает уже случившуюся подмену, но не устраняет гонку после
проверки. Файловые и сетевые системы, где lock не обеспечивает нужную семантику, не проверены.
Все реальные писатели, включая state, vault и factory reset, должны участвовать в будущем общем
протоколе. На Windows и других платформах этот тестовый прототип намеренно возвращает `Unsupported`;
Windows-lock, интеграция Tauri, fsync и падение питания не проверены.

Перед применением ещё раз проверяются актуальность диска, ссылки и бизнес-ограничения; нужные
зависимости предлагаются пользователю или применение блокируется. Только после локальной
резервной копии и атомарной, подтверждённой записи изменения считаются применёнными. Если диск
или локальные данные успели измениться после просмотра, нужен новый просмотр. Эти гарантии
пока не реализованы.

### Журнал реальной функции

В рабочем приложении понадобится отдельный устойчивый источник `logHub`, а не подмена журнала
скриптов. Для ручных и автоматических действий фиксировать время, тип, провайдера, идентификатор
операции, количество/разделы выбранных изменений и результат: подтверждённый успех, ошибка или
неизвестный исход с ожидающей проверкой. Успех отправки записывать лишь после подтверждения
версии на диске, успех обновления — после подтверждённого локального сохранения. Повтор операции
не должен создавать ложные дубликаты; сбой журнала необходимо сообщать пользователю.

Не записывать значения паролей и контактов, ключи, OAuth-токены, cookies, подписанные ссылки,
локальные пути или сырые снимки. Перенос существующих важных журналов между ПК — отдельная
задача с собственной схемой, миграцией идентификаторов и разрешением конфликтов; новый журнал
синхронизации сам по себе этого не делает.

## Подключения

Для обоих дисков нужна регистрация OAuth-приложения у соответствующего провайдера и
пользовательское разрешение. Вход выполняется на стороне провайдера; пароль от диска не
вводится в Твиноферму и не запрашивается в чате. Для настольной авторизации Google описывает
системный браузер, локальный callback и PKCE [1](https://developers.google.com/identity/protocols/oauth2/native-app);
Яндекс также описывает обмен кода с PKCE [2](https://yandex.com/dev/id/doc/en/codes/code-url).
Точные настройки приложений, обновление токенов и условия публикации нужно проверить для
выбранных разрешений и обоих сервисов.

Выбран **прямой API**, а не синхронизируемые папки установленных дисковых клиентов. Регистрацию
делает владелец приложения Твинофермы, а не каждый пользователь; на обоих ПК пользователю
нужно будет войти в один и тот же личный аккаунт соответствующего диска и разрешить доступ.
Создание регистраций здесь не выполнялось. Планируемые настройки для владельца приложения:

- Google: проект в Google Cloud, включённый Drive API, экран согласия и OAuth-клиент типа
  Desktop app. Предусмотрен узкий scope `drive.file`, а не доступ ко всему диску. Для личных
  аккаунтов и дальнейшего распространения — External, сначала Testing с добавленными тестовыми
  аккаунтами. В этом режиме доступ с Drive scope и refresh token обычно истекают через семь дней
  ([справка Google](https://support.google.com/cloud/answer/15549945)). Правила публикации и
  проверки нужно уточнить перед выпуском. Модель поиска/создания папки подготовлена, но её
  надёжная привязка и обнаружение на втором реальном ПК ещё не проверены.
- Яндекс: для работы с дисками **других пользователей** выбирать тип «Для авторизации
  пользователей», не «Для доступа к API или отладки»: [Яндекс](https://yandex.ru/dev/id/doc/ru/register-client)
  указывает, что второй тип работает только с данными разработчика, а тип нельзя изменить после
  регистрации. Предполагаемое разрешение — `cloud_api:disk.app_folder`, без доступа ко всему
  диску. Для предварительной регистрации выбрана платформа «Веб-сервисы» и тестовый redirect
  `http://127.0.0.1:37181/oauth/cloud/callback`; это локальный приёмник на ПК пользователя, не
  интернет-сервер. Именно такой порт по умолчанию использует `oauthPkce.js` в диагностике.
  Возможность регистрации и работа с этим адресом ещё не проверены на Яндексе; при занятости
  порта попытка должна остановиться, а не переключиться на незарегистрированный адрес. По
  [описанию Яндекса](https://yandex.com/dev/disk-api/doc/en/concepts/app-folders) папка приложения
  на личном диске создаётся при первом подходящем запросе и доступна через `app:/`. Безопасное
  обновление токена и совместимость выбранного типа клиента ещё требуют реальной проверки.

Похожие названия разрешений Яндекса не следует автоматически считать одним правом:
«Доступ к Яндекс.Диску для приложений» встречается как `yadisk:disk` в
[примере регистрации](https://marketplace.1c-bitrix.ru/solutions/apikit.yadisk/), а «Доступ к
папке приложения на Диске» — как `cloud_api:disk.app_folder` в
[документации Диска](https://yandex.com/dev/disk-api/doc/en/concepts/quickstart). В текущем
прототипе запрашивается только второе. Точный объём `yadisk:disk` и необходимость его
автоматического добавления в конкретной форме не установлены; не запрашивать его без проверки.

Идентификаторы клиента не являются паролями, однако секреты приложения, токены, коды
авторизации и пароль диска нельзя помещать в чат, демо, исходники или журналы. Одной регистрации
недостаточно для готовой синхронизации: сначала необходимо завершить локальное хранение,
применение, журнал и испытания на настоящих устройствах.

### Экспериментальная разовая проверка регистрации

В настоящем приложении **Настройки → Синхронизация → Синхронизация между ПК** находится
свёрнутая форма диагностики. Она принимает только публичный Client ID локально и не сохраняет
его в настройках. Нельзя вводить пароль, Client Secret или полученный код. Через системный
браузер сценарий запрашивает разрешение, принимает callback с PKCE, один раз обменивает код и
запрашивает метку выбранного аккаунта. Google в диагностике не запрашивает offline-доступ;
Яндекс всё же может вернуть refresh token. Access/refresh токены не сохраняются и не
используются для чтения или записи диска. Сервис может сохранить разрешение даже после отмены
или ошибки; при необходимости пользователь сам отзывает доступ в аккаунте. Отзыв доступа
приложения может отключить другие устройства и токены той же регистрации; избирательный отзыв
тестового обычного токена Яндекса не обещается. Отмена JS не гарантирует отмену уже отправленного
POST; неоднозначный результат не повторяется автоматически.

Для диагностики нативная команда `cloud_oauth_network` использует операции обмена **кода** и
предпросмотра аккаунта; отдельно добавлен не подключённый к UI экспериментальный refresh Google.
URL и заголовки задаются в Rust. Доступны только `oauth2.googleapis.com/token`,
`oauth.yandex.com/token`, Google Drive `about.get` и Яндекс ID `/info`; произвольных адресов,
refresh Яндекса, скачивания и записи файлов нет. Главному окну выдаётся только JSON успешного
ответа, объём ответа ограничен 64 КиБ; JS-проверка идентичности — 8 КиБ. Клиент использует TLS/rustls,
без редиректов, системного proxy, сжатия и автоматических повторов; время подключения ограничено
10 секундами, общий запрос — 25 секундами. При необходимости системного proxy проверка может
не работать. Одновременные запросы в одном процессе запрещены. Токены не входят в URL и ошибки;
их строки и ответ, как и метку аккаунта, нельзя журналировать. Вредоносный код главного окна
или процесс с доступом к памяти не сдерживается этой политикой. Сброс строки в JS не гарантирует
стирания её копий из памяти. Tauri IPC, системное хранилище сертификатов и сборка Windows
требуют отдельной проверки.

Результат показывает только полученную метку или её отсутствие; `request_bound` Яндекса —
свидетельство о параметрах нашей попытки, не проверка реальных разрешений. `reported` тоже не
проверяет доступ к файлам. Отдельный экспериментальный первый вход может сохранить привязку
аккаунта локально; управления ключами, работающей очереди, автосинхронизации, загрузки или
применения нет. Тесты сценария используют фальшивые ответы и IPC; Rust-политика и сетевой
исполнитель проверены в изоляции с поддельными Tauri/HTTP типами, не настоящим `reqwest` или
Windows. Пользователь сообщил о регистрации обоих приложений, но параметры и фактическая
работа не подтверждены.

### Подготовительный callback и PKCE: ещё не подключение

`oauthPkce.js` генерирует независимые значения verifier, `state` и приватный handle через
переданный Web Crypto/CSPRNG, использует S256 и фиксированные HTTPS-адреса Google и Яндекса,
а также только предполагаемые разрешения `drive.file` и `cloud_api:disk.app_folder`.
Системный браузер и вызовы desktop-команд передаются модулю явно; сам он их не подключает.
После получения кода можно сформировать одноразовый POST-запрос для **переданного доверенного**
транспорта. Экспериментальные диагностика и первый вход соединяют эти части с ограниченным
native HTTPS; надёжность хранения в настоящем приложении ещё не подтверждена. Запрос содержит код и verifier и не должен
попадать в журналы. После неоднозначного результата обмен автоматически не повторяется.
Никакой успех входа до проверки ответа, разрешений и аккаунта не утверждается.

Native-приёмник временно слушает только `127.0.0.1` и только путь `/oauth/cloud/callback`.
Он ограничивает HTTP-запрос, проверяет Host, формат и повторяющиеся параметры, сравнивает
случайный `state` и при наличии проверяет `iss`; код выдаётся только владельцу отдельного
случайного handle и не более одного раза. Ответ в браузере не содержит код и означает лишь
получение ответа, а не успешный вход в диск. Статический скрипт с ограничением CSP пытается
убрать параметры callback из текущей адресной строки и записи истории; это не гарантирует,
что браузер, расширения или сторонние журналы не сохранили прежний адрес. Отмена, ошибка или пятиминутный срок завершают
попытку; параллельно допускается одна попытка на процесс. При потере IPC-ответа отмена может
быть не подтверждена, поэтому listener также закрывается по сроку. JavaScript прекращает
использовать данные при отмене/истечении и учитывает сдвиг часов назад; таймер не является
гарантией немедленного стирания памяти при остановленном процессе. Rust и JavaScript не
гарантируют стирания всех копий строк. Приёмник проверяет формат `state` и handle, **но не
может доказать случайность**, которую обязан обеспечивать доверенный вызывающий код.

Google использует динамический свободный порт loopback. Для Яндекса в текущем прототипе
предварительно выбран фиксированный порт `37181` и redirect
`http://127.0.0.1:37181/oauth/cloud/callback`; при явной замене порта вызывающий код обязан
использовать заранее зарегистрированный у Яндекса адрес с тем же хостом, портом и путём. Иначе
[Яндекс может проигнорировать переданный redirect](https://yandex.ru/dev/id/doc/en/register-auth)
и использовать зарегистрированный по умолчанию. Возможность такой регистрации и поведения
конкретного клиента ещё нужно проверить. Занятый порт не заменяется другим молча.
Пользователь сообщил о регистрации Яндекса, но её параметры не проверены; регистрация Google
не подтверждена. Клиентский секрет в приложение не помещается. Обновление токенов Яндекса и
условия конкретного типа клиента требуют отдельной проверки.

Метка `main` ограничивает вызовы других окон, но не защищает от вредоносного кода в самом
главном WebView. Локальный процесс может занимать порт или мешать работе, а процесс с доступом
к памяти приложения или браузеру может повлиять на попытку. `state` виден в адресе браузера;
адрес callback и содержимое IPC тоже нельзя логировать. Открывающий браузер API, CSP и среду
Tauri, фактические разрешения и идентичность выбранного аккаунта ещё нужно проверить.
Диагностика предлагается только как эксперимент и не создаёт настоящего подключения.

Проверены тестовый вектор RFC 7636, ошибки и гонки с поддельным IPC и транспортом; локальный
Rust-приёмник и сериализация отдельно испытаны в изолированном Linux-пространстве имён с
приватным loopback. Мост JS/Rust с поддельной Tauri-обёрткой прошёл для обоих провайдеров;
изолированный Clippy 1.88 не нашёл предупреждений в этой модели. Это не тест реального Tauri,
Windows, актуального CI-toolchain, системного браузера, зарегистрированных приложений, CORS
или настоящих OAuth-серверов и не аудит безопасности.

### Экспериментальный обмен и обновление токена

`oauthTokenTransport.js` отделён от GET-транспорта дисков. Обмен кода используется экраном
разовой диагностики и экспериментального первого входа с локальным хранилищем; автоматическая
синхронизация не подключена.
Его `fetchImpl` необходимо передать явно и полностью доверять ему: именно он обязан соблюдать
TLS, `redirect: 'error'`, запрет cookies и остальные параметры. Проверка конечного URL в
ответе не отменит утечку, если недоверенный адаптер уже перенаправил запрос. Для диагностики
используется ограниченный native-мост выше; настоящие Tauri и серверы ещё не проверены,
сетевые тесты используют только поддельный `fetch` или фальшивый HTTP-слой.

Транспорт принимает POST только на фиксированный OAuth endpoint выбранного провайдера и
сверяет точный состав заголовков и формы. Код, verifier и refresh token находятся в `body`
**объекта запроса** и в памяти `fetchImpl`: этот объект, его строки, исходные ошибки и ответы
нельзя логировать или сохранять в обычное состояние, журнал и localStorage. Снимок параметров
делается до ожидания ответа. Ограничены размер и тип JSON, время ожидания и отдельные поля;
отклоняются повторные, неожиданные или несовместимые поля, неожиданные права, редирект,
неподходящий статус и истёкший срок. Консервативный разбор может отклонить будущий корректный
ответ, если провайдер добавит поле: совместимость потребуется проверить, а не ослаблять молча.

Результат содержит только сводку и одноразовый метод `takeSecrets()`. Саму сводку можно
сериализовать без токенов, но она не является доказательством входа или идентичности аккаунта.
Время действия access/refresh вычисляется консервативно от начала запроса; выдача из результата
ограничена также 60 секундами, истечением токена и сдвигом часов назад. `discard()` отбрасывает
ссылку раньше. Таймер при остановленном процессе может сработать позже, а JavaScript и поток
не гарантируют уничтожения всех строк и копий в памяти. Передача через `takeSecrets()` и
дальнейшее хранение/использование — ответственность доверенного вызывающего кода.

При отсутствующем `scope` сводка обычно сообщает `unverified`. Исключение в эксперименте:
[Яндекс документирует](https://yandex.com/dev/id/doc/en/codes/code-url#token-response), что
поле необязательно и возвращается, когда выдан меньший набор прав. Для **исходного объекта**
запроса, созданного нашей одноразовой PKCE-попыткой Яндекса с единственным обязательным
`cloud_api:disk.app_folder` и без `optional_scope`, сводка сообщает `request_bound`. Свидетельство
используется один раз и не переносится в копию запроса. Для произвольного запроса, другого
провайдера или повтора остаётся `unverified`; явно присланный неизвестный scope отклоняется.
Это предполагает доверенный браузер, сервер и `fetch`, корректную работу PKCE и описанную
семантику ответа. **Ни одна из этих меток не является технической блокировкой**: `takeSecrets()`
всё равно доступен. `request_bound` и `reported` не доказывают настройки данной регистрации,
реальный доступ к Диску или личность пользователя. Реальные провайдеры не проверены;
надёжной связки с защищённым хранилищем и приложением пока нет.

Одна попытка на экземпляр не повторяется даже при потере сети, таймауте или неподходящем
ответе. Таймаут возвращается и при зависшем адаптере; отмена сети/потока предпринимается,
но не гарантируется. Провайдер мог уже использовать код или сменить refresh token: такой
результат неизвестен, а не безопасен для повторной отправки. Новый экземпляр, другой процесс
или перезапуск этот запрет обходят; постоянный карантин и согласование ротации ещё нужны.
При необходимости потребуется новый вход без удаления локальных или облачных данных.

Только для Google предусмотрен подготовительный запрос обновления без `client_secret`, как
описано в [документации desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app).
Если Google не прислал новый refresh token, сам транспорт **не** подставляет старый; отдельная
экспериментальная модель ниже рассматривает сохранение старого при дополнительных условиях.
Для [обновления Яндекса](https://yandex.com/dev/id/doc/en/tokens/refresh-client) документация
указывает пароль приложения; встраивать его в клиент нельзя. Поэтому refresh Яндекса в этой
заготовке заблокирован до проверки регистрации и выбора безопасного решения. Это не означает,
что автоматическое продление на Яндексе уже работает.

#### Экспериментальная модель привязки аккаунта

`providers/oauthAccountIdentity.js` содержит проверки ID и отдельные readers предпросмотра.
Предпросмотр используется разовой диагностикой и экспериментальным первым входом; настоящие
аккаунты и сервисы ещё не проверены. Обычная проверка Google `about.get` с `drive.file` запрашивает только
[`user.permissionId`](https://developers.google.com/workspace/drive/api/reference/rest/v3/User),
не адрес почты. Google описывает ID как идентификатор пользователя в ресурсах Permission;
стабильность при всех изменениях аккаунта и совместимость ограниченного формата ещё не проверены.
Отдельный reader предпросмотра запрашивает `permissionId` и `emailAddress` **из одного ответа**.
По документации email может отсутствовать; его не заменяют догадкой или непрозрачным ID. Ответ
Google не подтверждает `client_id`.

Яндекс [`/info`](https://yandex.com/dev/id/doc/en/user-information) может принимать токен другого
сервиса без дополнительных прав ID: модель сравнивает возвращённый `client_id` с ожидаемым.
Обычная проверка выдаёт только `psuid`, а отдельный reader предпросмотра — `psuid` и `login`,
если он получен. Логин не называют почтой и не выводят `id`. По документации `psuid` формируется
из пары пользователь/приложение; при смене регистрации его нельзя без проверки считать тем же
самым. Дополнительные, повторные или неожиданно оформленные поля блокируют ответ; это
консервативное ограничение, которое может потребовать пересмотра после реальных испытаний.
Оба новых reader возвращают `label: null` при отсутствующей метке; они не выполняют подключение.
Первое подключение и экспериментальный Windows-installer доступны в настройках, но настоящего
проверенного подключения или обновления refresh token Яндекса пока нет.

Токен передаётся только в заголовке, не в URL; фиксированный GET ограничивает время и размер,
не принимает redirect и скрывает подробности ошибок. Помимо таймера срок сверяется по
монотонным часам текущего контекста при принятии ответа; это не гарантирует точное поведение
при приостановке устройства. Внедрённый `fetch` должен быть доверенным: проверка URL ответа
не защитит, если он уже утёк токен или последовал перенаправлению. Отмена пытается остановить
запрос/поток, но некооперативная реализация может продолжать работу; её слот остаётся занятым
до завершения. ID, email/login и ответы — личные данные: их нельзя писать в журнал или
облачный файл. ID используется только для защищённого локального закрепления подключения;
email/login в такую запись не включаются. Метку можно передавать лишь доверенному UI для
подтверждения, а не включать в синхронизируемые контакты. Модель не сохраняет метку, но
переданный callback может удержать её в памяти; JavaScript не гарантирует стирания строк и
всех их копий.

Для показа `oauthAccountLabel.js` консервативно допускает только ограниченные ASCII-форматы
email Google и логина Яндекса: управляющие и невидимые символы, bidi-подстановки, HTML, слишком
длинные или неоднозначные значения отклоняются; другие корректные для провайдера форматы тоже
могут быть отклонены. Метка не исправляется и не нормализуется. Отдельное окно подтверждения показывает её
целиком как текст, не HTML, без многоточия; при длинной метке содержимое переносится и
прокручивается. Оно просит сравнить метку с аккаунтом, выбранным в системном браузере.
Окно подключено к экспериментальному первому входу. Метка сама по себе не подтверждает личность
и не защищает от подмены интерфейса, вредоносного кода или похожих имён. Ни одна проверка не
доказывает полный набор разрешений, согласие пользователя при первом входе, подлинность
сохранённого закрепления аккаунта или отсутствие его отката. CORS/CSP, системный браузер,
реальные серверы и среда Tauri/Windows ещё не проверены.

#### Экспериментальное первое подключение Google и Яндекса

`providers/oauthCredentialEnrollment.js` связывает уже полученный одноразовый ответ обмена,
предпросмотр и **явное подтверждение** через внедрённые доверенные callback. Первый вход в
настройках вызывает эту модель; отдельно сама модель не запускает браузер. Для Google
обязателен сообщённый ожидаемый `scope` и
новый refresh token; для Яндекса принимается также описанный выше `request_bound`, а refresh
не обязателен и не сохраняется. Ответ `unverified` не используется. Callback `previewAccount`
возвращает из одного ответа ID и проверенную метку; `confirmAccount` получает только метку,
без ID и токенов. При `label: null` модель возвращает `account_label_unavailable`, не вызывает
подтверждение и не устанавливает запись; неподходящий формат также блокирует операцию. После
согласия она повторно запрашивает и сравнивает **и ID, и точную метку**: при изменении или
исчезновении метки установка не начинается. Отказ, отмена, ошибка проверки или истечение срока
также останавливают запись. Метка не попадает в аргументы installer, credential-запись или
результат операции.

`providers/oauthYandexCredentialRecord.js` готовит только каноническую **открытую в памяти**
запись с access token и его сроком, привязанную к ID приложения и аккаунта. Сам кодек ничего не
шифрует и не сохраняет. Экспериментальный Windows-installer ниже подключён к интерфейсу, но
пока не подтвердил все описанные гарантии. Если токен истёк во время установки, возвращается
`installed_access_expired`: запись могла сохраниться, повторять установку автоматически нельзя.
После истечения потребуется новый вход; автоматическое продление Яндекса пока не разработано.
Тесты проверяют только поддельные IPC, ответы провайдера и installer; они не подтверждают вход
или доступ с реальной регистрацией.

Callback `ui/confirmCloudAccount.js` используется в экспериментальном первом входе.
Он требует нативный модальный `<dialog>.showModal()` и поддержку `:modal`; без них отказывает,
не подменяя окно обычным немодальным блоком. Начальный фокус на отмене, Escape и кнопка отмены
отказывают, `AbortSignal` закрывает окно и отклоняет ответ. Подтверждение требует отдельной
галочки и кнопки, неизменного содержимого, видимой неусечённой метки и открытого модального
окна; если метка прокручена за пределы видимой области, нужно вернуть её на экран. При смене
или удалении содержимого, скрытии метки, потере документа и ошибках подтверждение блокируется.
Одновременно допускается одно такое окно на документ. После завершения слушатели и окно
удаляются, метка очищается из DOM; исходные ошибки и метка не пишутся в журнал.

Само окно не запускает браузер и не получает токены; экспериментальный сценарий настроек
отдельно запускает вход и вызывает его для подтверждения. В демо кнопка примера передаёт только фиксированные вымышленные email
Google или логин Яндекса; при перерисовке или уничтожении макета пример отменяется. Нажатия,
даже с нативной модальностью, не являются доказательством, что человек действительно сравнил
аккаунты: вредоносный код того же окна может управлять UI и событиями. Нельзя считать `isTrusted`
или похожие имена защитой от подмены. Проверены модальность, фокус, клавиатура, адаптивность и
axe в Chromium, включая встроенное демо; реальное Tauri/Windows, экранные читалки и системный
браузер ещё требуют испытаний. Обычный reader ID остаётся отдельным для ротации.
Секреты и метка удерживаются в памяти, но JS не обещает физического стирания. `reported` scope
по-прежнему не доказывает фактически выданные права. Неиспользованный после отказа токен мог
уже быть выдан провайдером; автоматический отзыв не выполняется и его безопасное поведение
нужно отдельно решить.

После подтверждения готовится запись с новыми случайными ID, но её установка поручается
внедрённому `installer`. Его строгий контракт — устойчиво связать защищённый pin и секретную
запись, не заменяя существующее подключение; проверка чтением не доказывает устойчивости или
атомарности. Ниже описан экспериментальный Windows-кандидат, свойства которого ещё не доказаны.
Отсутствие записи не доказывает, что подключение никогда не существовало.
Отмена до начала записи останавливает сценарий; после начала нельзя обещать отмену. Таймаут,
ошибка или неподтверждённое перечитывание означают неизвестный исход, и тот же экземпляр не
повторяет установку. Неотвечающий backend может завершить её позже; доказанный устойчивый
карантин для другого процесса/перезапуска ещё нужен. Ни локальные данные, ни файлы диска этот прототип не
сравнивает и не меняет: перед реальной первой синхронизацией остаются проверка облака,
резервная копия и выбор пользователем.

#### Экспериментальный локальный backend Windows

В `cloud_credential_store.rs`, `cloud_credential_records.rs`, `cloud_credential_service.rs` и
`commands/cloud_credentials.rs` подготовлен кандидат на защищённое хранение OAuth. Команды IPC
зарегистрированы только для главного окна, на других ОС возвращают ошибку. Сценарий
`nativeOAuthEnrollment.js` соединяет локальную предварительную проверку, PKCE, предпросмотр,
подтверждение аккаунта и этот installer; по отдельному согласию он вызывается интерфейсом.
Для первого Google входа он просит `access_type=offline` и `prompt=consent`; провайдер всё равно
может не выдать refresh token. Однократная диагностика остаётся отдельной и токены не сохраняет.
Весь сценарий UI проверен с поддельными IPC и ответами, а не с настоящим Tauri и аккаунтами.
Перед разрешением входа и локального забывания UI читает состояние учётной записи и pin набора;
при существующем или повреждённом pin эти действия заблокированы. Внутри Windows команды
проверяют pin и устанавливают/удаляют доступ под тем же CredentialLock, чтобы изменение после
просмотра не обошло запрет. Для забывания дополнительно сверяется slot, показанный при проверке;
результат `blocked` или `mismatch` не удаляет запись. При потере ответа интерфейс в текущем
JS-контексте блокирует повтор даже после последующего чтения. В том же контексте
`credentialResetCoordination.js` запрещает сброс, пока вход или забывание ещё выполняются либо
их результат неизвестен, и не допускает новый вход во время ожидающего сброса. После отправки
сброса барьер остаётся до перезапуска; если сброс остановился до IPC, он снимается. Это не
межпроцессная защита: другой процесс или прямой IPC не участвуют; необходимо завершить операции
и закрыть другие окна. Ограничение также не является устойчивым карантином, защитой от
согласованного удаления/отката или доказательством отсутствия старого облака.

Windows-кандидат кладёт каноническую ASCII-запись в фиксированные части по 768 символов в
Credential Manager с `CRED_PERSIST_LOCAL_MACHINE`, отдельно от обычной roaming-записи vault.
Общая запись-head содержит slot ID, длину и SHA-256, но не токен или идентификатор аккаунта.
До изменения head становится `pending`; затем части записываются, перечитываются, лишние части
удаляются и только после этого публикуется новый head. Повреждение, отсутствующая или лишняя
часть, несовпадение отпечатка и оставшийся `pending` блокируют чтение и установку. Google CAS
принимает только `ready → pending → ready` с неизменной привязкой и без старого refresh в
`pending`; для Яндекса предусмотрена только первая установка. Смена аккаунта или подключение
после истечения Яндекс-токена требуют отдельного явного локального забывания и нового
подтверждения; автоматической очистки нет. Ошибка записи или потерянный ответ считаются
неопределённым результатом. Локальное забывание и factory reset не удаляют облачные файлы и
не отзывают разрешение у сервиса; сброс сообщает о неудачной очистке известных записей.

Кооперативные операции берут постоянный Windows lock-файл с `share_mode(0)`; открытый файл и
его имя сверяются по volume/file ID, отвергаются reparse point и hard link. Это не защита от
неучаствующего процесса, подмены родителя, непроверенной сетевой ФС или иной учётной записи ОС.
Содержимое частей доступно коду с доступом к хранилищу ОС и в памяти процесса; гарантированного
стирания строк нет. Head и части не являются независимым противооткатным якорем: согласованный
откат обоих не обнаруживается, а полное исчезновение всех записей не отличимо от первого входа.
Чтение после записи не доказывает порядок и сохранность при выключении питания. До решения этих
вопросов автоматический refresh и обмен файлами не включены; экспериментальный первый вход
уже доступен в настройках и требует реальных испытаний.

Изолированные Rust-тесты подставного vault проверяют обрывы до/после вызовов, частичные
данные, CAS, проверку pin перед входом/отключением и очистку. JS-тесты проверяют полный сценарий
панели с fake IPC для обоих провайдеров. Windows CI отдельно выполняет Credential Manager с
синтетическими именами и значениями и тесты блокировки; это не проверка настоящего Tauri IPC,
сборки приложения, реальных провайдеров или отключения питания.

#### Что необходимо для защищённой установки и восстановления

Это **оставшиеся требования**, а не описание доказанного installer:

1. Зафиксировать точные угрозы и границы каждой ОС. Связать одну установку с проверенным
   провайдером, регистрацией клиента и аккаунтом через отдельно защищённые pin/ключ;
   обеспечить актуальное чтение, межпроцессный атомарный CAS и сериализацию **всех** писателей,
   включая повторный вход, обновление токена, отключение и сброс. Смена аккаунта не должна
   молча перезаписывать старую запись. Неучаствующий процесс или повреждённое окружение остаются
   отдельной угрозой; только кооперативный lock не является доказательством целостности.
2. До неизвестного результата иметь устойчивый защищённый признак незавершённой операции и
   протокол, при котором pin, ключ и credential-запись наблюдаются как согласованное целое
   либо безопасно остаются на проверке. Это может потребовать другой архитектуры хранения;
   несколько обычных записей keyring, `rename` и последующее чтение сами по себе не являются
   общей транзакцией. Readback подтверждает лишь прочитанные байты в данный момент, а не CAS,
   `fsync`, сохранность после отключения питания или защиту от отката.
3. Защитить ключ и pin от подмены/потери, определить их срок жизни и порядок уничтожения,
   проверить требования к локальности, правам каталога и границам пользователя ОС. Для обнаружения
   отката корректного старого `ready` требуется независимый доверенный противооткатный якорь;
   если он недоступен или откатывается вместе с данными, автоматический повтор refresh нельзя
   объявить безопасным. Сам шифротекст с AES-GCM не доказывает свежесть.
4. Проверить границы размеров и способ хранения **до** использования настоящих токенов.
   Обычный `vault.rs` на Windows сначала вызывает keyring с `CRED_PERSIST_ENTERPRISE`
   (роуминг зависит от среды), а `CRED_PERSIST_LOCAL_MACHINE` — запасной путь при некоторых
   ошибках. Экспериментальный облачный backend отдельно выбирает локальную запись сразу, но
   фактическое поведение ещё нужно проверить. Windows ограничивает generic credential blob
   [2560 байтами](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentiala);
   существующая строка кодируется UTF-16LE: даже без накладных расходов помещается не более
   1280 однобайтовых ASCII-символов. Конверт прототипа может быть намного больше. Разбиение
   записи на части без атомарности и восстановления не решает проблему.
5. Реализовать недеструктивное восстановление с понятным пользователю состоянием, без
   автоматической очистки локальных данных или файлов облака; отдельно решить отзыв токена,
   повреждённое/заблокированное хранилище ОС, reset, повторное подключение и безопасные
   журналы без меток и секретов. Проверять Windows/Tauri, несколько процессов, сбои на каждом
   этапе и восстановление после реального перезапуска; модельные тесты не заменяют этот аудит.

Существующий `STATE_IO_LOCK` действует только внутри одного процесса и отдельных IPC-команд;
`secrets_set_many` записывает элементы по одному и может завершиться после частичной записи.
Текущий vault и fake-installer потому нельзя использовать как реализацию этого контракта.

Ожидаемая **матрица сбоев** для будущего протокола (частично смоделирована, но не доказана и не проверена на ОС):

| Момент прерывания или неопределённости | Безопасное ожидаемое поведение |
| --- | --- |
| До начала установки, отказ пользователя или смена аккаунта | Ничего локально не устанавливать; выданный провайдером токен всё равно мог существовать и сам не отзывается. |
| После устойчивого намерения, до подтверждённой установки | Сохранить незавершённое состояние; не считать пустую запись разрешением на новый вход или запись. |
| Во время установки либо после неё при потере ответа | Исход неизвестен; после перезапуска заблокировать автоматический повтор и сверить согласованность всех частей по доверенному протоколу. |
| Чтение совпало, но завершение/карантин не подтверждены устойчиво | Оставить проверку; одно совпадение чтения не превращать в доказанный успех. |
| Pin есть, ключ или запись отсутствуют, повреждены либо vault заблокирован | Остановиться и предложить безопасную проверку/восстановление; не удалять pin и не создавать новый слот автоматически. |
| Конкурируют процессы, reset или смена аккаунта | Только единый согласованный протокол всех участников; при потере ответа не считать операцию отменённой или безопасной для повтора. |
| Сбой после начала refresh POST | Сохранённый `pending` блокирует автоматический повтор, потому что сервер мог уже сменить токен; при сомнении нужен повторный вход. |
| Старые корректные данные восстановлены вместе с pin/якорем | Самостоятельно обнаружить откат нельзя; без независимой защиты не возобновлять автоматически по старому `ready`. |

#### Шифрование локальной записи подключения

`oauthCredentialRecord.js` задаёт строгий канонический формат Google с refresh token;
`oauthYandexCredentialRecord.js` — формат Яндекса с access token и сроком. Оба формата содержат
секреты в памяти и не являются подтверждением установки. Отключённый
`oauthCredentialCipherStore.js` шифрует запись AES-256-GCM и привязывает её к провайдеру и
независимо переданным `slotId`, `clientId` и `accountKey` через AAD. В конверте нет открытого
токена или ID, хотя размер и факт записи видимы. Нужны отдельный надёжно сохранённый неэкспортируемый ключ на
установку и доверенный CSPRNG; нельзя использовать ключ облачного файла вместо него. Недавний
повтор nonce обнаруживается лишь в одном экземпляре: между экземплярами или после перезапуска
эта проверка не гарантирует уникальность. Потеря ключа или pin требует восстановления доступа
или повторного входа, а не молчаливого удаления данных. Non-extractable WebCrypto-ключ не
защищает от вредоносного кода с доступом к нему и не гарантирует стирания копий в памяти.

Шифрующий слой требует внешний атомарный и устойчивый `compareExchange` **шифротекста** и
актуальное чтение; он сам не делает бэкенд устойчивым, не защищает от удаления и отката старого
корректного конверта. Для обоих провайдеров допустима только первая явная установка в пустую
ячейку; для Google дополнительно моделируются переходы `ready → pending → ready`. Замена или
повторная установка записи Яндекса не реализована. Проверка срока и прав токена остаётся
обязанностью вызывающего кода: чтение конверта их не проверяет. Отсутствие ячейки не является
разрешением её автоматически заново создать. Pin и ключ пока не сохраняются, OS keyring не
предоставляет доказанного для этого слоя CAS. Нельзя подменять его `localStorage`, браузерной
базой или обычным файлом.

Помимо fake-store с реальной Web Crypto, в Chromium испытана **тестовая** IndexedDB: две вкладки
одного процесса конкурировали за замену шифротекста, затем профиль закрывался и открывался с
ожидающей записью. Это проверка логики в конкретном браузере, не реализация native backend.
Даже `durability: strict` — [подсказка браузеру](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/durability),
а не доказательство поведения при сбое питания; браузерные данные могут удаляться или
[вытесняться](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).
Ключ в испытании передавался тестовым кодом, не хранилищем ОС. Windows, Tauri, несколько
нативных процессов, восстановление и аппаратные сбои не проверены.

#### Отключённая модель ротации Google refresh

`providers/oauthCredentialRotation.js` моделирует одну запись подключения при **строгом
предположении**, что внедрённое хранилище обеспечивает актуальное чтение и атомарный,
устойчивый после сбоев `compareExchange` между всеми процессами/писателями. Нынешний OS keyring
и его проверка чтением этих гарантий не предоставляют; Windows-кандидат ниже не доказывает
полной устойчивости. Запись, аргументы store и исходные сетевые ответы содержат чувствительные
данные и не должны попадать в логи, обычное состояние или синхронизируемые файлы. Требуются
независимо защищённые `slotId`, `clientId` и `accountKey`; установка, подтверждение, отключение
и reset существуют лишь как неподключённые экспериментальные компоненты. Защищённое хранение
привязки, замена аккаунта и восстановление ещё не завершены.
При уже переданном pin отсутствие записи возвращает `blocked_missing`, а не объявляет устройство
новым: при потере хранилища автоматическая повторная установка недопустима.

До POST модель атомарно переводит запись из `ready` в `pending` **без refresh token**;
ревизия не позволяет начать новую попытку по устаревшему наблюдению. После неопределённого
исхода запроса или проверки автоматический повтор не допускается, а оставшийся `pending`
требует повторного входа без удаления локальных и облачных данных. Только при ожидаемом
`scope` в ответе, совпадении аккаунта доверенной проверкой и действующих сроках модель пытается
вернуть запись в `ready`. Новый refresh заменяет прежний согласно
[RFC 6749 §6](https://www.rfc-editor.org/rfc/rfc6749.html#section-6); если нового нет,
сохраняется прежний с прежним сроком. Отсутствие нового не доказывает, что старый ещё будет
принят. После подтверждённой записи access доступен один раз не более 60 секунд и до истечения
срока; данные access/refresh не содержатся в статусах. Сдвиг часов назад проверяется только в
рамках одного экземпляра; защищённого времени между запусками нет. Таймеры и JS не гарантируют
физического стирания токенов из памяти.

Модель намеренно не считает readback доказательством CAS, `fsync`, отсутствия другого писателя
или подлинности данных. Возврат старой записи `ready` не обнаруживается, в том числе при
возврате вместе с ней и старого pin; повреждение или неизвестный результат записи требуют
остановки, а не повторной отправки. Блокировка после ошибки хранится только в текущем
экземпляре: после перезапуска `pending` останавливает попытку, но найденный `ready` эта
модель не отличает от откатанного старого состояния. Без независимого противооткатного якоря
автоматическое возобновление после сбоя считать безопасным нельзя.
В тестах хранилище и сеть поддельные: конкуренция, сбои, отмена, поздние ответы и смена ID
проверяют логику модели, но не свойства keyring или реальных провайдеров. `reported` scope —
лишь значение ответа, а не независимая проверка разрешений. Пока не решены эти вопросы,
реальные пользовательские токены использовать и объявлять синхронизацию работающей нельзя.

#### Экспериментальная сессия с локальной записью

`nativeGoogleRefreshFetch.js` и операция `refresh` в Rust пропускают только фиксированный
Google token endpoint и форму из трёх известных полей, без client secret и произвольного URL.
Для каждого вызова теперь обязателен одноразовый claim: готовая каноническая запись, соответствующая
ей `pending` и точное совпадение client ID и refresh token с формой. **Сам native IPC** под общим
межпроцессным lock сверяет отдельный pin аккаунта, делает CAS `ready → pending` и контрольное
чтение до POST. Второй вызов с прежней записью не проходит, пока хранилище не откатили или не
изменили отдельно. При ошибке, таймауте или потере ответа автоматический повтор запрещён;
отмена ожидания JS не останавливает уже начатый IPC или POST. При неизвестном исходе может
потребоваться повторный вход, но автоматической очистки нет. JS дополнительно проверяет точную
`pending`-запись до использования ответа. Общий lock кооперативный, readback не доказывает fsync;
вредоносный код главного окна или процесс с доступом к тому же пользователю ОС не изолированы.

Для будущего повторного открытия `cloud_credential_binding.rs` записывает **отдельный** от
токена локальный pin `slotId/clientId/accountKey` в Credential Manager. После явного подтверждения
аккаунта установка под общим lock сначала фиксирует `pending`, записывает и перечитывает токен,
затем публикует и проверяет pin. Несовпадение, отсутствие одной части или незавершённая установка
блокируют доступ; старые экспериментальные записи без pin не признаются подключением и не
обновляются автоматически. `cloud_credential_binding_read` отдаёт только сверенную привязку,
а `openStoredNativeCloudSession` использует её без ручного ввода ID аккаунта. Pin содержит личный
идентификатор, но не токен; он не передаётся в облако и не должен попадать в журнал. При явном
локальном забывании и полном сбросе обе части удаляются; файлы на диске и разрешения OAuth
не удаляются. Ошибка может означать частичное удаление.

Обе части находятся в одном защищённом хранилище того же пользователя ОС: это отдельная запись,
но **не независимый противооткатный якорь**. Согласованный откат или удаление обеих частей не
обнаруживается; `empty` не подтверждает первого входа. Настоящий IPC, восстановление после сбоев,
Tauri, сетевые сервисы и другие процессы с доступом к vault всё ещё требуют проверки. Привязка
набора и корня проверяется отдельным экспериментальным pin ниже, но доверенная установка и
защита от отката ещё не решены. В Windows CI синтетический opt-in тест прошёл установку
разделённой записи и pin, однократный claim с длинным токеном,
чтение и удаление через настоящий Credential Manager с временными уникальными именами. Это
не проверка Tauri IPC, сетевого запроса или сохранности после выключения питания.

`nativeCloudSession.js` связывает ожидаемые идентификаторы с экспериментальным хранилищем,
ротацией Google или ограниченным по сроку access Яндекса. Перед каждым действием повторно
проверяются локальная запись и срок, затем провайдером — аккаунт. При истечении доступа
Яндекса требуется новый вход, а не refresh с общим секретом приложения. Изменение записи,
обратный сдвиг часов или недоступность прекращают новую операцию до сети; однако проверка не
атомарна с последующим запросом и не защищает от отката, постороннего процесса или изменения
системных часов между запусками. При ошибке после начала отправки результат остаётся неизвестным.
Отмена/закрытие сессии не отменяет уже начатую операцию. Сессия возвращает статусы без токенов,
но не гарантирует стирания строк из памяти.

Отдельный отключённый `cloud_dataset_binding` хранит в локальном Credential Manager pin
слотов аккаунта и ключа, dataset, отпечатков ключа/корня и Google folder ID; токенов и dataKey
в нём нет. Он записывается `pending → ready` с readback только после явного подтверждения,
не перезаписывает готовую или повреждённую запись и при чтении сверяет оба локальных слота.
При смене обёрток ключа старый pin блокируется: безопасное обновление pin ещё не сделано.
`pinnedNativeCloudSession` дополнительно проверяет HMAC внутреннего ключа в JS и повторно
сверяет pin и запись перед сетевой операцией. Это не атомарная проверка с сетью, не защита
от согласованного отката всех записей и не доказательство, что код или папка получены
независимо. Нативная установка доверяет утверждению вызывающего интерфейса; для включения
нужны проверенная процедура выбора, backup и тесты реального Tauri. Фабричный сброс пытается
удалить этот pin, но не удаляет файлы в облаке. Без отдельно сохранённого кода сверки текущая
модель не устанавливает доверие при восстановлении.

В синтетических тестах сохранённая запись Google проходит через pending, fake POST и проверку
аккаунта, прежде чем выдать короткий access; потерянный ответ блокирует повтор после нового
открытия. Для Яндекса проверяются срок и совпадение аккаунта. Это не испытания настоящего
Credential Manager, Windows/Tauri, сетевого клиента или облачных сервисов. Сессия не подключена
к интерфейсу, очереди приложения, сохранению ключей или пользовательским аккаунтам.

Для Google следует использовать ограниченный доступ к файлам приложения через
[`drive.file`](https://developers.google.com/workspace/drive/api/guides/api-specific-auth);
условия публикации и доступ к общей папке требуют проверки. Скрытая папка `appDataFolder`
[не равнозначна видимой](https://developers.google.com/workspace/drive/api/guides/appdata).
Яндекс документирует отдельное разрешение `cloud_api:disk.app_folder` и путь
[`app:/`](https://yandex.com/dev/disk-api/doc/en/concepts/app-folders); клиент пока готовит
запросы именно в папку приложения, окончательные условия регистрации ещё не проверены.

### Предложение для файлов на личном диске

- **Google Диск:** папка приложения, видимая пользователю, например «Твиноферма», и созданные
  приложением файлы версий с ограниченным разрешением `drive.file`. Видимая папка — предложение,
  а не уже зарегистрированная/проверенная интеграция; создание, обнаружение на втором ПК,
  согласие и точные ограничения доступа необходимо испытать на реальных аккаунтах.
- **Яндекс Диск:** папка приложения через `app:/` с минимальным подходящим разрешением;
  отображаемое имя определяется зарегистрированным приложением. Путь, регистрацию и реальное
  поведение также нужно проверить.
- В обоих случаях сохранять не `state.json` и не отдельные читаемые файлы с персонажами, а
  зашифрованные версионированные снимки. Имя файла содержит случайные идентификаторы, а не
  ники, контакты или пароли. Провайдер всё равно видит факт хранения, размер и время файлов,
  а также необходимые технические метаданные. Формат версий и метаданные истории должны
  пройти отдельную проверку безопасности.
- Предлагать новые неизменяемые версии вместо слепой перезаписи единственного файла. История,
  общий предок, происхождение частичного выбора и метки удаления проверяются движком, а не
  определяются по времени создания файла. Google допускает дубликаты имён, а список и загрузка
  могут иметь неопределённый исход: нужны полная пагинация, проверка содержимого, обработка
  дубликатов и отказ при неоднозначности. На Яндексе `overwrite=false` и ответ `202` сами по себе
  не подтверждают завершённую запись.
- Файлы нельзя автоматически удалять, пока не разработаны политика хранения, подтверждения
  устройств и безопасная уборка старых версий. Нужно учитывать квоты и показывать ошибки.
  Папку или файлы пользователь может удалить вручную: приложение должно заметить отсутствие
  ранее известных версий и не превращать его в массовое удаление локальных записей.

Это план, а не утверждение о готовом протоколе хранения. Данные на диске предполагается
защищать случайным внутренним ключом. Экспериментальная настройка и восстановление по коду
подключены, но полное восстановление, ротация и реальная работа на другом ПК ещё не проверены.
Если пользователь потеряет все доступные способы восстановления, расшифровать такие данные не получится.

По документации Яндекса [загрузка](https://yandex.com/dev/disk-api/doc/en/reference/upload)
по подписанной ссылке не требует OAuth, а [скачивание](https://yandex.com/dev/disk-api/doc/en/reference/content)
требует тот же токен. Конструкторы запросов не содержат токена. Новый экспериментальный
read-only транспорт повторно проверяет адрес до отправки и допускает только известные хосты и
пути без перенаправлений; одного маркера `credential` для защиты было бы недостаточно.
Дополнительно подготовлен отключённый native-мост, который повторяет ограничения в Rust и не
зависит от браузерного CORS, но ещё не испытан с настоящим HTTPS-клиентом и Tauri. Неизвестные
варианты адресов отклоняются и могут потребовать уточнения после испытаний на настоящих
аккаунтах. Поддержка потоков и политики Tauri/WebView ещё не проверены в собранном приложении;
использовать пользовательские токены пока нельзя.

### Экспериментальный native-транспорт дисков

`cloud_disk_network` предназначен только главному окну. Он принимает названную операцию и её
параметры, а не произвольные метод, URL или заголовки. Rust строит запросы Google для проверки
аккаунта, выделения ID, списка и создания папки, списка, чтения и создания новой версии.
Для Яндекса доступны проверка аккаунта, список, метаданные, ссылки и чтение/создание версии.
Загрузка версии разрешена только в каноническом формате конверта, с совпадающими ID,
допустимыми base64url-полями и без дополнительного открытого JSON. Это структурная проверка,
а не доказательство действительного шифрования. Доверенная привязка ID папки Google и
устойчивое хранение намерения создать её не реализованы. Скачивание Яндекса
использует OAuth только на проверенном downloader, а PUT на проверенный uploader — без токена.
Подписанные ссылки и содержимое IPC считаются чувствительными и не пишутся в журнал.

Клиент не использует системный proxy, redirect, сжатие или автоматические повторы; подключение
ограничено 10 секундами, запрос — 60 секундами. Системам, требующим proxy, такой вариант может
не подойти. Тела HTTP-ошибок не возвращаются. Ответ идентичности ограничен 8 КиБ, короткие
ответы — 64 КиБ, списки — 2 МиБ, версия — 45 МиБ; Google multipart — 5 MB. Передача через IPC
больших файлов и потребление памяти ещё не испытаны на Windows. Возврат 201/202 или совпадение
при повторном чтении не заменяют устойчивую очередь и подтверждение истории. Сетевая ошибка,
таймаут или отмена после начала записи оставляют исход неизвестным, и автоматический повтор
запрещён. Лимит одного нативного запроса действует только внутри процесса; устойчивого
межпроцессного lock и восстановления очереди этот канал не предоставляет.

`nativeDiskFetch.js` преобразует запросы существующих моделей в ограниченные операции и
проверяет форму ответа. Пока нативный вызов не завершился, он не освобождает слот даже после
отмены ожидания в JS. Отменить уже переданный IPC или гарантировать стирание токена из памяти
нельзя. Поддельные IPC-тесты проходят полный путь шифрования, записи, сверки, списка, даты и
чтения для обоих провайдеров без применения к приложению. Политика Rust и сетевой исполнитель
проверены в изоляции с поддельными Tauri/HTTP-интерфейсами и синтетическими запросами JS; это
не доказывает сборку или поведение настоящего reqwest, сервисов, Windows и системы сертификатов.
Интерфейс и автоматическая синхронизация не вызывают этот канал.

### Экспериментальная постоянная очередь отправки

`durableOutbox.js` шифрует журнал отдельным ключом HKDF от ключа набора и привязок
устройства/слота. Внутри находятся уже зашифрованные версии, подтверждённый провайдер,
аккаунт и идентификаторы. Состояния идут от `queued` через `prepared` и `attempting` к
`confirmed`: намерение записи фиксируется **до** единственной сетевой попытки. После потери
ответа повторная отправка не запускается; сверяется именно ранее выделенный ID Google или
путь Яндекса и исходный конверт. Только точное совпадение разрешает записать `confirmed`.
Даже оно не доказывает, что файл навсегда останется в облаке. Для подтверждённых точной сверкой
элементов добавлено явное `compactConfirmed`: исходные конверты убираются только из локальной
очереди, а ID, отпечаток истории, адрес Google и ID попытки остаются в зашифрованных квитанциях.
Повторная постановка того же ID отклоняется и после перезапуска. Не подтверждённые или ожидающие
сверки элементы не сворачиваются. Файлы в облаке эта операция не удаляет. `confirmedPins()`
возвращает сохранённые отпечатки для отдельной проверки истории; они не доказывают свежесть,
полноту или отсутствие отката хранилища.

Очередь по-прежнему ограничена 16 активными/несвёрнутыми элементами и 16 МиБ состояния; число
локальных квитанций ограничено 128 — текущим пределом читателя истории. При достижении предела
сворачивание останавливается, не отбрасывая данные; политика архивирования общей истории и
удаления старых облачных файлов пока не определена. Новый зашифрованный формат журнала v2
читает старый v1 и переводит его в v2 при следующей записи; старый код, знающий только v1,
не сможет открыть обновлённый журнал. Квитанции, как и pin очереди, не защищают от совместного
отката обоих локальных хранилищ.

Windows-кандидат хранит независимый head в Credential Manager и зашифрованный файл в папке
данных для каждого провайдера. Под общим кооперативным lock он записывает `pending`, атомарно
публикует и перечитывает файл, затем фиксирует `ready` с длиной, SHA-256 и привязками. Неверные
части, незаконченная запись или отсутствие одной из копий блокируют работу; `empty` не
доказывает первого запуска. Журнал не использует localStorage. JS-адаптер блокирует экземпляр
после неизвестного результата или таймаута: timeout не отменяет нативную операцию. Прямые IPC
доступны доверенному главному окну и не защищают от вредоносного кода внутри него.

Проверка чтением и кооперативный lock не доказывают fsync, устойчивость к отключению питания,
защиту от некооперативного изменения каталога, совместного отката или удаления обеих частей.
При полном сбросе приложение пытается удалить оба известных файла и head; ошибка может
означать частичную очистку. Облачные файлы и OAuth-разрешение не удаляются. Синтетические
IPC-тесты проверяют оба диска и восстановление после потерянного ответа. Windows CI также
испытал файловую часть в отдельном временном каталоге: создание, проверку замены, hard link,
недоступный или слишком большой файл и сброс с поддельным vault. Это не проверка настоящего
Credential Manager, сбоя питания, Tauri или облачных провайдеров. Очередь не подключена к UI,
ключам, локальному сохранению, backup или реальным аккаунтам.

#### Поиск папки Google и первый POST

`googleFolderManager.js` использует поиск по приватной метке `appProperties.tfFolder=1` и MIME
папки, а не по названию: переименованная папка остаётся кандидатом. Он проверяет страницы и
дубликаты, ограничивает результат 128 папками и дважды сравнивает полный список ID и имён.
При нескольких кандидатах возвращается `ambiguous`, при изменении между обходами — `changed`;
ни одна папка автоматически не выбирается. Неполный поиск, повторный токен страницы, повторы
ключей в JSON, неверные типы и опасные управляющие символы в имени блокируют результат. Имя
папки может содержать личную информацию и в будущий интерфейс должно попадать только как
текст, без журналирования или выполнения HTML.

Отключённый `openStoredNativeGoogleFolderDiscovery` теперь связывает этот поиск с ранее
проверенной локальной записью аккаунта и guarded refresh без заранее известного folder ID.
Он выдаёт только чтение: создание и отправка недоступны. `probeRoot` работает лишь с папками
последнего успешного списка и сравнивает точный отпечаток корневого конверта с кодом,
полученным **по независимому каналу**. Это не проверка GCM, не сохранение выбранной папки,
не доказательство полноты или свежести списка; одинаковый корень может быть скопирован в
несколько папок. После загрузки снова сверяется локальная учётная запись, но проверка не
атомарна с работой провайдера. В fake IPC на втором условном ПК проверена цепочка поиск →
сверка корня → восстановление backup-ключом → проверка истории и read-only сравнение, без
записи локальных пользовательских данных. Реальный Tauri и реальные диски не проверялись.

ID выделяется заранее через `generateIds` и должен быть устойчиво записан вместе с намерением
создания до POST. Отдельный вызов `createOnce` ещё раз обходит список и не создаёт папку, если
нашёл существующую. Он отправляет только фиксированные метаданные и этот ID; `accepted` не
заменяет последующую проверку. При неизвестном исходе этот экземпляр не повторяет попытку.
Однако после перезапуска, на другом ПК или при устаревшем списке дубликаты всё ещё возможны:
хранилище намерений, защищённый pin, доверенный выбор, восстановление и межпроцессная
координация не подключены. Доступность метки и `drive.file` на двух ПК зависит от фактической
OAuth-регистрации и должна проверяться на реальном сервисе. Google документирует поддержку
заранее выданных ID для папок, но этот сценарий пока протестирован только имитацией.

### Что уже проверяется при чтении версий

`versionReaders.js` дочитывает все страницы Google и Яндекса, затем выполняет второй полный
обход и отказывает при замеченных изменениях. Для Google проверяются `incompleteSearch`,
повторы и циклы токенов страниц, идентификаторы файла и метаданные. Если токен страницы
отклонён, текущая проверка останавливается; следующий самостоятельный вызов начинается с
первой страницы. Для Яндекса проверяются `offset`, `limit`, `total`, пустые/повторные
страницы и имена версий. Повторный ID версии или неоднозначный файл блокируют результат.
Лимиты — 128 страниц и версий набора, 5 000 элементов папки Яндекса, 2 МиБ ответа метаданных
и 45 МиБ файла. Превышение или неверный ответ останавливает проверку, а не даёт усечённый список.

Не подключённый к приложению `listWithDates()` дополнительно возвращает справочное время
из `modifiedTime` Google или `modified` Яндекса для каждой найденной версии. Разбирается только
консервативное подмножество RFC 3339 с явным смещением; неизвестное или некорректное значение
становится `null`, а не заменяется временем проверки или текущими часами. Известные метки
сравниваются между обходами с точностью исходных долей секунды: замеченное изменение
останавливает результат. Метаданные не подписаны и не связаны криптографически с загруженным
файлом; проверка двух обходов не исключает подмену, откат или изменение после обхода.
`list()` сохраняет прежний формат списка ID. Оба пути и разбор даты испытаны только на
поддельных ответах, без OAuth и настоящих облачных аккаунтов.

Прочитанный файл проверяется как конверт с совпадающими ID набора и версии; его ещё нужно
расшифровать и проверить историю с независимыми сохранёнными доверенными отпечатками. Два
одинаковых обхода **не доказывают атомарность или полноту облака**: сервис может скрыть ветку
или повторить устаревший список. Отсутствие файла/ответ `404` не является подтверждённым
удалением записей. Проверки пока используют имитации ответов, без реальных данных и аккаунтов.

Каждый провайдер должен предоставлять общему движку получение полного списка версий,
чтение и создание новой версии с проверяемым результатом. Различия HTTP API, авторизации,
ограничений и ошибок остаются внутри адаптера. Выбор Google и Яндекса означает поддержку
обоих вариантов, а не автоматическое копирование одних данных сразу в оба аккаунта.

## Порядок реализации и приёмка

1. Разработать точный allowlist, миграцию стабильных идентификаторов и отдельное хранение
   служебных данных устройства. Проверить, что секреты и локальные пути не попадают в экспорт.
2. Реализовать устойчивую локальную очередь, зашифрованный формат, резервное копирование и
   безопасное применение входящих версий; добавить тесты с перезапуском и сбоями записи.
3. Реализовать и протестировать независимые адаптеры Google и Яндекса и OAuth-вход без
   секретов в исходниках. Проверить выход из аккаунта и отозванный доступ.
4. Подключить автоматический обмен и ручную кнопку только после предыдущих гарантий. Проверить
   два реальных устройства и тестовые аккаунты: первая настройка, оба режима офлайна,
   одновременные правки, удаление, сбои сети, исчерпание места, повреждённые данные и
   восстановление из резервной копии.

### Что ещё решить и проверить

- Аудировать экспериментальные формат обёрток, ограничения пользовательских ключей и scrypt на
  поддерживаемых устройствах; определить поведение «запомнить на этом ПК», безопасную смену,
  отзыв и ротацию ключей. Основной и запасной секрет не должны совпадать. Нужны защищённое
  хранение и проверка отпечатков, ввод и подтверждение сохранения запасного ключа, передача на
  другой ПК и полное восстановление; секреты не нужны разработчику. Потеря всех способов
  восстановления и ключа на других устройствах означает потерю доступа к старым облачным копиям.
- Сколько версий хранить, как учитывать давно отключённые устройства и когда вообще безопасно
  удалять старые версии и метки удаления. До этого — без автоматической очистки истории.
- Какие из существующих журналов и групп настроек действительно переносить, как долго хранить
  новый журнал операций и как показывать детали без чувствительных значений.
- Регистрация Google- и Яндекс-приложений, разрешения, проверки публикации, доступность
  облачных аккаунтов для испытаний и полноценное тестирование собранного Tauri-приложения.
  OAuth-данные и пароли пользователей не запрашиваются и не помещаются в репозиторий.
- Отдельно спроектировать согласование необратимых действий на нескольких ПК и проверку
  состояния сайта: перенос истории без этой защиты не предотвращает повтор покупки или передачи.

До проверки на настоящих аккаунтах и в собранном desktop-приложении не объявлять интеграцию
работающей. Статический GitHub Pages не является сервером синхронизации.

### Экспериментальный локальный ключ и проверка резервного секрета

`keyStateRecord.js`, `keyProvisioning.js`, `providers/nativeKeyStateStore.js` и
`cloud_key_state.rs` пока не подключены к настройкам или сетевой синхронизации.
Создание нового набора требует отдельного согласия, затем подтверждения, что запасной
секрет сохранён отдельно, и его повторного ввода. До успешного ввода запись не
устанавливается. Внутренний ключ данных и две зашифрованные обёртки хранятся только
в локальном журнале хранилища ОС (Windows Credential Manager); пароль и запасной
секрет туда не записываются. Каждое чтение в JS заново проверяет привязки,
отпечаток и криптографическое доказательство. Rust проверяет лишь каноническую
форму и переходы и не доказывает правильности пароля или обёрток.

Журнал использует отдельные имена, общий межпроцессный lock, `pending → части →
ready` и проверку чтением. Ошибка или потеря ответа блокирует текущий экземпляр;
после неизвестного исхода надо отдельно проверить запись, а не устанавливать её
повторно вслепую. Изменение обёрток сохраняет тот же ключ данных, но НЕ отзывает
старые файлы или старые секреты. Полный сброс пытается удалить известный локальный
ключ; облачные файлы он не удаляет.

`empty` и подтверждение создания не доказывают отсутствия старого набора.
Экспериментальный `portableKeyCapsule.js` позволяет включить в **каждую конкретную**
зашифрованную облачную версию v2 две зашифрованные обёртки из `keyBundle.js`. Поскольку
капсула находится в том же файле, используется прежний create-only журнал и после
неизвестного ответа проверяется точный файл, а не повторяется POST. Отдельная публикация
или отдельный журнал ключа не нужны. Формат v1 по-прежнему читается; файлы v1 не содержат
капсулы. AES-GCM связывает целиком сериализованную капсулу с версией и набором; HMAC
связывает метаданные и обе обёртки с ключом данных, но сам по себе не доказывает, что
обе обёртки расшифровываются. При создании отдельно проверяются обе, при восстановлении —
только введённая. Домен отпечатка истории для v2 включает капсулу; отпечатки v1 не меняются.

Капсула, параметры scrypt и зашифрованные обёртки видны облачному провайдеру, хотя пароли
и внутренний ключ в открытом виде в неё не помещаются. Это позволяет **офлайн-подбор
слабых пользовательских секретов**. Случайный запасной ключ нужно хранить отдельно;
проверка сложности пользовательского пароля не доказывает его энтропию. Смена обёрток не
отзывает уже загруженные файлы и секреты. Формат и реализация криптографии не аудированы.

`pairingCode.js` формирует код `TFP1-` из dataset ID, отпечатка обёрток и отпечатка
корня истории. Код не содержит секреты, но его обязательно передавать и сверять по
**независимому доверенному каналу**: скачанный из того же облака код не доказывает
подлинности или свежести. Это метаданные, их тоже не стоит публиковать без необходимости.
Разбор кода и локальный pin существуют только в отключённых моделях; интерфейса и процедуры
безопасного сохранения/передачи кода человеком пока нет. Без сохранённого доверенного корня
полноценная проверка истории после потери всех ПК
ещё не решена. После потери пароля и запасного ключа, без внутреннего ключа на другом
ПК или копии, восстановить старые данные невозможно.

`portableKeyDiscovery.js` ищет v2 только в уже открытой сессии для известного dataset;
возвращённые диском отпечатки до независимой сверки недоверенные. Он не выбирает файл по
дате и не предполагает, что отсутствие v2 означает удаление ключа. `keyRecovery.js`
проверяет независимо сверенные dataset ID/отпечаток и секрет, расшифровывает файл и однократно устанавливает ключ в
пустой локальный журнал с readback. Занятая запись не затирается; отмена до установки
ничего не записывает, а неизвестный исход установки не повторяется автоматически.
Восстановление ключа не проверяет полноту облака и не применяет данные.

`cloudReview.js` читает все наблюдаемые версии, проверяет корень, ранее известные пины,
родителей, GCM и капсулы и предлагает явный выбор версии для **только чтения** сравнения
с предварительно скопированным публичным локальным снимком. Время файла, время проверки
и переданное достоверное время локального сохранения остаются разными значениями; если
дата неизвестна, она не придумывается. `only_local`/`only_cloud` не означают удаление;
дата не выбирает победителя. Отмена ждёт уже начатое native-чтение и не запускает следующее.
Это не backup, не применение, не проверка свежести облака и не защита от изменения локального
state после сравнения; для записи нужны отдельные witness, backup и подтверждение.

Тесты JS соединяют создание ключа, очередь и имитацию Google/Яндекс IPC с потерянным
ответом, сворачивание квитанций, поиск файла, независимый код, восстановление в отдельном fake
vault и сравнение. В модели двух ПК у каждого свои имитации credential pin и ключевого vault,
общим остаётся только поддельный диск. Оба сценария также устанавливают раздельные локальные
pin набора и открывают закреплённую сессию на каждом условном ПК. Тесты проверяют частичную
установку, старую запись без pin и один расход refresh; это синтетика, не реальные компьютеры.
Проверка Chromium использовала реальный WebCrypto и fake IPC: открытие с pin, чтение и отказ
при изменении pin до записи; axe для блока демо — 0 нарушений. Дополнительно 198 синтетических
форм локального pin совпали между JS и изолированной проверкой Rust; криптография подменённого
тестового sha2 при этом не проверялась. Полный локальный Vitest прошёл двумя частями
(232 файла, 4112 тестов прошли, один тест пропущен как неприменимый к Яндексу). CI ветки
проверил точный npm lockfile, Windows `cargo test --locked`, fmt, clippy и повторный cargo audit:
<https://github.com/drednight/Tvinoferma/actions/runs/41010746342>. В CI есть отдельная проверка,
которая требует запуска и положительного результата opt-in теста Windows Credential Manager;
она прошла с временными синтетическими записями Google и Яндекса, включая блокировку входа и
забывания при pin набора. Это **не** тест настоящих сервисов, Tauri IPC, передачи между
физическими ПК, отключения питания или восстановления реального state. Readback не гарантирует
fsync, не выявляет совместный откат head и частей и не защищает от процесса с доступом к тому
же пользователю ОС. JS/Rust не гарантируют стирание секретных строк в памяти. Локальное
закрепление аккаунта экспериментально подключено к настройкам; поиск и закрепление корня,
первое сравнение с backup, безопасное применение, передача и автоматизация ещё не подключены.

### Диагностика отказа OAuth после возврата из браузера

Сообщение локальной страницы «Ответ получен» подтверждает только получение callback,
не обмен кода, не разрешения и не сохранение доступа. Если последняя надпись —
«Проверяем ответ авторизации…», отказ относится к этапу обмена кода/проверки токена,
а не к последующему чтению аккаунта.

Проверка регистрации и сохранение доступа теперь показывают фиксированный код
`token/…` либо `identity/…`. Нативный транспорт читает ограниченный ответ ошибки
и возвращает только разрешённый код; исходный ответ/описание, код авторизации,
идентификаторы и токены не попадают в статус или журнал. Неизвестная ошибка остаётся
`transport_failed`/`response_invalid`. Автоматического повтора обмена нет.

- `token/client_secret_required`: Google явно сообщил об отсутствующем параметре
  `client_secret`. Импортируйте Google Desktop JSON в разовой настройке новой сборки;
  секрет добавляется нативно для code exchange и refresh. Это не доказательство
  неправильного Client ID. Не вводить секрет в поле Client ID или чат.
- `token/invalid_client`: сервер отклонил параметры клиента; сам код не устанавливает,
  какой параметр неверен/отсутствует. Не нужно наугад расширять разрешения.
- `token/invalid_grant`: код не принят (например, истёк/использован или не совпали параметры).
- `token/connection_failed`, `token/timeout`: проблема соединения/ожидания, не обязательно
  настройка OAuth. Для timeout результат выдачи токена может остаться неизвестным.
- `token/response_invalid`: успешный HTTP-ответ не прошёл прежние строгие проверки
  формата/прав; они не ослаблены ради диагностики.
- `identity/api_disabled`: известный ответ Google об отключённом Drive API.

Само добавление этих кодов **не исправляет и не подтверждает реальный вход**. По скриншотам
установлен этап отказа Google, но точная причина требует кода из новой Windows-сборки.
Для отчёта достаточно этого кода; не присылать callback URL, секреты или ответы сервера.

Workflow **Windows acceptance build** собирает отдельный unsigned `.exe` с README,
commit SHA и SHA256SUMS, без установщика, секретов подписи, релиза и latest.json.
Он запускается для изменений OAuth в PR либо вручную. Полный набор тестов остаётся
в основном CI и не дублируется упаковкой. Использовать отдельный тестовый Windows-профиль:
identifier/vault обычного приложения эта сборка не изолирует; встроенная версия может
совпадать со стабильной. Готовый артефакт сам по себе не заменяет приёмку и успешный CI.


### Упрощённое подключение и нативный Google Desktop client (31.10.2026)

Этот блок уточняет исторические описания выше про отсутствие client_secret: frontend
по-прежнему строит строгие формы без секрета, но Windows-исполнитель после проверки формы
добавляет secret из локального Credential Manager или owner-configured сборки. Поддержаны
и authorization code, и Google refresh. URL из импортированного JSON не используются.
JSON только типа `installed`, ограничен 64 КБ; каноническая запись ограничена 1200 ASCII
байт. IPC возвращает только статус и открытый clientId. Привязка/токен не переписываются
импортом; другой clientId при готовой привязке, blocked и pending запрещены. Refresh
preflight и одноразовый claim выполняются под одним lock; сетевых автоповторов нет.

Обычный вход — одна кнопка с автоматической проверкой локальной записи и прежним
обязательным подтверждением аккаунта. Диагностика и ручное управление свёрнуты. После
входа показываются новый набор/подключение существующего; перед новым набором ID и
местное сохранение готовятся автоматически с прежними backup-защитами. Подтверждение
сохранённого запасного ключа, доверенного кода другого ПК и загрузки не убраны.
Файловая панель появляется только при готовой локальной привязке, не после проверки
регистрации. Это не означает, что файл уже отправлен или доступ ещё действителен.

Настройка сборки владельцем, ограничения и план реального прогона:
`docs/CLOUD-SYNC-ACCEPTANCE.md`, раздел «Новый короткий вход и Google Desktop JSON».
Реальные Google/Яндекс и два Windows-ПК остаются отдельной приёмкой, не результатом CI.

### Повторный вход Google и уточнение сетевого отказа (31.10.2026)

В обычной панели больше нет ручных «Проверить локальную запись», «Сохранить доступ»
и «Удаление локального доступа». Проверка локального состояния выполняется самой
кнопкой входа; подтверждение аккаунта остаётся обязательным. Историческая разметка
ручных инструментов существует только в тестовой fixture, а не в скрытом DOM приложения.

Для уже сохранённой или pending-записи Google доступен **«Повторить вход Google»**.
Это новая явная PKCE-авторизация в системном браузере, не повтор старого refresh POST.
Защищённая native-запись должна быть канонической и соответствовать своему pin.
Оба чтения аккаунта свежим access token должны совпасть с прежним accountKey;
clientId и slotId не меняются. После подтверждения выполняется точный CAS старой
записи: pending→ready либо ready→pending→ready, затем readback. Конкурирующее
изменение не перезаписывается; неизвестный исход не повторяется автоматически.
Привязка набора, ключи, путь/байты ожидающего полного файла и файлы облака этим
входом не меняются. После входа ожидающий файл по-прежнему сначала сверяется.
Повреждённый pin и произвольная смена аккаунта не «ремонтируются» новым входом.
Этот механизм не распространяется на замену Yandex access token.

Native disk transport теперь выдаёт только фиксированные коды: timeout, connect
(включая DNS/TLS), busy, redirect, encoding, size, body, policy, client либо общий
transport. JS принимает **только точное совпадение** кода, прикрепляет этап через
WeakMap и показывает статическое русское описание. Исходные ошибки/URL/токены,
подписанные ссылки и ответы не попадают в статус, очередь или журнал. HTTP 401/403
по-прежнему отличаются от сетевого отказа. Для обычных файловых запросов JS ждёт
до 70 с, чтобы получить ограниченный native-результат (HTTP timeout 60 с), вместо
прежнего преждевременного JS timeout 25 с. Таймауты credential IPC/refresh и явные
пользовательские/test deadlines не увеличены. Блокировка native-запроса сохраняется
до его фактического завершения; автоматических сетевых повторов не добавлено.

HTTPS, allowlist хостов, запрет redirect/proxy/decompression, ограничения размера,
побайтовая сверка и независимость провайдеров не ослаблены. Продолжение после
ошибки скачивания проверяет прежний файл один раз и не делает новый PUT при
неопределённости. Синтетические тесты воспроизводят каждый безопасный отказ,
сохраняют неизменный pending intent и подтверждают его после восстановления
чтения без повторной загрузки. Реальная причина пользовательского сбоя Яндекса
остаётся неизвестной до нового диагностического результата Windows-сборки;
redirect, HTTP 403 и повреждение файла не считаются установленными причинами.

Подтверждающий независимый пример схемы downloader→storage (не пользовательская ссылка):
https://github.com/PXSYS13/yadisk_backup/blob/2390037ff62143dd9d0580b5a9732a6e0c14baf0/storage_fetch.py .
Это не доказательство адреса в конкретном пользовательском ответе; неподдерживаемый
Location возвращает фиксированный `download_content_native_redirect_target`.
Повторный переход возвращает `…_native_redirect_chain`. Redirect API-запросов,
Google, PUT/POST/DELETE по-прежнему запрещён. Проверяются сырой Location, HTTPS,
точный suffix/label хоста, порт 443, путь, percent escapes; userinfo/IP/fragment,
dot segments, закодированные разделители и дубликаты Location отклоняются.
Второй запрос создаётся заново: без OAuth, cookies, Referer или тела. Подпись URL
остаётся только в native-памяти. Оба шага делят прежний 60-секундный бюджет;
лимит тела/UTF-8/каноническая побайтовая сверка сохраняются. Это продолжение GET,
не повтор PUT; ожидающий полный файл не заменяется.

Google теперь отдельно сообщает pending refresh и повреждённую защищённую привязку.
При pending/неподтверждённом обновлении рядом с ошибкой есть кнопка повторного входа
в тот же аккаунт. Она переключает только способ входа, не направления сохранения.
Восстановление Desktop JSON того же clientId разрешено и при pending: меняется
только конфигурация приложения, не запись OAuth/pin/dataset/key/pending-файл.
Прежний refresh не повторяется и pending этим импортом не завершается. Старый
нативный запрос уже захватил неизменяемую форму под общим lock; новая явная OAuth
попытка по-прежнему заканчивается точным CAS и двумя проверками того же аккаунта.
Другой clientId и повреждённый pin запрещены. Успех реального Google пока не доказан.

CI: полный frontend suite распределён Vitest `--shard=N/4` по четырём отдельным
runner-ам, с изоляцией файлов и двумя workers на runner; тесты не исключены.
Итоговый прежний check `frontend` зависит от quality и всех четырёх частей,
поэтому одна упавшая/отменённая часть не даёт зелёного результата. Устаревшие
запуски того же PR отменяются concurrency; PR/main не отменяют друг друга.
После merge полного дубликата по-прежнему нет. В unsigned acceptance exe отключён
LTO и разрешены 16 codegen units; стабильный release-профиль не изменён. Размер
и быстродействие тестового exe могут отличаться. Реальное ускорение оценивается
по новому прогону, а не обещается по числу параллельных частей.
