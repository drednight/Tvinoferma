# Приёмочная проверка синхронизации на двух Windows-ПК

Это **план испытания, не отчёт об успешном подключении**. Автоматические проверки с
подставными дисками и Windows credential-smoke не доказывают работу приложения с настоящими
Google/Яндекс API, полноту облачного списка или сохранность при отключении питания.

## Основной прогон нового файлового режима

Для Google и Яндекса отдельно, одинаковой новой desktop-сборкой:

1. На A подключить набор и отправить полный файл. Записать версию сборки и дату проверки.
2. На B восстановить доступ основным паролем; отдельно повторить запасным секретом. Само
   подключение и проверка не заменяют местные данные.
3. Скачать файл для сравнения: проверить добавления, изменённые поля и отсутствующие записи,
   отдельно дату файла, дату проверки и местное сохранение. Никакой автоматической записи.
4. Подтвердить полную замену на B. Сверить данные, порядок, удаления и полностью пустой банк.
   Проверить наличие точной местной копии до замены и сохранение местных контактов у сохранённых ID.
5. Изменить B и сохранить без отправки: принятые pin/hash остаются прежними, сравнение
   сбрасывается. После «Отправить на диск» A должен увидеть новый файл и различия.
6. Независимо изменить A и B. После отправки A отправка B должна предупреждать о непринятой
   облачной версии. Проверить отмену и явную замену полным B, без автоматического объединения.
7. Изменить данные/диск/файл во время подтверждения: старое согласие не применяется.
8. Отключить сеть до загрузки и после возможной записи. Проверить pending, перезапуск и
   сверку тех же байтов/Google ID без повторной отправки неизвестной попытки. Новые местные
   правки не теряются при подтверждении ранее отправленного файла.
9. Проверить, что новый местный пароль не появился в облачном публичном файле. Ранее
   переданная приватная часть переносится только после отдельного согласия.
10. Убедиться, что предыдущие облачные файлы остались. Две конкурентные головы должны
    показать список без автоматического выбора. Просмотр выбранного файла не заменяет
    местные данные и не меняет актуальную версию на диске.
11. Выбрать A как итоговый полный файл: отдельное подтверждение, отдельное согласие на
    приватную часть. B и его приватные значения не смешиваются с A; оба прежних файла
    остаются. На другом ПК при проверке должен быть один актуальный head, поля строго из A.
    Отдельно повторить, выбрав текущие местные данные, не облачный файл.
12. Во время подтверждения выбора добавить третий файл с другого ПК: старое согласие
    должно остановиться. При конкуренции уже во время загрузки оба файла сохраняются,
    pending подтверждённого файла снимается, UI не объявляет единственного победителя.
13. Для prepared изменить местные данные, отменить подготовку без сети, проверить backup
    с прежним шифртекстом и сохранность текущих данных; отправить их отдельным новым файлом.
14. Для attempting с неизвестным результатом проверить отказ от отдельного согласия.
    После явного снятия ожидания проверить backup и unsettled-отпечаток. Поздно появившийся
    файл должен обнаружиться и потребовать нового выбора, а не молча примениться/повториться.
    После подтверждённого итогового файла, покрывающего обе попытки, метка исчезает.
15. Ошибка backup или местная правка во время согласия не должна очистить pending.

16. В ручном блоке контактов проверить выключенные категории, отказ без полноты источника
    и отдельного риска пароля. Подготовка ничего не отправляет. Выбрать один пароль,
    проверить «Выбрать все»/«Снять все», отменить подтверждение; значений в DOM/журнале нет.
17. Явно отправить полный файл с одним выбранным контактом; на B сравнить и применить только
    его с независимой копией. Другие контакты, публичные поля и принятые pin/hash не меняются.
    Отдельно выполнить до принятия публичного файла на B с уже известными sync-ID: принятая
    база должна остаться прежней/пустой, даже если контакт применился успешно.
18. Изменить пароль на A, выполнить обычную отправку: новый местный пароль не попадает в
    облако. Выбранное вручную пустое поле очищает значение только в новой актуальной партии;
    не выбранные прежние категории остаются. Проверить vault включённый и выключенный,
    недоступность и внешнюю замену vault-записи: это не разрешение экспортировать пустоту.
19. Прервать загрузку приватной партии и перезапустить. Изменить местный пароль до сверки:
    сверяются прежние зашифрованные байты без повторной неизвестной загрузки и без добавления
    нового пароля. Отмена/снятие ожидания предупреждает, что backup и поздний файл могут
    содержать уже одобренные контакты.
20. Удалить персонажа с ранее переданными контактами. Без отдельного согласия отправка
    остановится; после согласия history v7 исключает его приватную запись из нового файла,
    не из резервной истории. Секреты оставшихся персонажей не исчезают. На B файл читается
    новой сборкой; старая сборка обязана остановиться на неизвестном формате.

21. Подготовить архив истории, в том числе с несколькими heads. Сверить счётчик и запас
    до лимитов, отсутствие открытых контактов/ключей/токенов в `.tf-history.json`. Сохранить
    отдельно от основного/запасного секрета. Скачивание не объявляется подтверждённой записью.
22. Выбрать сохранённый архив и сверить чтением: локальные данные, принятая база и диск не
    меняются. Подменить файл, изменить привязку/диск или добавить облачную версию во время
    сохранения: старый архив не объявляется актуальным. Другой выбранный файл снимает прежний
    статус успеха. Pending/unsettled и прежняя очередь блокируют подготовку. Архив сам не освобождает лимит и не разрешает удалить цепочку вручную.

23. На A принять нужный файл; остановить B, сохранить отдельный ключ, подготовить/сохранить/
    сверить архив. Создать v8: точная облачная публичная/приватная часть сохраняется,
    неотправленные местные изменения остаются местными. Без согласий/сверенного архива — отказ.
24. Выбрать предшествующий архив ещё раз, проверить и отдельно подтвердить корзину.
    После очистки сверить root+checkpoint на A и восстановить привязку на чистом B
    основным и запасным секретом. Новый локальный файл B не применять молча; сначала сравнение.
25. Прервать ответ checkpoint upload/trash, перезапустить. Проверка прежних байтов не
    создаёт второй upload/trash. Attempting сохраняется; неизвестный исход не называется
    отменённым. Новая голова/подмена/изменившаяся дата перед очисткой останавливает её.
    Проверить SHA/ETag, app:/ и корзину настоящих API; без ETag Google операция отказывает.
26. Из архива выбрать историческую версию, показать удаления, восстановить местно с
    точным backup. Принятая база и облако прежние. Отдельно выбрать пароль, проверить риск,
    независимый backup/vault, отсутствие значений в DOM/логах и неизменность невыбранных полей.
27. Не запускать старый клиент после очистки. В отдельном тестовом наборе проверить
    позднюю ссылку на удалённого родителя: отказ, сохранение файлов, никакого скрытия
    поздней головы. Автоматического ремонта DAG архивом нет; для этого случая нужна
    отдельная процедура возврата недостающих родителей, не местный restore.

Это план, не отчёт. Имитация двух профилей не заменяет этот прогон.

## Архивный план прежнего режима

Следующие сценарии описывают старую выборочную передачу/merge, а не новые обязательные
правила полного файла. Автоматическое объединение не требуется новым сценарием.

## Подготовка

- Использовать два тестовых профиля Windows и одинаковую актуальную desktop-сборку.
  Веб-демо не подключается к настоящим дискам. Не смешивать версии протокола.
- Проверять Google Диск и Яндекс Диск **отдельными прогонами**, не переключать провайдера
  посередине незавершённой операции. Инструкции регистрации и ограничения OAuth приведены в
  [CLOUD-SYNC.md](CLOUD-SYNC.md).
- Использовать только синтетические персонажи, контакты, финансы и события. Настоящие
  пароли, деньги и необратимые игровые действия для этой проверки не нужны.
- До начала создать независимые копии данных обоих профилей. Если контакты в OS-vault,
  отдельно сохранить защищённую копию самих тестовых контактов: `state.json` может содержать
  только ссылки. Не отмечать подтверждение копии, пока она действительно не создана.
- Основной пароль и запасной ключ сохранить отдельно. Не включать их в отчёт, скриншоты,
  Git, сообщения об ошибках или OAuth-регистрацию. Входить через системный браузер;
  доступы и коды подтверждения не передавать в чат.
- Отключить все игровые/необратимые автоматические действия. Облачная проверка сама по себе
  не должна запускать игровые скрипты, покупки, передачи или повторно выполнять задачи.

## Что записывать в отчёт

Версию и commit сборки; версии Windows; провайдера; режим vault; состояние автоотправки;
пункты ниже с отметками «прошёл / не прошёл / не выполнялся». Для ошибки — безопасный код,
стадию и наличие очереди/копии, **без исходных запросов, токенов, ключей и контактных значений**.
Не считать отсутствие ошибки, завершённый PUT или HTTP 202 доказательством проверенной записи.

## Последовательность для каждого диска

| № | Действия | Ожидаемый результат |
| --- | --- | --- |
| 1 | На ПК A открыть «Настройки → Синхронизация». | Блок между ПК изначально свёрнут; нет выбранных разрешений контактов или включённой по умолчанию автоотправки. |
| 2 | Подключить тестовый аккаунт и создать новый набор. | Аккаунт, ключ и первый снимок подтверждены; потерянный ответ не приводит к созданию нового набора поверх прежнего. |
| 3 | На ПК B сохранить независимую копию и восстановить тот же набор основным паролем; отдельно повторить восстановление запасным ключом в другом чистом профиле. | Набор и корень совпадают; неверный секрет не заменяет локальные данные. Проверка версии ещё не является её применением. |
| 4 | На A менять по очереди персонажа, пати, прогресс марафона/сайта, финансы, ручное событие/задачу, повтор и выбранные настройки напоминаний. Сохранить и отправить. | В B видны различия нужных записей и полей. Cookies, статусы входа и местные пути не подменяются. Не выбранные настройки не стираются. |
| 5 | На B выполнить проверку. Отметить только часть записей; проверить «Выбрать все» и «Снять все». | Показаны отдельно дата облачного файла, время проверки, известное местное сохранение, источник и местный часовой пояс. Неизвестная дата остаётся неизвестной. По времени победитель не выбирается. |
| 6 | Включить автоотправку на A, сделать сохранение; отключить сеть и сохранить ещё раз, затем перезапустить и вернуть сеть. | Неотправленные данные остаются в зашифрованной очереди. После проверки реально отправленного потомка очередь освобождается. Статус проверки/подготовки не называется успешной отправкой. |
| 7 | При общей подтверждённой основе независимо править разные поддерживаемые поля на A и B. | Явное объединение сохраняет обе правки. Для одновременной правки одного поля требуется выбор; нет автоматической победы по дате. |
| 8 | Удалить ручную запись календаря на A, а на B изменить её до проверки. | Показывается подтверждённое удаление против правки; без отдельного выбора B не удаляет запись. После выбора удаления и проверенного потомка ID не воскрешается. В отдельном прогоне выбрать «Сохранить местную версию как новую задачу»: местные поля и отметки повторов переходят в новый ID, прежняя метка удаления остаётся; после перезапуска и отправки нет второй копии. |
| 9 | На A отдельно подготовить только тестовый Email и отправить. Потом отдельно подготовить тестовый пароль с предупреждением риска. | Категории независимы. Не выбранный телефон не добавляется. Значения отсутствуют в сравнении и журнале. Разрешения сбрасываются после операции. |
| 10 | После подготовки партии на A изменить местный тестовый пароль без новой ручной подготовки; сохранить обычные данные и отправить. | Новое местное значение не выгружается. В зашифрованных потомках сохраняется только ранее явно подготовленная приватная часть. |
| 11 | На B сравнить контакты, не отмечая поля. Затем с заранее сохранённой отдельной защищённой копией применить только одно поле; отдельно испытать явно пустой тестовый Email. | Без выбора и подтверждений замены нет. Пустое поле обозначено как очистка. Не выбранные контакты не меняются. Применение не включает автоматический экспорт местных секретов. |
| 12 | Входящая версия содержит новую секретную партию, а на B есть независимая публичная правка. | Обычное объединение по умолчанию блокируется. Отдельная галочка разрешает сохранить входящую зашифрованную партию в будущих версиях, **не заменяя местные контакты** и не выгружая их новые значения. Публичный конфликт всё ещё требует своего выбора. |
| 13 | Пока идёт диалог подтверждения, сменить выбор, версию или диск, где интерфейс это позволяет; затем повторить сравнение. | Устаревшее подтверждение не применяется к другому источнику. Не возникает успеха или молчаливого выбора новых данных. |
| 14 | После безопасного отключения сети перезапустить приложение и проверить возобновление операции с сохранённой отметкой. | Применяется только прежний pin и сохранённое решение. Если привязка/история/состояние изменились, операция останавливается. Служебные отметки вручную не удалять. |
| 15 | При выключенном vault повторить проверку контактов на синтетических данных; затем при включённом vault. | Облако в обоих режимах зашифровано. При выключенном vault локальные файлы и копии могут содержать открытые контакты. При недоступном vault пустые поля не выдаются за осознанную очистку. |
| 16 | Проверить запуск приложения с уже настроенным диском и журнал. | Стартовая проверка не применяет данные без выбора, не запускает игровые действия и не открывает секреты в журнале. |
| 17 | После появления конфликта удаления выбрать новую копию, затем сменить провайдера или местную правку до подтверждения. | Старое решение не применяется; копия не создаётся. «Выбрать все» не включает новую копию автоматически. |
| 18 | На тестовом стенде прервать подтверждённое создание копии после изменения очереди и перезапустить приложение. | v5-отметка восстанавливает тот же новый ID и прежний выбор, отправка до завершения заблокирована; резервная копия старого состояния доступна. |

### Дополнительный прогон архива пати

1. На A архивировать пати с основной и дополнительной ролью участников; включить в состав
   активного и архивного персонажа. На B независимо изменить заметку/характеристику и имя пати.
   После согласования обе правки должны сохраниться вместе с точными `memberLinks` и порядком.
2. Повторить восстановление пати в активный список, включая пати с меньшим `order`, чем у
   уже активных. Перезапуск не меняет согласованный порядок и не повреждает checkpoint.
3. На B перед сравнением изменить основную пати или порядок участника. Должен быть выбор
   всей связанной группы пати, а не молчаливое смешивание ролей; проверить обе стороны выбора.
4. На тестовом стенде прервать после изменения очереди, затем возобновить. До завершения
   отправка заблокирована; прежнее намерение не теряется, backup доступен, секреты не заменены.
5. Перенос разных пати с общим участником и новое членство только что созданного персонажа
   в переносимой пати должны безопасно остановиться. Это ещё не выполненные сценарии общей
   синхронизации связей. Пункты выше остаются планом, пока не выполнены на настоящих API.

## Сценарии, которые пока должны останавливаться

Следующие пункты — проверка безопасного отказа, **не выполненное требование полной
синхронизации**:

- Несколько расходящихся облачных голов или неподдерживаемая история.
- Отдельная неотправленная местная секретная партия, в том числе prepared-партия перед
  обычным queued-сохранением. Галочка сохранения входящего ciphertext не разрешает потерю
  этой партии и не является выбором между разными паролями.
- Неподдерживаемые удаления иных сущностей, неоднозначные изменения связей/порядка.
- Несовпадение аккаунта, ключа, принятой основы или состава выбранных настроек.
- Утрата ключей без доступной другой копии: расшифрование невозможно; старое облако
  автоматически не удаляется и не перезаписывается новым набором.
- Предел истории, неизвестный результат локальной записи или необходимость восстановления
  после частичного сбоя. Не «лечить» повтором отправки или ручной очисткой очереди.

Для испытаний питания, нескольких процессов и сбоев записи нужен отдельный стенд и анализ
реальных файлов/credential store. Успешная обычная перезагрузка этого не доказывает.

## Условие завершения приёмки

Сохранить результаты обоих провайдеров раздельно. Любая неисполненная строка остаётся
«не выполнялась», а безопасно остановленный неподдерживаемый сценарий не объявляется
реализованным объединением. Основной файловый режим остаётся экспериментальным до завершения его ограничений и
прохождения нового сквозного прогона на двух ПК. Незавершённые старые merge-сценарии
не следует выдавать за требования нового режима.

### Сборка владельцем для обычных пользователей

Владелец один раз настраивает OAuth у провайдеров. При сборке Rust:
`TVINOFERMA_GOOGLE_CLIENT_ID` + `TVINOFERMA_GOOGLE_CLIENT_SECRET`; при сборке Vite:
`VITE_YANDEX_CLIENT_ID`. Windows acceptance workflow берёт Google ID из одноимённой
repository variable, секрет из одноимённого Actions secret, Яндекс из variable
`TVINOFERMA_YANDEX_CLIENT_ID`. Не добавлять реальные значения в Git/PR/чат.
В этой правке реальные параметры **не созданы и не настроены**.

Без этих параметров используется разовый импорт/ввод на ПК. Пустая пара Google
считается отсутствием настройки; частичная/некорректная — ошибкой, а не рабочим клиентом.
Desktop client_secret, встроенный в exe, извлекаем пользователем и не считается
серверным секретом: защита авторизации остаётся PKCE + точный loopback + сверка аккаунта.
Загружать/хранить пользовательские refresh token в параметрах сборки запрещено.
Drive API, consent/test users и ограничения Testing по-прежнему настраиваются владельцем.

## Уточнение setup/identities (после PR145)

Сбой на базе пользователя остался: прежнее исправление новой карточки не доказало
причину именно его базы. В подготовке ID теперь есть безопасные коды по разделу и

имена полей, локальные ID, контакты и значения не используются в кодах. Каталог
фиксированный, хранится отдельно в WeakMap, error.code от внешнего объекта не читаем.

«Проверить данные без изменений» не требует пароля, OAuth или подтверждения нового
набора. Выполняет проверки на копии, отменяет план без commit; не вызывает saveNow,
loadData, backup, native или сеть. Это проверка структуры и roundtrip, НЕ проверка
доступности/актуальности сохранённого файла и не обещание успешной отправки. Кнопка
недоступна в браузере, при занятом мастере и пока ожидается подтверждение ключа.
Проверяется и база, где все sync-ID уже назначены (раньше был ранний выход).

Примеры: `setup/identities/ids.characters/sync_id`,
`setup/identities/public.characters.stats/unknown_field`,
`setup/identities/public.finance.operations/reference`,
`setup/identities/roundtrip.finance/reload_changes`.
При финансовой ссылке на отсутствующий объект не удаляем движение и не подставляем
null: отдельная проблема исторических ссылок требует решения, а не потери учёта.

Дополнительно воспроизведён другой реальный дефект: normalizeArchivedParty законно
сохраняет order:null у старого архива без номера, а exporter требовал число. Экспорт
теперь сохраняет null ТОЛЬКО в архиве; активные пати требуют прежнее число. Regression
RED до исправления, затем полный заполненный fixture (архив/пати/марафоны/шаблон/
планер/банк) проходит save → backup → ID commit → baseline → получение на другом
локальном состоянии → reload. Это всё ещё не доказывает причину базы пользователя.
