# Issues, проверки и тестовые сборки

## Где вести задачи

- GitHub Issues — актуальные требования, незавершённые проверки и решения об отказе от идеи.
- `ROADMAP.md` — автоматически обновляемый обзор прогресса по issues.
- `docs/ROADMAP-FULL.md` — исходный подробный план; старое описание пункта не доказывает отсутствие реализации.
- `CHANGELOG.md` — только сделанные изменения, сгруппированные по выпускам. Правила: [CHANGELOG-GUIDE.md](CHANGELOG-GUIDE.md).

Перед закрытием issue сверить описание с текущим кодом и тестами. Если реализация частичная
или нужна живая проверка Windows, не закрывать как выполненное. Если исходная идея заменена
другой компоновкой, указать замену и закрыть с причиной `not planned`, а не выдавать отказ за реализацию.
`roadmap.yml` обновляет обзор при изменениях issues; вручную исправлять его счётчики не нужно.

## CI

`ci.yml` сохраняет отдельные проверки качества интерфейса, полную регрессию PR четырьмя
группами и проверки Rust на Windows. Итоговая проверка `frontend` требует успеха всех
предусмотренных для события проверок. Тесты с защищённым хранилищем Windows используют
синтетические значения и не подменяются браузерными тестами.

Локальный action `.github/actions/setup-frontend` устанавливает Node 22 и восстанавливает
`node_modules` только по точному совпадению ОС, архитектуры, фактической версии Node и
`package-lock.json`. При промахе кэша выполняется `npm ci --no-audit --no-fund`.
Аудит npm остаётся отдельным информационным шагом, аудит Rust использует готовый cargo-audit.
Кэш не является подтверждением успешных тестов: проверки запускаются и при попадании в него.

В `release.yml` полная JS-регрессия выполняется четырьмя группами на Linux; сборка и создание
черновика Windows-релиза зависят от успеха всех групп. Это не отменяет проверок нативного кода.

## Тестовая сборка Windows

```sh
gh workflow run windows-acceptance.yml --ref <рабочая-ветка>
gh run list --workflow windows-acceptance.yml --branch <рабочая-ветка>
gh run download <номер-запуска> --dir <папка-для-артефакта>
```

Workflow собирает обычный неподписанный `.exe`, файл с исходным commit SHA и SHA-256.
Он не создаёт стабильный релиз, установщик или пакет автообновления. Артефакт хранится 14 дней.
Исходный SHA важнее встроенного номера версии для различения тестовых сборок.

Профиль данных тестового exe не изолирован от установленного приложения. Проверять на
отдельной тестовой учётной записи Windows; не запускать старую и новую копии одновременно.
Для контактов и предметов использовать [план приёмки](CONTACTS-AND-INVENTORY-ACCEPTANCE.md).
Никогда не помещать настоящие пароли, куки, токены и исходные пользовательские копии в issue.

## Стабильный выпуск

Версию повышать отдельным решением, подготовить раздел CHANGELOG относительно прошлого
стабильного тега, затем следовать [RELEASE.md](RELEASE.md). Успех тестовой сборки не означает,
что новая версия опубликована или сценарии на реальном ПК уже приняты.
