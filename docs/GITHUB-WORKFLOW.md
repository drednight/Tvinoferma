# Как вести роадмап на GitHub

Схема работы в одном абзаце: **каждый пункт роадмапа — это Issue**, версии — это **Milestones**, обзор и доска — это **GitHub Project**, а `ROADMAP.md` в репозитории показывает прогресс и обновляется сам. Править нужно только Issues.

| Что | Где живёт | Зачем |
| --- | --- | --- |
| Пункт роадмапа с описанием и чекбоксами | Issue | Единственный источник правды |
| Версия (v0.3, v0.4 ...) | Milestone | Полоса прогресса, группировка, заметки релиза |
| Приоритет, трудоёмкость, этап, тип | Labels | Фильтры и сортировка |
| Доска, таблица, таймлайн | Project | Удобный обзор |
| Публичный обзор для читателей репозитория | `ROADMAP.md` | Обновляется workflow |
| Подробный разбор, риски, решения | `docs/ROADMAP-FULL.md` | Справочник, редко меняется |

## 1. Первоначальная настройка (один раз, около 20 минут)

### Шаг 1. Положить файлы в репозиторий

Распакуйте архив в корень репозитория `drednight/Tvinoferma` (папки `.github`, `docs`, `scripts` и файл `ROADMAP.md` должны встать рядом с `package.json`).

```powershell
git checkout -b docs/roadmap
git add .
git commit -m "docs: роадмап, шаблоны Issues и PR, скрипты синхронизации"
git push -u origin docs/roadmap
```

Откройте Pull Request и влейте в `main`. Шаблоны Issues и workflow работают только из основной ветки.

### Шаг 2. Установить GitHub CLI

1. Скачайте с https://cli.github.com и установите.
2. Выполните вход: `gh auth login` (GitHub.com → HTTPS → через браузер).
3. Проверка: `gh auth status`.

### Шаг 3. Создать метки, версии и Issues одной командой

Сначала посмотрите, что будет создано, ничего не меняя:

```powershell
node scripts/roadmap/setup.mjs --dry-run
```

Потом запустите по-настоящему. Рекомендую начать с одной версии, проверить результат в браузере и добавить остальное:

```powershell
node scripts/roadmap/setup.mjs --version=v0.2.3
node scripts/roadmap/setup.mjs
```

Что делает скрипт:
- создаёт 27 меток (`prio/*`, `effort/*`, `source/*`, `type/*`, `stage/00`–`stage/13`);
- создаёт 10 вех (v0.2.3 ... v1.0, «После 1.0»);
- создаёт 69 Issues с названием вида `[0.1] Заголовок`, описанием, чекбоксами, метками и вехой;
- безопасен при повторном запуске: пункты, которые уже есть (по префиксу `[0.1]`), пропускаются;
- делает паузу 1,5 с между Issues, чтобы не упереться в лимиты GitHub.

Скрипт я не мог запустить на вашем репозитории (нет доступа), проверен только режим `--dry-run`. Если на каком-то шаге появится ошибка, пришлите текст, поправлю.

### Шаг 4. Создать Project (доска)

1. Репозиторий → вкладка **Projects** → **New project** (или профиль → Projects → New project).
2. Шаблон **Table**, название «Tvinoferma Roadmap».
3. Добавьте Issues: в проекте нажмите **+** → **Add item from repository** → выберите все, либо включите автодобавление (шаг 5).
4. Настройте **три вида** (кнопка «New view»):

| Вид | Тип | Настройки |
| --- | --- | --- |
| **Доска** | Board | Group by: **Status** (Todo / In Progress / Done). Колонки можно переименовать на «Не начато / В работе / Готово» |
| **По версиям** | Table | Group by: **Milestone**. Поля: Labels, Assignees, Status. Сортировка по номеру |
| **Таймлайн** | Roadmap | Нужны даты: добавьте поле **Target date** (Date) и задайте даты версий (см. ниже) |

5. Полезные встроенные автоматизации (Project → ⋯ → **Workflows**): *Item closed → Status = Done*, *Item reopened → Status = In Progress*, *Auto-add to project* (фильтр `is:issue is:open`), *Auto-archive items* (закрыты более 14 дней).

**Как сделать таймлайн.** У версий в GitHub есть поле Due date: Issues → Milestones → выберите версию → Edit → Due date. В Project добавьте поле **Milestone** в отображение и, для таймлайна, поле дат **Target date** (в виде Roadmap «Date fields» выберите его). Если сроки пока неизвестны, не задавайте их: честнее оставить версии без дат, чем с придуманными.

### Шаг 5. Включить автоматизацию (по желанию)

**а) Автообновление `ROADMAP.md`.** Уже настроено в `.github/workflows/roadmap.yml`. Проверьте:
- Settings → Actions → General → **Workflow permissions** → *Read and write permissions*;
- если ветка `main` защищена правилом «только через Pull Request», у workflow не будет права пушить. Варианты: разрешить боту обход в настройках правила либо запускать `node scripts/roadmap/render.mjs` вручную и коммитить.
- Первый запуск: вкладка **Actions** → *Roadmap progress* → **Run workflow**.

**б) Автодобавление Issues в Project через Actions** (если не хватило встроенной автоматизации). Файл `.github/workflows/add-to-project.yml`:
- Settings → Secrets and variables → Actions → **Variables** → `PROJECT_URL` = адрес проекта;
- **Secrets** → `ADD_TO_PROJECT_PAT` = personal access token с правом `project`.
Без этих настроек workflow просто не запускается.

### Шаг 6. Подсказки в README

Добавьте строку в `README.md`:

```md
Планы развития: [ROADMAP](ROADMAP.md) · [Issues](../../issues) · [Предложить идею](../../issues/new/choose)
```

## 2. Как вести роадмап изо дня в день

### Взять пункт в работу
1. Откройте Issue, назначьте себя (**Assignees**), в Project перетащите карточку в «В работе».
2. Создайте ветку, название по шаблону `тип/номер-коротко`:

```powershell
git checkout -b fix/12-balance-decimal
```

Типы: `fix/` ошибка, `feat/` функция, `chore/` инфраструктура, `docs/` документы.

### Коммиты
Формат Conventional Commits (пригодится для автогенерации CHANGELOG):

```
fix(balance): учитывать дробную часть монет (#12)
feat(parties): несколько партий у персонажа (#13)
test(parsers): фикстура страницы chests2.php (#14)
```

Префиксы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `perf`.

### Закрыть пункт
В описании Pull Request напишите `Closes #12`. После слияния Issue закроется сам, карточка уйдёт в «Готово», а `ROADMAP.md` получит галочку.

Отмечайте чекбоксы внутри Issue по мере работы: GitHub показывает прогресс (`3 of 7`) в списках.

### Выпуск версии
Когда у вехи все Issues закрыты:

1. Проверьте: Issues → Milestones → версия показывает 100%.
2. Поднимите версию и поставьте тег, как описано в `docs/RELEASE.md`:
   ```powershell
   npm run version:bump 0.3.0
   git commit -am "chore: версия 0.3.0"
   git push
   git tag v0.3.0
   git push origin v0.3.0
   ```
3. Дождитесь сборки (**Actions → Release**), откройте черновик релиза. Нажмите **Generate release notes**: GitHub соберёт список по закрытым Pull Request.
4. Опубликуйте релиз (**Publish release**), без этого автообновление его не увидит.
5. Закройте веху: Milestones → версия → **Close**. Незакрытые пункты перенесите в следующую веху (в Issue справа выберите Milestone).

## 3. Как менять сам роадмап

| Ситуация | Что делать |
| --- | --- |
| Появилась новая идея | **New issue → Идея или предложение**. Потом выставьте метки приоритета и этапа и веху. Вносить её в `ROADMAP.md` не нужно |
| Пункт нужно перенести в другую версию | В Issue поменять **Milestone**. `ROADMAP.md` обновится сам |
| Изменился приоритет | Заменить метку `prio/...` |
| Пункт слишком большой | Разбить на подзадачи: в Issue добавьте список чекбоксов, а затем кнопкой у чекбокса «Convert to issue» превратите их в отдельные Issues. GitHub свяжет их как sub-issues |
| Пункт отменён | Закрыть Issue с причиной «Close as not planned» и комментарием, почему |
| Хотите изменить описание в полном документе | Правьте `docs/ROADMAP-FULL.md` обычным коммитом |
| Нужно пересоздать Issue | Закройте старый, запустите `setup.mjs --only=0.1` (старый с таким префиксом тоже считается существующим: удалите его или переименуйте префикс) |

Правила, чтобы роадмап не превращался в свалку:
1. **У каждого открытого Issue есть веха.** Идеи без срока складывайте в «После 1.0».
2. **В «В работе» не больше 2–3 карточек.** Начатое важнее нового.
3. **Раз в неделю 10 минут разбор** (триаж): новые Issues → метки и веха; зависшие в «В работе» → вернуть или закрыть.
4. **Раз в релиз** пересмотр вех: что реально успеете, остальное в следующую.
5. Пункты из `ROADMAP-FULL.md` пока лежат как задумки. Уточняйте описание в Issue перед началом работы, особенно для автоматизации (проверьте правила сайта, см. раздел 3 полного документа).

## 4. Полезные команды `gh`

```powershell
gh issue list --milestone v0.3                      # открытые задачи версии
gh issue list --label prio/critical,type/bug       # срочные ошибки (метки через запятую = И)
gh issue list --assignee @me                        # мои задачи
gh issue view 12 --web                              # открыть в браузере
gh issue close 12 --reason completed                # закрыть как выполненный
gh issue edit 12 --milestone v0.4 --add-label prio/high --remove-label prio/medium
gh pr create --fill --body "Closes #12"            # Pull Request, связанный с Issue
gh release create v0.3.0 --generate-notes --draft  # черновик релиза с автозаметками
node scripts/roadmap/render.mjs                    # обновить ROADMAP.md вручную
```

## 5. Что важно знать

- **Публичность.** Если репозиторий публичный (а он должен быть, иначе автообновление не скачает `latest.json`), Issues и роадмап видят все. Не публикуйте в Issues пароли, логины, куки, личные данные и точные правила обхода защиты сайта.
- **Доступ к Project.** Project можно сделать приватным, даже если репозиторий публичный. Для личных заметок и неподтверждённых идей держите отдельный приватный Project либо ваш Notion/Obsidian.
- **Названия `[0.1]` в заголовках Issue менять нельзя.** По ним `ROADMAP.md` сопоставляет пункты с Issues. Остальную часть названия править можно (но тогда в `ROADMAP.md` останется старый текст; он берётся из `scripts/roadmap/items.json`).
- **Автоматизация с учётными записями игры** (промокоды, переводы, инжекция) запускайте в разработку только после вывода по правилам сайта. Он должен быть записан в `docs/COMPLIANCE.md` (пункт 1.7 роадмапа).
- **Откат.** Если создали лишнее скриптом: `gh issue list --label stage/04 --json number -q ".[].number" | ForEach-Object { gh issue delete $_ --yes }` удалит Issues этапа (PowerShell). Метки и вехи удаляются в интерфейсе.
