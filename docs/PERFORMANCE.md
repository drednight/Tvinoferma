# Аудит ресурсов для 1.1.1

## Что проверено

Исходный код интерфейса и Rust: таймеры, очередь браузерных задач, закрытие окон,
подписки, журналы, резервные копии, файлы состояния и временные данные OCR.
Локальные проверки выполнялись в Linux / Chromium / Vite на шести вымышленных
персонажах. Реальных запросов к аккаунтам, покупок и передач не было.

**Это не замер Windows-приложения.** JS heap не равен памяти приложения; метрика
Chromium TaskDuration не включает все процессы браузера, WebView2, GameCenter,
игру и работу ОС. По этим проверкам нельзя обещать конкретный расход системной RAM/CPU.

## Подтверждённые проблемы и исправления

| Участок | Проблема | Исправление |
| --- | --- | --- |
| Обычные модальные формы | После закрытия кнопкой оставался document-обработчик Escape | Единый жизненный цикл: очистка при кнопке, Escape, замене и программном закрытии |
| Вложенные окна и подписки | Удаление через корневой контейнер могло миновать close() | Зарегистрированные окна закрываются через их API, с отпиской и отменой фоновых операций |
| Плашки задач | notify() обновлял карточку, затем renderDock() повторно пересоздавал весь док | Полная перестройка только при изменении состава; чужие плашки сохраняются |
| Полный журнал | Каждая строка заново строила весь список, фильтр сбрасывался | Обновление пачками не чаще раза в 100 мс; фильтр сохраняется и таймер очищается при закрытии |
| Фоновая проверка входа | setInterval мог запускать новые пачки, пока старая ещё шла | Флаг выполнения и проверка ручных задач; новая пачка ждёт следующего интервала |
| Копии в браузере | Параметр maxCount не учитывался, ключи накапливались | Ротация по лимиту, уникальные ключи и сохранение прежних копий при ошибке |

Регрессии проверяются в `modalLifecycle.test.js`, `desktopBackground.test.js`,
`browserBackups.test.js`, `taskLogJournal.test.js`. Для производительности важна
не только скорость одного клика, но и отсутствие накапливающихся обработчиков.

## Какие ограничения уже есть

- Общий семафор фоновых скриптов: по умолчанию три одновременные задачи (`queue.js`).
- Пул Rust: не более четырёх общих воркеров; свободный воркер закрывается после
  15 секунд простоя (`pool.rs`). Окна профиля закрываются, если операция запросила `closeAfter`.
  Видимые окна входа и запущенная пользователем игра сами по себе не закрываются.
- Журнал скриптов: до 300 задач и 500 строк на задачу. Завершённые задачи сохраняются;
  при переполнении localStorage старые записи сокращаются. Промокоды: до 50 записей;
  передача и подарки: до 300 записей каждого вида.
- Запись состояния выстраивается в очередь и схлопывает одновременные вызовы.
  Rust пишет один временный `state.json.tmp`, синхронизирует и переименовывает его.
  Успешные записи не создают по новому постоянному временному файлу на каждый клик.
- Резервные копии Windows ротируются в `commands/backup.rs`; браузерные теперь тоже
  учитывают лимит. При восстановлении Windows сохраняет дополнительную копию текущего состояния.
- OCR работает через буфер в памяти, без серии временных файлов изображений.

Лимиты количества записей **не являются лимитами в мегабайтах**: длинные сообщения,
предметы и большие наборы данных могут увеличивать объём даже при ротации.

## Где сохраняются данные и что может расти

- `state.json`: основные данные; обычные резервные копии — рядом, с ротацией.
- `pw-sync-profiles/`: профили персонажей и служебные профили пула. Куки нужны для
  сохранения входа; дисковый кэш WebView2 не имеет введённого приложением лимита размера.
- `cookie-bank/`: зашифрованные сессии. Удаление карточки не означает автоматически
  удаление всей соответствующей папки WebView; старые профили могут оставаться.
- Журналы и настройки скриптов находятся в localStorage профиля приложения.
- `state.broken-*.json`: сохранённые копии повреждённого состояния; они не участвуют
  в обычной ротации бэкапов. При повторных ошибках запуска их может стать больше.

Не удаляйте профили, банк сессий, state.json или повреждённые копии автоматически
по имени/возрасту: можно потерять входы или возможность восстановить данные.
Этот релиз **не очищает профили и восстановительные файлы без согласия пользователя**.

## Как проверить установленное приложение на Windows

1. Создайте резервную копию и используйте тестовые аккаунты. Запишите версию Windows,
   процессор, RAM, версию WebView2, число персонажей и параллельность скриптов.
2. В диспетчере задач учитывайте Твиноферму и её дочерние процессы WebView2 вместе.
   GameCenter и игровые клиенты фиксируйте отдельно, иначе расход игры будет ошибочно
   приписан приложению.
3. После двух минут прогрева наблюдайте простой пять минут. Затем откройте и закройте
   формы сто раз, переключите разделы, выполните разрешённые проверки сайта с обычной
   и уменьшенной параллельностью. Настоящие покупки для этого не нужны.
4. После завершения задач подождите освобождения воркеров, затем ещё одну минуту.
   Повторите одинаковый цикл три раза. Ищите продолжающийся рост RAM, числа окон,
   дескрипторов и нагрузки в простое, а не только краткий пик во время работы.
5. До и после циклов измерьте папку приложения, отдельно `pw-sync-profiles`,
   `cookie-bank`, обычные бэкапы и восстановительные файлы. Проверьте, что количество
   обычных бэкапов после создания новой соответствует лимиту.
6. Если рост продолжается, приложите только обезличенные показатели и журналы.
   Не публикуйте профили WebView, банк сессий, файлы с паролями или экспорт аккаунтов.

Решение о лимите/очистке кэша WebView2 следует принимать после этих замеров и
отдельно проверять, что оно не сбрасывает входы и не удаляет ещё работающие профили.
