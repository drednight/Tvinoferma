# НОВЫЙ РОАДМАП (рабочий)

> Отличается от `ROADMAP.md`. Тот — публичный трекер по Issues/версии. Этот — рабочий документ с конкретными правками, привязкой к файлам и правилами «зачем/чем поможет».

## §0. Как пользоваться
- **Формат пункта:** проблема → зачем → что сделать → где → как проверить
- **Приоритеты:** `критично` / `важно` / `желательно`
- **Правило по дизайну:** косметика только там, где улучшает читаемость/юзабилити. Иначе не трогать. Новое — по токенам темы, не вводить параллельные шкалы.

## §1. Критичные правки

### 1.1. Умная очередь запуска (FIFO + устойчивость)
- **Приоритет:** критично
- **Проблема:** очередь работает по FIFO, но недостаёт видимости и жёсткой устойчивости при сбоях/перезагрузках.
- **Зачем:** меньше путаницы при запуске нескольких партий, меньше «зависших» задач.
- **Что сделать:**
  - В UI очереди явно показывать: «выполняется», «№ в очереди», «кто следующий». Снять задачу из очереди до старта.
  - Распространить обработку квоты `localStorage` на `saveJournal()` (по образцу `localStorageAdapter` / `logStore`).
  - Продумать ротацию журнала очереди (лимит записей) чтобы не раздувать `localStorage`.
  - Проверить краевые случаи восстановления `running`-задач.
- **Где:** `js/core/taskLog.js`, `js/modules/launcher/partyLaunch.js`, `js/modules/launcher/launch.js`, `tests/launchQueue.test.js`, `tests/taskLogJournal.test.js`
- **Как проверить:** запустить несколько партий → очередь корректна. Эмулировать `QuotaExceededError` → нет падения, задача не теряется бесследно. Перезагрузка при `running` → в журнале есть пометка «Прервано: ...».

### 1.2. Экран проверки (preflight)
- **Приоритет:** критично
- **Проблема:** диалог предзапуска нуждается в доработке UX.
- **Зачем:** быстрее и безопаснее запуск, меньше ошибок.
- **Что сделать:**
  - `Esc` = отмена, `Enter` = основное действие (с учётом контекста).
  - Фокус-трап, возврат фокуса при закрытии.
  - Не блокировать остальной UI при долгих проверках.
  - Сохранить идемпотентный `settle(result)` + флаг `settled` + `MutationObserver` (защита от удаления `.tf-overlay` мимо `close()`).
- **Где:** `js/modules/launcher/preflightDialog.js`, `js/modules/launcher/preflight.js`, `tests/preflight.test.js`
- **Как проверить:** `npm test -- tests/preflight.test.js` зелёный. Ручной прогон: клавиатурой, удаление оверлея не ломает возврат результата.

### 1.3. Журнал задач
- **Приоритет:** критично
- **Проблема:** журнал полезен, но нужно доработать надёжность и удобство просмотра.
- **Зачем:** дебаг очереди/запусков, меньше догадок при инцидентах.
- **Что сделать:**
  - Обработка квоты при сохранении (как в 1.1).
  - Ротация по кол-ву записей (настраиваемый/разумный лимит).
  - Фильтры/поиск по сообщению/уровню/области.
  - Экспорт журнала при необходимости.
- **Где:** `js/core/taskLog.js`, `js/modules/launcher/launchLogView.js`, `js/modules/launcher/launchLog.js`, `tests/taskLogJournal.test.js`, `tests/taskLogNick.test.js`
- **Как проверить:** заполнить журнал → фильтры работают. При нехватке места — без краша, с осмысленным поведением.

### 1.4. Устойчивость парсеров
- **Приоритет:** критично
- **Проблема:** при изменении вёрстки игры парсеры ломаются тихо/непонятно.
- **Зачем:** меньше регрессий, проще диагностика.
- **Что сделать:**
  - Единый контракт ошибок через `errorCodes.js`.
  - Отображение здоровья парсеров в UI через `parserHealth.js`.
  - Тесты на «сломанную вёрстку».
- **Где:** `js/core/errorCodes.js`, `js/core/parserHealth.js`, `js/modules/marathons/*`, `js/modules/runes/*`, `js/modules/servers/*`, `tests/parsers.test.js`, `tests/parserHealth.test.js`
- **Как проверить:** симулировать поломку парсера → в UI виден статус, ошибка читаемая.

### 1.5. Данные и хранилище
- **Приоритет:** критично
- **Проблема:** миграции, квота, экспорт настроек требуют аккуратности.
- **Зачем:** безопаснее обновления, предсказуемее поведение.
- **Что сделать:**
  - Версионирование схемы в `migrations.js`.
  - Распространить защиту от квоты на все места записи в `localStorage`.
  - Продумать более аккуратный экспорт/импорт с учётом `secrets.js` (без утечки секретов).
- **Где:** `js/core/migrations.js`, `js/core/storage.js`, `js/core/secrets.js`, `js/core/storageAdapters/localStorageAdapter.js`
- **Как проверить:** миграция со старой схемы проходит. Квота не валит приложение.

## §2. Удобство

### 2.1. Командная палитра
- **Приоритет:** важно
- **Зачем:** быстрый доступ ко всем действиям.
- **Что сделать:** расширить команды, добавить нечёткий поиск.
- **Где:** `js/core/commandPalette.js`, `js/core/commandPaletteData.js`
- **Как проверить:** поиск по фрагменту находит нужное действие.

### 2.2. Длинные списки (виртуализация)
- **Приоритет:** важно
- **Проблема:** виртуализации нет. При росте партий/персонажей/логов DOM растёт.
- **Зачем:** меньше лагов, меньше памяти.
- **Что сделать:** добавить виртуализацию через `IntersectionObserver`/подходящую реализацию там, где списки действительно длинные (партии, персонажи, логи).
- **Где:** `js/modules/parties/*`, `js/modules/characters/*`, `js/modules/launcher/launchLogView.js`, `js/core/taskLog.js`
- **Как проверить:** большой список скроллится плавно, элементов в DOM меньше видимых.

### 2.3. Логи и уведомления
- **Приоритет:** важно
- **Зачем:** меньше шума, больше контроля.
- **Что сделать:** ротация/уровни/фильтр по источнику в `logStore`/`logHub`; группировка и непрочитанные в `notifyCenter`/`navBadges`.
- **Где:** `js/core/logStore.js`, `js/core/logHub.js`, `js/core/notifyCenter.js`, `js/core/navBadges.js`
- **Как проверить:** фильтры логов работают, бейджи обновляются корректно.

### 2.4. Горячие клавиши и доступность
- **Приоритет:** важно
- **Зачем:** удобнее опыт, лучше доступность.
- **Что сделать:** единый реестр хоткеев; расширить `:focus-visible` на таблицы/строки/карточки/кастомные контролы; клавиатурная навигация в таблицах; корректные `aria-*` где не хватает.
- **Где:** `js/core/*` (общие), `css/core/base.css`, `css/core/components.css`, модули с таблицами/меню
- **Как проверить:** навигация с клавиатуры без мыши. Фокус виден всегда при `Tab`.

## §3. Эстетика дизайна: где стоит и где не надо

### 3.1. Токены
- **Приоритет:** важно
- **Факт:** в `css/core/variables.css` есть `--radius-lg/md/sm/xs/pill`, `--shadow-1/2/3`, `--gap-xs/sm/md/lg` (4/8/12/16/24), `--topbar-h/--sidebar-w/--content-max`, `--speed/--ease/--focus-ring`. **Нет** `--space-*`.
- **Что сделать:** использовать только существующие токены. Алиасы `--radius`/`--radius-sm`/`--shadow` трогать аккуратно. Новые компоненты — по шкале. В `variables.css` — только добавления/документирование. Замены — в модулях.
- **Где:** `css/core/variables.css`, `css/modules/*.css`
- **Как проверить:** нет новых магических `px` там, где есть токен.

### 3.2. Фокус и клавиатура
- **Приоритет:** важно
- **Факт:** `:focus-visible` уже реализован в `base.css`, `components.css`, `fab.css`, `notify.css`, `taskLog.css`.
- **Что сделать:** расширить покрытие на таблицы, строки таблиц, карточки, кастомные селекты/кнопки. Всегда использовать `--focus-ring`.
- **Где:** `css/core/base.css`, `css/core/components.css`, `css/modules/*.css`
- **Как проверить:** видимый фокус при Tab во всех интерактивных элементах.

### 3.3. Скроллбары
- **Приоритет:** важно
- **Факт:** стили скроллбаров уже есть.
- **Что сделать:** согласовать толщину/цвет/радиус во всех скроллируемых контейнерах (модалки, таблицы, командная палитра).
- **Где:** `css/core/*`, `css/modules/*`
- **Как проверить:** визуально консистентны во всех местах.

### 3.4. Движение
- **Приоритет:** важно
- **Факт:** `prefers-reduced-motion` уже есть в `base.css:140`, `serverStatus.css:123`, `taskLog.css:302`, `update.css:35`.
- **Что сделать:** расширить покрытие на все новые анимации/переходы. Не анимировать ради анимации. Использовать `--speed`/`--ease`.
- **Где:** `css/core/*`, `css/modules/*`
- **Как проверить:** в режиме `prefers-reduced-motion: reduce` анимации минимальны/отключены.

### 3.5. Плотность и таблицы
- **Приоритет:** важно
- **Зачем:** читаемость и меньше визуального шума.
- **Что сделать:** единые высоты строк, отступы по `--gap-*`, числа выравнивать вправо, использовать `tabular-nums` там, где цифры.
- **Где:** `css/modules/*` (таблицы), `css/core/components.css`
- **Как проверить:** колонки с числами ровные, отступы консистентны.

### 3.6. Состояния элементов
- **Приоритет:** важно
- **Зачем:** предсказуемый UX.
- **Что сделать:** унифицировать `hover/active/disabled/loading`. Использовать статус-цвета из токенов (`--success/warning/danger/gold` и soft-варианты).
- **Где:** `css/core/components.css`, `css/modules/*.css`
- **Как проверить:** все состояния различимы и не конфликтуют с фокусом.

### 3.7. Чего НЕ трогать
- **Приоритет:** критично (правило)
- **Не трогать:** общую тёмную палитру, `--topbar-h`, `--sidebar-w`, `--content-max` (только без необоснованных правок), уже существующие скроллбары/фокус/reduced-motion (только расширять). **Не** вводить `--space-*` параллельно с `--gap-*`. Не править радиус/тени глобально без веской причины.

## §4. План действий

1. **Подготовка** — прочитать затронутые файлы, убедиться в консистентности с токенами.
2. **Критичные правки (§1)** — очередь/журнал/preflight/парсеры/хранилище. Сопровождать тестами.
3. **Удобство (§2)** — палитра/виртуализация/логи/уведомления/доступность.
4. **Дизайн (§3)** — точечные правки по токенам, без глобального рефакторинга.
5. **Проверка** — `npm run lint && npm run typecheck && npm test` (или `npm run check`). При необходимости `npm run shots`.
