# Очередь запуска: жалоба, разбор и что проверять

Документ для проверки с другого ПК. Описывает жалобу, что уже сделано, что нашлось в
журнале задач, где в коде смотреть и как воспроизвести проверку.

---

## 1. Жалоба (дословно)

> «То что нажимается - ставится в очереди после того, что уже было добавлено, а не вместо
> него. У меня шел скрипт запуска пати, но он сбился при том, что я начал запускать
> одиночных персонажей.»

Разбор по частям:

- «то, что нажимается, ставится в очереди **после** того, что уже было добавлено» —
  новый запуск встаёт в конец очереди и ждёт всех, кто встал раньше.
- «**а не вместо него**» — ожидалось, что нажатый персонаж встаёт на место уже стоящих в
  очереди, то есть пойдёт следующим (или прервёт текущий запуск).
- «у меня шёл скрипт запуска пати, но он сбился» — запуск пати прервался/пропал.

**Что осталось неясным (нужен ответ):** «вместо него» — это «перед теми, что уже в очереди»
(новый клик идёт следующим) или «вместо текущего идущего» (новый клик прерывает пати)?
Это две несовместимые семантики, поэтому очередь сейчас оставлена как есть (FIFO), а вопрос
вынесен пользователю. См. §6.

---

## 2. Как работает очередь сейчас

Очередь запуска — это общая очередь док-задач в шапке, а не отдельный механизм лаунчера.

| Шаг | Место в коде |
|---|---|
| Задача создаётся сразу, до проверок | `js/modules/launcher/partyLaunch.js` → `launchGroup()` (строка 233) |
| Задача встаёт в очередь, если в доке есть другая идущая | `js/core/taskLog.js` → `startTask()` → `enqueueIfBusy()` (строка 252) |
| Запуск ждёт своей очереди | `launchGroup()` → `await task.waitTurn()` (строка 236) |
| Очередь продвигается | `Task.finish()` → `startNextQueued()` (`js/core/taskLog.js`, строки 232 и 263) |

Важные детали:

- Проверки (preflight) идут **после** ожидания очереди. Иначе «окна уже запущены»
  считались бы по окнам чужого, ещё не закончившегося запуска, и персонаж был бы пропущен.
- Порядок — FIFO: первым встаёт тот, кто ждёт дольше всех (`startNextQueued()` берёт
  `[...tasks].reverse().find(t => t.waiting)`).
- Ждущий снимается крестиком прямо в списке задач (`data-dock-cancel`); отменённый в очереди
  закрывается как «Отменён в очереди» и очередь не держит.
- Блокировки «Запуск уже идёт» больше нет: счётчик `activeLaunches`, функция
  `isLaunching()` экспортируется, но нигде не используется.

## 3. Что нашлось в журнале задач (факты, а не догадки)

Журнал лежит в `localStorage` приложения, ключ **`tf_task_journal_v1`**.
У dev-сборки origin — `http://localhost:1420`, у установленного приложения — `http://tauri.localhost`,
это **разные** localStorage, поэтому журналы не смешиваются.

Запуск 22.10.2026, dev-приложение (время в журнале — UTC, в тексте ниже МСК):

| Задача | Начало | В очереди? | Итог |
|---|---|---|---|
| Запуск игры: Кном | 14:07:38 (17:07 МСК) | нет, пошёл сразу | 1 окно за 11 с |
| Запуск игры: Кукумбер | 14:07:51 (17:07) | да | освободилось место в 14:07:59 |
| Запуск игры: Cheery_diona | 14:08:07 | да | освободилось место в 14:08:18 |
| Запуск игры: Огонек | 14:08:10 | да | освободилось место в 14:08:53, отменён на экране проверки |
| Запуск игры: Banshee | 14:08:11 | да | освободилось место в 14:08:59 |

У всех, кроме первого, в журнале ровно две служебные строки:

```
В очереди: жду завершения текущего скрипта
Начато: освободилось место, запускаюсь
```

**Вывод: очередь работает как задумано — по одному, в порядке нажатий.** Отдельно: первый
запуск (Кном) пошёл сразу без ожидания, значит в момент 17:07:38 МСК док был свободен.

**Главное противоречие с жалобой: запуск пати 22.10 в журнале НЕТ вообще** — ни dev, ни в
установленном приложении. В установленном приложении единственный запуск пати за день —
«Запуск игры: Просперята» от 2026-10-22T12:48:46Z (15:48 МСК): 10 запрошено, 9 ок, 1 уже
запущено, 147 с. Это за час до сессии в dev, и там старая версия кода (2.2.0, без очереди).

## 4. Почему запуск пати «сбился» — и это не очередь

Хронология по логу Vite dev-сервера (терминал `npm run tauri dev`):

```
17:06:33  Запущено приложение (dev)
17:07:16  page reload js/modules/launcher/partyLaunch.js     ← перезагрузка страницы
17:07:17  console.warn: IPC custom protocol failed ... at js/modules/launcher/launch.js:29:41
                  at async js/modules/launcher/launch.js:591:16
                  at async Object.run (js/modules/sync/queue.js:20:20)
17:07:25  page reload js/modules/launcher/partyLaunch.js     ← ещё одна перезагрузка
17:07:28  [TAURI] Couldn't find callback id 1405402025 ...
17:07:38  первый одиночный запуск (Кном) — пошёл сразу
```

Читается однозначно:

1. В 17:07:1x шёл запуск (строка `launch.js:591` — это `invoke('launcher_start', …)`, общий
   код и для пати, и для одиночных персонажей). Это и был «скрипт запуска пати».
2. В 17:07:16 страница перезагрузилась — **это HMR от моей правки `partyLaunch.js` во время
   работы приложения**. JS-состояние приложения при этом обнуляется: задача пати исчезла из
   дока, а её Rust-часть продолжала работать (отсюда «Couldn't find callback id» в 17:07:28 —
   callback потерялся, а окно игры продолжает открываться).
3. Первый одиночный запуск в 17:07:38 пошёл сразу, потому что док к этому моменту был уже
   свободен (перезагрузка убила задачу пати).

**Итог: запуск пати в этой сессии потерялся из-за перезагрузки страницы (моя правка кода
через HMR), а не из-за очереди.** Пользователь увидел, что пати исчезла, и связал это с
нажатиями по одиночным персонажам — нажатия шли сразу следом.

Отсюда же видно настоящий пробел в коде: **идущая задача не пишется в журнал, пока не
закончилась.** После перезагрузки страницы/перезапуска приложения она исчезает бесследно —
никакой записи «прервано». Это стоит чинить (см. §7).

## 5. Живая проверка (22.10, dev-приложение)

Кнопка «▶ Запустить» в карточке пати работает: клик создаёт задачу «Запуск игры: Основная
пати», док показывает её и шаг «#Дреднайт: запуск…», запуск идёт (проверка отработала, экран
проверки не показывался). Запуск остановлен кнопкой ■ — в журнале появляется
«Остановлено: работа прервана на середине», очередь при этом освобождается.

Во время этой проверки случайно открылись три окна игры (#Дреднайт, Ластэнд, ТобиоЗак) —
они закрыты через `closeClientsByPid`. На другом ПК повторять без необходимости не стоит:
запуск пати реально открывает окна игры.

## 6. Что нужно от пользователя (один вопрос)

Фраза «а не вместо него» допускает два прочтения, и они дают разное поведение:

- **А. Новый клик идёт следующим.** Текущий скрипт доводится до конца, но нажатый персонаж
  встаёт перед теми, кто уже стоял в очереди (а не после них). Ничего не прерывается.
- **Б. Новый клик прерывает текущий запуск.** Запуск пати останавливается, нажатый персонаж
  стартует сразу. Минус: часть окон пати уже открыта, они останутся висеть.

Сейчас работает вариант «в конце очереди» (FIFO). Если нужен А или Б — скажите какой,
правка небольшая: очередь задач в `js/core/taskLog.js` (`startNextQueued()`), порядок выбора
там же (`[...tasks].reverse().find(t => t.waiting)`).

## 7. Что предлагается чинить (по убыванию важности)

1. **Идущая задана не переживает перезагрузку страницы** — записать её в журнал при старте и
   при загрузке помечать как «Прервано: приложение перезапущено». Сейчас пропадает молча,
   и это выглядит как «запуск сбился».
2. **Зависшая задача блокирует очередь навсегда.** Если задача осталась в статусе `running`,
   а её скрипт умер (исключение мимо `catch`, закрытие окна), все следующие клики уходят в
   очередь и ничего не выполняется. Стоит подстраховаться: при старте новой задачи, если
   блокирующая задача «жива» (растёт `updatedAt`), предупредить; если нет — снять её.
3. **Экран проверки (`openPreflight`, `js/modules/launcher/preflightDialog.js`) обязан всегда
   отдавать результат.** **Сделано.** Добавлены идемпотентный `settle(result)` с флагом `settled` и `observer?.disconnect()`, `onClose: () => settle(answer)`, `MutationObserver` на `documentElement` (subtree/childList) для отлова удаления `.tf-overlay` мимо `close()` — при срабатывании вызывает `dlg.close()` и `settle(answer)` (также покрывает замену/очистку `#modal-root`). В `tests/preflight.test.js` добавлены два теста: «оверлей убрали из DOM мимо close()» и «затёрли весь #modal-root». **Осталось:** прогнать `npx vitest run tests/preflight.test.js --reporter=verbose`, затем `npm run check`, сделать коммит `fix(проверка): экран проверки всегда отдаёт результат` и `git push` в `origin/feat/tools-groups` (PR не создавать). Если его промис не разрешится (esc/закрытие окна), задача останется `running` и заблокирует очередь — пункт 2 покрывает и этот случай.

## 8. Как проверить с другого ПК

Нужно: Node, Rust (tauri), `npm install`.

```bash
git pull
npm install
npm run tauri dev          # Vite на :1420, приложение открывается само
```

Сценарий (нужна пати из 2–3 персонажей и один-два отдельных персонажа):

1. Вкладка «Пати» → «▶ Запустить» у пати. В шапке появляется плашка «Запуск игры: <пати>».
2. **Не дожидаясь конца** перейти на «Персонажи» → «▶» у одного-двух персонажей.
3. В списке задач в шапке у них должно быть «в очереди — ждёт завершения текущего скрипта»
   и крестик ✕ для отмены. После освобождения места — «Начато: освободилось место, запускаюсь».
4. Проверить, что порядок соблюдён: кто встал раньше, тот и пошёл раньше.

Посмотреть журнал без DevTools (в dev-приложении origin — `http://localhost:1420`):

```js
// в консоли DevTools или через CDP
JSON.parse(localStorage.getItem('tf_task_journal_v1'))
  .slice(0, 10)
  .map(t => [t.startedAt, t.status, t.title, t.summary])
```

Через CDP без DevTools (нужен запущенный webview с отладочным портом):

```bash
# Windows, при запуске dev-приложения:
set WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333
# затем GET http://127.0.0.1:9333/json/list → webSocketDebuggerUrl → Runtime.evaluate
```

Полезные ключи в журнале: `tf_task_journal_v1` (журнал задач), `tf_launch_log_v` (история
запусков). В установленном приложении origin другой — `http://tauri.localhost`, журналы
не общие с dev.
