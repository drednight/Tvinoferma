# Character Manager & Marathon Tracker (Tauri Edition)

Локальное desktop-приложение в стиле dashboard для учёта игровых персонажей, пати, древних монет, проходок в данжи и марафонов с заданиями, этапами, комбо-наградами и запасными днями.

Основной формат приложения — **Tauri**.  
Фронтенд написан на **vanilla JavaScript + HTML + CSS**, без обязательного использования UI-фреймворков.  
Данные хранятся локально на ПК в JSON-файле, а не только в браузере.

---

## Ключевые особенности

- Работает как установленное приложение на ПК.
- Хранит данные локально в файле `state.json`.
- Имеет резервные копии состояния.
- Поддерживает экспорт/импорт JSON для переноса на другой ПК.
- Опционально поддерживает Google Drive для облачного бэкапа.
- Опционально поддерживает Google Sheets для выгрузки выбранных данных в таблицу.
- Интерфейс выполнен в стиле dashboard v2.
- Позже может быть дополнен иконками классов.

---

## Технологии

### Frontend

- HTML;
- CSS;
- Vanilla JavaScript;
- ES Modules.

### Desktop runtime

- Tauri v2;
- Rust backend для работы с файлами, окном, настройками и системными функциями.

### Storage

- Основное хранилище в Tauri-режиме: локальный файл `state.json`.
- Fallback для браузерной разработки: `localStorage`.

### Optional cloud integrations

- Google Drive API;
- Google Sheets API.

## Режимы работы

### 1. Tauri desktop-приложение

Основной режим.

Приложение устанавливается на ПК и работает как обычное desktop-приложение.

Данные хранятся локально, например:

#### Windows

```txt
C:\Users\<username>\AppData\Roaming\com.charactermanager.app\state.json
```

#### macOS

```txt
~/Library/Application Support/com.charactermanager.app/state.json
```

#### Linux

```txt
~/.local/share/com.charactermanager.app/state.json
```

В этой же папке могут храниться резервные копии:

```txt
state.json
state.backup-1.json
state.backup-2.json
state.backup-3.json
settings.json
logs/
```

---

### 2. Браузерный dev-режим

Для быстрой разработки фронтенда можно запускать приложение в браузере.

В этом режиме данные хранятся в `localStorage`.

Это не основной режим, но он удобен для проверки UI и логики без сборки Tauri.

## Установка и запуск

### Требования

Для разработки и сборки Tauri-приложения нужны:

- Node.js 20+;
- npm или pnpm/yarn;
- Rust;
- Cargo;
- системные зависимости Tauri;
- на Windows — WebView2 Runtime.

Официальные зависимости Tauri лучше проверять по документации Tauri для вашей ОС.

---

### Установка зависимостей

```bash
npm install
```

---

### Запуск в браузере для разработки

```bash
npm run dev
```

Используется для быстрого просмотра UI.

Данные в этом режиме сохраняются в `localStorage`.

---

### Запуск Tauri-приложения в dev-режиме

```bash
npm run tauri dev
```

Приложение откроется как desktop-окно.

Данные будут сохраняться в локальный `state.json`.

---

### Сборка приложения

```bash
npm run tauri build
```

Готовые установщики и portable-сборки появятся в папке:

```txt
src-tauri/target/release/bundle/
```

В зависимости от ОС там могут быть:

- `.msi` / `.exe` для Windows;
- `.dmg` / `.app` для macOS;
- `.deb` / `.rpm` / `.AppImage` для Linux.

## Party

Пати хранятся как отдельные сущности, но персонаж ссылается на пати **по названию**, а не по ID.

```js
{
  name: "Основной состав",
  createdAt: "ISO date",
  updatedAt: "ISO date"
}
```

Правила:

- название пати уникально;
- сравнение названий происходит после `trim()`;
- при переименовании пати всем персонажам старой пати обновляется поле `party`;
- при удалении пати персонажи не удаляются;
- у персонажей удалённой пати `party` становится `null`;
- в UI `null` отображается как `Без пати`.

## Марафоны

Марафон — событие с участниками, заданиями, этапами, комбо-наградами и запасными днями.

Марафон начинается с `startDate` и длится до `endDate` включительно.

### Основные сущности

- участники;
- задания;
- этапы заданий;
- комбо-награды;
- записи выполнения;
- итоговые награды;
- запасные дни каждого задания.

---

## Участники марафона

Участники выбираются из списка персонажей.

Возможности:

- выбрать всех;
- снять всех;
- искать по нику;
- фильтровать по классу;
- фильтровать по пати.

---

## Задания марафона

Пользователь создаёт задания.

Каждое задание имеет:

- название;
- описание;
- требуемое количество зачётов;
- запасные дни;
- расписание;
- этапы награды.

Пример:

```txt
Задание: Убить 50 монстров
Требуется зачётов: 20
Запасные дни: 5

Этапы:
- 10 зачётов: награда A
- 20 зачётов: награда B
```

В один день может быть несколько заданий.

---

## Расписание заданий

Задание может быть:

### everyDay

Доступно во все дни марафона.

### dates

Доступно только в указанные даты.

Для таблицы выполнения используются даты марафона.

---

## Таблица марафона

Используется вариант: **один столбец на день**.

Пример:

```txt
Персонаж   01.09                         02.09
Hero123    [x] Убить 50 монстров         [ ] Убить 50 монстров
           [ ] Пройти данж               [x] Пройти данж

Mage99     [x] Убить 50 монстров         [x] Убить 50 монстров
           [x] Пройти данж               [ ] Пройти данж
```

Если в день несколько заданий, они показываются списком в одной ячейке.

---

## Этапы награды

Этап задания имеет:

- порог в количестве зачётов;
- текстовое описание награды;
- количество древних монет, если награда включает монеты.

Пример:

```txt
Этап 10:
  Награда: малый сундук
  Древние монеты: 50

Этап 20:
  Награда: большой сундук
  Древние монеты: 100
```

---

## Правило награды за этапы

Персонаж получает награду **только за максимальный достигнутый этап**.

Поэтапные награды не суммируются.

Пример:

```txt
Этапы: 10, 15, 20
Персонаж выполнил 20 зачётов.
Награда выдаётся только за этап 20.
```

Если персонаж выполнил 16 зачётов:

```txt
Максимальный достигнутый этап: 15
Награда выдаётся только за этап 15.
```

Если персонаж выполнил 9 зачётов:

```txt
Награда не выдаётся.
```

---

## Запасные дни задания

Запасные дни считаются **отдельно для каждого задания марафона**.

Для каждого задания и каждого персонажа вычисляются:

```txt
availableChecks = количество дат, в которые задание доступно
completedChecks = количество выполненных отметок
targetChecks = требуемое количество зачётов
spareDays = запасные дни задания
```

Пропущенные зачёты:

```txt
missedChecks = max(0, availableChecks - completedChecks)
```

Осталось до цели:

```txt
remainingToTarget = max(0, targetChecks - completedChecks)
```

Осталось запасных дней:

```txt
spareRemaining = max(0, spareDays - missedChecks)
```

Персонаж находится в допуске по запасным дням, если:

```txt
missedChecks <= spareDays
```

---

### Пример запасных дней

Марафон:

```txt
2026-09-01 — 2026-09-10
```

Задание доступно каждый день:

```txt
availableChecks = 10
```

Настройки задания:

```txt
targetChecks = 7
spareDays = 3
```

Персонаж выполнил:

```txt
completedChecks = 6
```

Расчёт:

```txt
missedChecks = 10 - 6 = 4
remainingToTarget = 7 - 6 = 1
spareRemaining = max(0, 3 - 4) = 0
```

Вывод:

```txt
Не хватает 1 зачёт до цели.
Запасные дни закончились.
```

---

## Влияние запасных дней на награду

Награда за этап задания выдаётся только если персонаж не превысил запасные дни этого задания.

Условие получения награды:

```txt
completedChecks >= threshold этапа
AND
missedChecks <= task.spareDays
```

Если запасные дни превышены, задание считается проваленным по допуску, даже если количество выполненных зачётов формально достигает этапа.

---

## Процент выполнения марафона

Процент считается по максимальному этапу, то есть по требуемому количеству зачётов.

Для одного задания:

```txt
taskPercent = completedChecks / targetChecks * 100
```

Для всего марафона:

```txt
overallPercent =
  sum(completedChecks по всем заданиям) /
  sum(targetChecks по всем заданиям) * 100
```

Значение ограничивается сверху:

```txt
100%
```

Если заданий нет:

```txt
overallPercent = 0
```

Процент показывает прогресс по зачётам.  
Запасные дни показывают отдельный допуск по пропускам.

---

## Сколько нужно пройти заданий для награды

Для каждого задания показывается:

```txt
Осталось зачётов до цели = targetChecks - completedChecks
```

Если значение равно `0`, цель по зачётам достигнута.

Также показывается:

```txt
Осталось запасных дней = max(0, spareDays - missedChecks)
```

Если запасные дни закончились, награда по этому заданию не выдаётся.

---

## Комбо-награды

Марафон может содержать особые награды за выполнение условий по нескольким заданиям.

Пример:

```txt
Комбо-награда: Мастер марафона
Условие: закрыть максимальные этапы минимум у 4 заданий из 5.
Награда: 300 древних монет + особый титул.
```

Для MVP поддерживается условие:

```txt
allStagesInTasks
```

Задание считается полностью закрытым, если:

```txt
completedChecks >= максимальный threshold среди этапов задания
AND
missedChecks <= task.spareDays
```

Если у задания нет этапов, оно не участвует в комбо-условии `allStagesInTasks`.

Комбо-награда выдаётся, если количество полностью закрытых заданий больше или равно `minTasks`.

Завершение доступно:

- в финальный день;
- после финального дня;
- или вручную, если нужно подвести итоги раньше.

При завершении система:

1. считает выполненные зачёты по каждому участнику и каждому заданию;
2. считает пропущенные зачёты;
3. проверяет запасные дни по каждому заданию;
4. определяет максимальный достигнутый этап;
5. начисляет награды только за максимальный этап;
6. проверяет комбо-награды;
7. создаёт записи о наградах;
8. если награда включает древние монеты, добавляет операцию в локальную историю монет персонажа;
9. переводит марафон в статус `completed`;
10. блокирует таблицу для обычного редактирования.

---

## Редактирование после завершения

После завершения марафона можно нажать:

```txt
Редактировать итоги
```

Это позволяет:

- исправить отметки;
- изменить задания;
- изменить этапы;
- изменить комбо-награды;
- снова завершить марафон и пересчитать итоги.

Если награды изменились, система корректирует древние монеты новыми записями в локальную историю.

Пример:

```txt
Было начислено: +100
Стало нужно: +50
Добавляется корректирующая запись: -50
```

Или:

```txt
Было начислено: +50
Стало нужно: +100
Добавляется корректирующая запись: +50
```

Такой подход сохраняет локальную историю изменений.

## Режимы импорта

При импорте JSON пользователь выбирает режим.

### 1. Заменить всё

Текущие данные полностью очищаются.

Вместо них загружаются данные из файла.

Требуется подтверждение.

Перед заменой рекомендуется создавать резервную копию.

---

### 2. Добавить только новое

Добавляются только те записи, которых ещё нет по `id`.

Существующие записи не изменяются.

---

### 3. Слить

Объединяет локальные и импортируемые данные.

Для конфликтов записей с одинаковым `id` доступны два под-режима.

---

## Разрешение конфликтов при слиянии

### Last write wins

Система сравнивает `updatedAt`.

Более свежая запись заменяет более старую.

Если импортируемая запись персонажа применяется к существующему персонажу:

- `ancientCoins` берётся из импорта;
- локальная `coinHistory` очищается, потому что история не переносится и может противоречить новому балансу.

Пользователь должен быть предупреждён об этом.

---

### Ручной разбор расхождений

Пользователь может выбрать режим:

```txt
Показать расхождения
```

Тогда для каждого конфликтующего персонажа открывается окно сравнения.

В окне показываются две карточки:

```txt
Локальная версия        Импортируемая версия
```

Карточки отображаются как раскрытая карточка персонажа.

Показываются все данные:

- ник;
- класс;
- пати;
- уровень;
- небо;
- уровень неба;
- email;
- пароль;
- дополнительная почта;
- телефон;
- проходки;
- древние монеты.

Различия подсвечиваются.

Чувствительные поля по умолчанию маскируются:

```txt
••••••••
```

Но пользователь может временно раскрыть их для сравнения.

Пользователь выбирает:

```txt
Оставить локальную версию
```

или:

```txt
Взять импортируемую версию
```

Если выбрана импортируемая версия:

- `coinHistory` очищается;
- `ancientCoins` берётся из импорта.

Если выбрана локальная версия:

- локальные данные не меняются.

}

То есть после изменения данных приложение ждёт 1 секунду и сохраняет `state.json`.

Также сохранение может выполняться:

- при закрытии окна;
